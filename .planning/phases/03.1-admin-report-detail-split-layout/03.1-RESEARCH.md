## Summary

Phase 3.1 is a frontend-only restructure of a single 651-line React page (`frontend/app/admin/reports/[id]/page.tsx`) and targeted bug fixes in one panel component (`GbaHierarchyPanel.tsx`). No new packages are needed, no API changes are required, and no new routes are added.

The core work has two independently deliverable parts: (1) restructure the `rightPanel` JSX variable so that metadata (status badges, telemetry grid) moves to the left column as an "identity strip" below the photo, while the action panels (StatusActionPanel, OrgAssignPanel, GbaHierarchyPanel, description, map, history) remain in the right column with independent scroll, and (2) fix six display bugs in `GbaHierarchyPanel` and the status timeline dot color map.

The existing split layout grid (`gridTemplateColumns: "1.3fr 1fr"`) already exists at `page.tsx:511`. The breakpoint guard (`isDesktop` via `matchMedia`) already exists at `page.tsx:68`. All named component primitives (StatusBadge, SeverityIndicator, ConfidencePill, Pill, Card, SectionLabel) are already imported. This phase is exclusively a redistribution of existing JSX between two already-existing DOM regions — no new component files are required, though the planner has discretion to extract named subcomponents.

**Primary recommendation:** Restructure `page.tsx` in a single plan (03.1-01-PLAN.md). Wave 0 adds tests for new left-column content and the bug-fix assertions. Wave 1 implements the layout change and bug fixes. Wave 2 verifies build + full test suite.

### Pattern 1: Flex Column Left Panel with Sticky Identity Strip

**What:** Left column uses `flex-direction: column` so the photo hero grows to fill space (`flex: 1`) and the identity strip is anchored at the bottom (`flex-shrink: 0`). The outer container has `overflow: hidden` so neither region scrolls.

**When to use:** Any panel where a large visual (photo/map) should fill available height and metadata "hugs" the bottom.

**Example (D-03 spec):**

### Anti-Patterns to Avoid

- **Moving mobile layout:** The mobile single-column path (`page.tsx:543-578`) must remain untouched. Only the `isDesktop = true` branch changes.
- **Removing `rightPanel` variable without updating mobile path:** If `rightPanel` JSX variable is split into left/right content, the mobile path must receive the combined content (or continue to reference the right-rail content for mobile, plus the identity strip content separately). Double-check the mobile `{rightPanel}` reference at `page.tsx:577`.
- **Inline `display: none` for null rows:** D-08 says hide the row entirely — filter the array, do not CSS-hide it. Hidden DOM elements still affect screen readers.
- **Breaking existing 12 tests:** The existing `page.test.tsx` checks `screen.getByText("broken_footpath")` (the CATEGORY telemetry row), `StatusBadge` presence, ward name, description — all of these must continue to pass. Since the telemetry grid moves to the identity strip (left column), not right column, its DOM presence is unchanged for test assertions.
- **Forgetting `isFirst` prop on first `ChainRowItem`:** The `ChainRowItem` component uses `isFirst` to suppress the top border on the first row. After conditional rendering, the first visible row may no longer be index 0 of the original array. Recompute `isFirst` from the filtered array.

## Common Pitfalls

### Pitfall 1: Mobile Path Regression

**What goes wrong:** Identity strip JSX is added to the desktop left column but the mobile path (`isDesktop = false`) still renders `rightPanel` which no longer includes the status/telemetry content, leaving mobile users with no badges or telemetry grid.

**Why it happens:** The desktop and mobile render paths diverge at line 510. The `rightPanel` variable is currently shared. When you split its content, you must update BOTH paths.

**How to avoid:** After restructuring, trace both branches of the `isDesktop` ternary and verify each renders: (1) photo, (2) status badges, (3) telemetry, (4) all action panels.

**Warning signs:** Test for `screen.getByText("Ward 27")` fails — that text is in the telemetry grid, which moves to the identity strip; if the mobile path omits it, the test still passes for desktop but mobile is broken.

### Pitfall 2: `isFirst` on ChainRowItem After Filtering

**What goes wrong:** After filtering null-name rows from `bureaucraticChain`, the Ward row (index 0 in the filtered array) still gets `isFirst={true}` — but if a null check causes the first visible row to be something other than index 0 of the unfiltered array, the border appears incorrectly.

**Why it happens:** `isFirst` is currently derived from `idx === 0` where `idx` is the `map()` index. After filter, recompute: use the filtered array's index.

**How to avoid:** Apply `.filter(...)` first, then `.map((row, idx) => <ChainRowItem isFirst={idx === 0} ... />)`.

**Warning signs:** First chain row shows an unexpected top border.

### Pitfall 3: `wardDisplay` Template Literal Coerces `undefined`

**What goes wrong (ISSUE-01):** `ward_number` is typed as `number | null` in `WardHierarchy`, but if the API returns the field as `undefined` (missing key rather than explicit `null`), `hierarchy.ward_number != null` is `false` for `null` but `true` for `undefined` — JavaScript's `!= null` check is `!== null && !== undefined`, so actually `undefined != null` is `false` too. Wait — in JS, `undefined != null` evaluates to `false` (loose equality). So `hierarchy.ward_number != null` should correctly guard against both `null` and `undefined`.

**Root cause:** The observed "undefined - Sampangirama Nagar" string suggests `ward_number` is coming through as the string `"undefined"` not JS `undefined`, OR the guard is passing a falsy value. Inspect: is `ward_number` a string "undefined" from JSON? Possible if the Rust serializer emits it.

**How to avoid:** In `wardDisplay`, use: `const wardDisplay = hierarchy.ward_number != null ? \`${hierarchy.ward_number} · ${hierarchy.ward_name}\` : hierarchy.ward_name`. Add a string check: if `typeof hierarchy.ward_number === 'string' && hierarchy.ward_number === 'undefined'`, treat as null.

**Warning signs:** Ward row renders "undefined · Ward Name".

### Pitfall 4: `calc(100vh - 120px)` Offset Mismatch

**What goes wrong:** The `120px` in `calc(100vh - 120px)` assumes the admin layout header is 120px tall. If the admin layout adds padding at different breakpoints, the left column may overflow or fall short of the viewport.

**Why it happens:** The `desktopActionBar` adds ~56px above the grid. The page container adds `padding: "24px 32px"`. Together: 24px top pad + ~56px action bar + 8px gap ≈ 88px. D-03 specifies 120px as the offset — verify this matches the actual layout.

**How to avoid:** Cross-check in the browser at 768px, 1024px, and 1440px. If `120px` is too small, the left column escapes its container and causes scroll on the page body.

**Warning signs:** Right rail scroll does not work; whole page scrolls instead.

### Pitfall 5: `rightPanel` Variable Still Referenced on Mobile

**What goes wrong:** After refactoring `rightPanel` into left-col and right-col content, the mobile path at line 577 (`{rightPanel}`) will reference a variable that no longer exists or is incomplete.

**Why it happens:** `rightPanel` is a JSX variable defined once, used in two places. When restructured, the mobile path needs updating.

**How to avoid:** After splitting `rightPanel` into `identityStripContent` and `actionRailContent`, the mobile path should render: `{identityStripContent}{actionRailContent}` in order.

1. **ISSUE-01 exact root cause**
   - What we know: `wardDisplay` template literal renders "undefined - Sampangirama Nagar"; `ward_number` is `number | null` in the TypeScript interface
   - What's unclear: Is the API returning the JSON key `ward_number` as the string `"undefined"`, or is it absent from the response (JS `undefined`), or is there a field name mismatch?
   - Recommendation: During implementation, add a `console.log(hierarchy)` in dev to inspect the raw API response for a report with a known ward. The fix is either (a) the existing `!= null` guard is sufficient and the bug is already fixed in the current code, or (b) add `typeof hierarchy.ward_number === 'string'` guard.

2. **ISSUE-04 display intent**
   - What we know: "162 - Shivajinagar" is constructed as a combined string in `acLabel`; CONTEXT.md says fix label formatting to show AC number and name separately
   - What's unclear: Should they be in separate DOM elements (e.g., `<span>162</span> <span>Shivajinagar</span>`) or just better typographically (e.g., `162` in mono, constituency name in sans)?
   - Recommendation: Apply Direction B typography pattern: AC number in `var(--font-mono)` as a label, constituency name in `var(--font-sans)` as a value — consistent with how telemetry rows are rendered elsewhere.

3. **`rightPanel` refactor scope**
   - What we know: `rightPanel` is a 190-line JSX variable used in two places (desktop right column and mobile single column)
   - What's unclear: Whether to extract into named subcomponents (e.g., `IdentityStrip`, `ActionRail`) or keep as inline JSX sections within `page.tsx`
   - Recommendation: Keep inline in `page.tsx` as named JSX variables (`const identityStripContent = ...`, `const actionRailContent = ...`). The file is already 651 lines; adding component files for these single-use sections would add complexity without benefit.
