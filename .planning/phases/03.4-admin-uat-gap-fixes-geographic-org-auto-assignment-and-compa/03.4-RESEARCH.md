# Phase 3.4: Admin UAT Gap Fixes — Geographic Org Auto-Assignment and Compact-Row Navigation — Research

**Researched:** 2026-06-01T02:13:27Z
**Domain:** Rust/Axum backend (create_report handler + admin_queries.rs) + Next.js frontend (ReportsTable.tsx compact-row tap target)
**Confidence:** HIGH

## Summary

Phase 3.4 closes two confirmed UAT gaps from Phase 3 re-testing (NF-03-A and NF-03-B). Both are surgical, well-scoped changes with no schema migrations required.

**NF-03-B (major)** — Geographic org auto-assignment at report creation. The `create_report` handler in `backend/src/handlers/reports.rs` currently calls `queries::insert_report(...)` with no `assigned_org_id`. After ward_id is resolved, the handler must look up the matching corporation in `organizations` using the ward's `wards.corporation` TEXT field (e.g. `'Central'`), then set `reports.assigned_org_id` to that org's UUID and insert a `status_history` row with `changed_by = NULL` (system action). The `list_admin_reports` query in `admin_queries.rs` currently reads `wards.corporation AS corporation` (raw geography string). It must switch to a `LEFT JOIN organizations o ON o.id = reports.assigned_org_id` so the CORP column shows the full org name (e.g., `'Bengaluru Central Corporation'`).

**NF-03-A (minor)** — Compact-row tap target. The `CompactRow` component in `frontend/app/admin/components/ReportsTable.tsx` (line ~425) renders the entire row as a plain `<div>`. Only the `WLK-XXXXX` chip is linked. The fix is to wrap the non-button body of the CompactRow in an `<a>` or add a navigation onClick, while preserving the Status and Delete button tap zones as separate interactive elements.

**Primary recommendation:** Two isolated plans — Plan 1 handles NF-03-B (backend: DB lookup + status_history insert + list query fix), Plan 2 handles NF-03-A (frontend: CompactRow navigation) — with no new DB migrations and no dependency between the two plans.

### Pattern 1: Org Lookup After Ward Resolution (NF-03-B Backend)

The UAT gap description provides the exact query to use [VERIFIED: 03-UAT.md product_direction]:

```rust
// Source: 03-UAT.md NF-03-B product_direction
// After ward_id is resolved in create_report:
let assigned_org_id: Option<Uuid> = if let Some(wid) = ward_id {
    // Fetch corporation string from wards table, then match to organizations
    queries::get_org_for_ward(&state.pool, wid).await.unwrap_or_else(|e| {
        tracing::warn!(ward_id = %wid, error = %e, "Org auto-assign lookup failed; proceeding with NULL");
        None
    })
} else {
    None
};
```

The DB function needs two queries or one JOIN:
```sql
-- Option A: Single query via JOIN (preferred — avoids round-trip)
SELECT o.id
FROM wards w
JOIN organizations o ON o.org_type = 'corporation'
  AND o.name ILIKE '%' || w.corporation || '%'
WHERE w.id = $1
LIMIT 1
```

This is safe because `wards.corporation` contains only the five values: `Central`, `North`, `East`, `South`, `West` — sourced from the trusted migration backfill, not user input. [VERIFIED: 009_ward_hierarchy.sql inspection, 010_org_seed.sql inspection]

### Pattern 2: status_history Insert with `changed_by = NULL`

The `status_history` table was created in `001_init.sql` with `note TEXT` (nullable). The `changed_by UUID` column was added in `002_admin.sql` as nullable (`REFERENCES admin_users(id) ON DELETE SET NULL`). [VERIFIED: migration file inspection]

The existing `assign_report_org` function in `admin_queries.rs` shows the insert pattern:

```rust
// Source: backend/src/db/admin_queries.rs:assign_report_org (verified by reading file)
sqlx::query(
    r#"INSERT INTO status_history (report_id, new_status, note, changed_by)
       VALUES ($1, $2::report_status, $3, $4)"#,
)
.bind(report_id)
.bind("open")           // status stays 'open' — NF-03-B product direction
.bind("Auto-assigned based on ward geography")
.bind(None::<Uuid>)     // changed_by = NULL (system action)
.execute(pool).await?;
```

Note: status stays `'open'` for auto-assignment at creation. Only the manual admin `assign_report_org` auto-advances to `'assigned'` (D-09). The auto-assignment at creation is purely for routing — the report is newly submitted.

### Pattern 4: CompactRow Full-Card Navigation (NF-03-A Frontend)

The `CardStreamRow` component in the same file uses a different approach — it has a `<a href=...>` wrapping only the WLK chip in the header, with Status/Delete buttons as separate interactive elements. The compact row must be made fully tappable.

Two safe approaches for accessible full-card navigation while preserving button tap zones:

**Option A — Overlay anchor (pattern used in DupeSubTable):**
```tsx
// Source: ReportsTable.tsx DupeSubTable pattern (verified by reading file)
// Add sr-only anchor + onClick on the outer div:
<div
  style={{ cursor: 'pointer', ...existingStyles }}
  onClick={() => window.location.assign(`/admin/reports/${report.id}`)}
>
  <a href={`/admin/reports/${report.id}`} className="sr-only">
    View report {report.id}
  </a>
  {/* existing content */}
  <Btn onClick={(e) => { e.stopPropagation(); onStatusChange(report.id); }}>Status</Btn>
  <Btn onClick={(e) => { e.stopPropagation(); onDelete(report.id); }}>Delete</Btn>
</div>
```

**Option B — useRouter push:**
```tsx
// Uses Next.js router for SPA-style navigation
import { useRouter } from 'next/navigation';
const router = useRouter();
<div onClick={() => router.push(`/admin/reports/${report.id}`)}>
```

**Recommendation: Option A** — consistent with the `DupeSubTable` row pattern already established in the same file (`window.location.assign` + `sr-only anchor`). The `STATE.md` decision records this pattern explicitly: "sr-only anchor + onClick=window.location.assign used for navigable `<tr>` rows." [VERIFIED: STATE.md Decisions section]

The Status and Delete `<Btn>` components must call `e.stopPropagation()` so tapping them does not trigger the card navigation.

### Anti-Patterns to Avoid

- **Do NOT auto-advance status to `'assigned'` on creation** — NF-03-B product direction explicitly states `status stays 'open'`. Only the manual admin `assign_report_org` (OrgAssignPanel) advances to `'assigned'` per D-09.
- **Do NOT use ILIKE on user input** — the `wards.corporation` string used in the ILIKE query comes from the trusted migration backfill (only 5 known values), not from user-submitted data.
- **Do NOT change `insert_report` return type** — the `Report` struct already has `assigned_org_id: Option<Uuid>`. The query just needs to be updated to bind the new parameter and the INSERT must include the column.
- **Do NOT use `e.preventDefault()` instead of `e.stopPropagation()`** in the Status/Delete button handlers — `stopPropagation` prevents the click from bubbling to the card's `onClick`, while `preventDefault` would block the button action itself.

## Common Pitfalls

### Pitfall 1: `insert_report` signature must change
**What goes wrong:** The current `queries::insert_report` signature does not accept `assigned_org_id`. Simply adding the auto-assign logic to the handler but not threading `assigned_org_id` through to the INSERT produces no compile error (Option<Uuid> defaults) but silently loses the assignment.
**How to avoid:** The INSERT SQL in `queries.rs` must gain the `assigned_org_id` column in the column list and a `$13` bind. The `Report` struct already has the field.

### Pitfall 2: status_history `note` column vs `note`/`notes` naming
**What goes wrong:** The `status_history` table uses `note` (singular) per `001_init.sql`. The `STATUS_HISTORY_SQL` in `admin_queries.rs` reads `sh.note`. The insert must use `note`, not `notes`.
**How to avoid:** Confirmed: column is `note TEXT` in `001_init.sql` line 76. [VERIFIED: migration inspection]

### Pitfall 3: Two SQL queries affected for NF-03-B
**What goes wrong:** Only fixing the `create_report` handler without fixing `list_admin_reports` leaves the CORP column still showing the raw geography string. The UAT success criterion #2 explicitly requires the list column to show the org name.
**How to avoid:** Both changes must be in the same plan/phase. The test for NF-03-B should assert on `list_admin_reports` SQL containing `reports.assigned_org_id` in the JOIN.

### Pitfall 4: `e.stopPropagation()` must be on the Btn's `onClick` wrapper, not inside the Btn component itself
**What goes wrong:** Adding stopPropagation inside `Btn.tsx` is a global change that would affect all Btn usage — not appropriate.
**How to avoid:** Add `(e) => { e.stopPropagation(); originalHandler(id); }` inline in `CompactRow`'s Btn props.

### Pitfall 5: `old_status` column in status_history
**What goes wrong:** The `status_history` table has an `old_status` column (nullable `report_status`). Existing `assign_report_org` and `update_report_status` functions do NOT set `old_status`. The auto-assignment insert should follow the same pattern — omit `old_status` (defaults to NULL).
**How to avoid:** Match the insert pattern from `assign_report_org` exactly.

### Pitfall 6: Ward lookup may return `None` — org lookup must be `None`-safe
**What goes wrong:** If `ward_id` is None (PostGIS failure, out-of-bounds point), the org lookup cannot run. Attempting to query with a NULL ward_id would produce an error.
**How to avoid:** Org lookup only runs `if let Some(wid) = ward_id`. When ward_id is None, `assigned_org_id = None`.

## Code Examples

### Example 1: Org lookup DB function (new function in queries.rs)

```rust
// New function: queries::get_org_for_ward
// Matches 'Central' → 'Bengaluru Central Corporation' via ILIKE
pub async fn get_org_for_ward(pool: &PgPool, ward_id: Uuid) -> Result<Option<Uuid>, AppError> {
    let row = sqlx::query_as::<_, (Uuid,)>(
        r#"
        SELECT o.id
        FROM wards w
        JOIN organizations o
          ON o.org_type = 'corporation'
          AND o.name ILIKE '%' || w.corporation || '%'
        WHERE w.id = $1
        LIMIT 1
        "#,
    )
    .bind(ward_id)
    .fetch_optional(pool)
    .await?;
    Ok(row.map(|(id,)| id))
}
```

## Open Questions

1. **Should the status_history auto-assign insert be in the same transaction as `insert_report`?**
   - What we know: `insert_report` is currently a single `sqlx::query_as` with no explicit transaction.
   - What's unclear: Product priority for strict atomicity (both fail or both succeed) vs. best-effort audit trail.
   - Recommendation: Best-effort (separate insert, non-fatal on error) is simpler and consistent with the existing non-fatal ward lookup pattern. If the planner prefers strict atomicity, a transaction can wrap both inserts in `create_report`.

2. **Should `insert_report` in `queries.rs` gain `assigned_org_id` as a parameter, or should the status_history-and-org-id logic all live in the handler?**
   - What we know: The current `insert_report` sets `assigned_org_id` to NULL implicitly (column not in the INSERT list).
   - Recommendation: Add `assigned_org_id: Option<Uuid>` to the `insert_report` function signature and include it in the INSERT SQL. This keeps the DB layer responsible for the INSERT shape and avoids a separate UPDATE after the fact.
