# Phase 03.4: Code Review Report

**Reviewed:** 2026-06-01T10:45:00Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

This phase introduces two features: (1) geographic org auto-assignment at report creation — the backend looks up the ward for a submitted coordinate and derives the owning BBMP corporation org, storing it as `assigned_org_id` at insert time; (2) a compact-row view mode in the admin `ReportsTable` component. The implementation is generally well-structured, but three blocker-level defects were found: a status/history semantic mismatch in the auto-assign audit trail, a missing `e.stopPropagation()` that causes `DupeExpandButton` inside `CompactRow` to navigate away on every click, and test fixtures that use deprecated status values against a codebase that explicitly rejects them. Five additional warnings cover a hardcoded page-size constant in the pagination display, unused declared props in `ReportsTable`, unsafe `as unknown as` type casts, and mismatched SQL structure in a SQL-string unit test.

## Critical Issues

### CR-01: Auto-assign status_history audit record uses wrong status token

**File:** `backend/src/handlers/reports.rs:308-309`
**Issue:** The `status_history` row inserted after a geographic org auto-assignment uses `'open'::report_status` as the `new_status`. This is semantically incorrect: the audit trail is meant to record the fact that the report was auto-assigned to an organization at creation time. Using `'open'` means the status history will show a duplicate "open" event that is indistinguishable from the report's initial status, providing no information about the auto-assignment. When an admin later reviews the history for an auto-assigned report they will see two consecutive `open` entries — one from the default creation state and one from this insert — with no visible evidence that a geographic assignment occurred. The correct token for this event is `'assigned'::report_status`, matching what `assign_report_org()` uses in `admin_queries.rs:789` for the manual assignment path.

Additionally, the test at `admin_queries.rs:2207-2211` explicitly asserts that this SQL contains `'open'::report_status`, so the test encodes the same bug and will not catch a fix unless updated together.

**Fix:**
```rust
// handlers/reports.rs line 308
sqlx::query(
    r#"INSERT INTO status_history (report_id, new_status, note, changed_by)
       VALUES ($1, 'assigned'::report_status, 'Auto-assigned based on ward geography', NULL)"#,
)
```
The corresponding test assertion in `admin_queries.rs:2209` must also change from `'open'::report_status` to `'assigned'::report_status`.

### CR-02: `DupeExpandButton` inside `CompactRow` has no `e.stopPropagation()` — expand click navigates away

**File:** `frontend/app/admin/components/ReportsTable.tsx:143`
**Issue:** `DupeExpandButton` renders a `<button>` with `onClick={() => onToggle(reportId)}` (line 143). When this button is rendered inside `CompactRow`, the parent `<div>` at line 442 also has `onClick={() => window.location.assign(...)}`. Because the button's click handler does not call `e.stopPropagation()`, every click on the "expand duplicates" button will bubble to the parent container and trigger a full-page navigation to the report detail page — making it impossible to expand duplicates without navigating away. The action buttons inside `CompactRow` (Status, Delete) correctly call `e.stopPropagation()` at lines 508 and 517, but the `DupeExpandButton` abstraction was not updated to follow the same pattern. This is a functional regression: the expand feature is effectively broken in compact-rows mode.

**Fix:**
```tsx
// DupeExpandButton — change the button's onClick to stop propagation:
<button
  data-testid="expand-duplicates-btn"
  onClick={(e) => { e.stopPropagation(); onToggle(reportId); }}
  // ... rest of props
>
```
Since `DupeExpandButton` is also used inside the desktop table view (where the row container does not have a navigation handler), the `stopPropagation` call is safe and harmless there.

### CR-03: Test fixtures use deprecated status values `"submitted"` / `"under_review"` that the production codebase explicitly rejects

**File:** `frontend/app/admin/components/__tests__/ReportsTable.test.tsx:46,54`
**Issue:** `REPORT_A.status = "submitted"` and `REPORT_B.status = "under_review"`. These values were renamed in migration 008 (see `admin.rs` and the backend `validate_status()` function, which explicitly rejects both). The test at line 128 asserts `data-tone="info"` and `data-status="submitted"` against a `StatusBadge` that only handles these values via a backward-compat legacy branch in `StatusBadge.tsx`.

This is a testing contract problem: the fixtures exercise a legacy code path that will be removed, not the current production data shape. Any test that passes because `StatusBadge` still supports `"submitted"` for backward compatibility gives false confidence. New reports in the system will never have `status="submitted"`, so these tests do not exercise real-world rendering. When the legacy fallback is eventually removed (a stated intent), these tests will start failing from a fixture problem rather than a logic regression, making root-cause analysis harder.

Furthermore, the test at line 136 asserts `badge.getAttribute("data-status") === "submitted"`. If a future cleanup normalises `"submitted"` → `"open"` in `StatusBadge`, this assertion will fail from a fixture change, not a bug.

**Fix:** Update all test fixtures to use current status enum values:
```typescript
const REPORT_A = {
  id: "report-uuid-001",
  category: "broken_footpath",
  severity: "high",
  status: "open",           // was "submitted"
  created_at: "2026-03-01T10:00:00Z",
};

const REPORT_B = {
  id: "report-uuid-002",
  category: "poor_lighting",
  severity: "low",
  status: "acknowledged",   // was "under_review"
  created_at: "2026-03-02T12:00:00Z",
  image_path: "uploads/img002.jpg",
};
```
Update the assertion at line 136 to match (`"data-status"` → `"open"`), and line 128 to check for `"open"` rather than `"submitted"`.

## Warnings

### WR-01: Pagination display hardcodes page size `20` regardless of `limit` prop

**File:** `frontend/app/admin/components/ReportsTable.tsx:801`
**Issue:** The pagination range label computes `((page - 1) * 20) + 1` and `Math.min(page * 20, totalCount ?? 0)`. The multiplier `20` is a hardcoded magic number, not derived from the `limit` prop that the parent passes down. When a parent renders `<ReportsTable totalCount={200} page={2} totalPages={5} />` with an implicit page size of 40, the label will display "21–40" instead of the correct "41–80". There is no `limit` prop on `ReportsTableProps` for the pagination display to use. This produces consistently wrong pagination labels whenever the page size is anything other than 20.

**Fix:** Add a `pageSize` (or reuse `limit`) prop and substitute it for the literal `20`:
```tsx
// In ReportsTableProps:
pageSize?: number;  // actual items per page, defaults to 20

// In pagination display:
const ps = pageSize ?? 20;
{((page - 1) * ps) + 1}–{Math.min(page * ps, totalCount ?? 0)} / {totalCount ?? 0}
```

### WR-02: `onCategoryChange` and `onStatusFilter` props are declared but never used

**File:** `frontend/app/admin/components/ReportsTable.tsx:42-43`
**Issue:** `ReportsTableProps` declares `onCategoryChange?: (value: string) => void` and `onStatusFilter?: (value: string) => void` (lines 42-43). Neither prop is referenced anywhere in the component body. The component implements its own internal filter chip / search state that ignores these callbacks. Any parent component that passes these props expecting them to be called will silently receive no behaviour. This is a dead interface that misleads callers.

**Fix:** Either remove the declarations from `ReportsTableProps` if the parent-driven filtering pattern is no longer used, or wire the callbacks to the internal `toggleFilter` and status filter logic.

### WR-03: `corporation` field access uses `as unknown as` type cast — bypasses type safety

**File:** `frontend/app/admin/components/ReportsTable.tsx:1047-1049`
**Issue:**
```tsx
{(report as unknown as {corporation?: string | null}).corporation
  ?? (report as unknown as {ward_hierarchy?: {corporation?: string | null}}).ward_hierarchy?.corporation
  ?? "—"}
```
The `corporation` field is not in the `Report` interface defined at lines 17-34. Rather than extending the interface to include the field that `list_admin_reports` returns (it is explicitly selected as `o.name AS corporation` in `admin_queries.rs:386`), the code escapes to `as unknown as` to access it. This means TypeScript provides zero type-checking on the field shape. If the API response shape changes (e.g., `corporation` is renamed), the fallback chain silently produces `"—"` with no compile-time error. The `ward_hierarchy` fallback path is further dead code — `list_admin_reports` never returns a `ward_hierarchy` nested object; that field only appears in `get_admin_report_by_id`.

**Fix:** Add `corporation` to the `Report` interface (it is always present from the API for the admin list endpoint):
```typescript
interface Report {
  // ... existing fields ...
  corporation?: string | null;   // from list_admin_reports LEFT JOIN organizations
}
```
Remove the `ward_hierarchy` fallback path — it cannot be populated from the list endpoint.

### WR-04: Unit test for org-scoped SQL uses inline CTE structure that differs from production code

**File:** `backend/src/db/admin_queries.rs:1976-2010`
**Issue:** The test `list_admin_reports_with_org_id_includes_recursive_cte` builds the org filter clause as:
```sql
AND reports.ward_id IN (
    WITH RECURSIVE org_subtree AS (...)
    SELECT w.id FROM wards w JOIN org_subtree s ON w.org_id = s.id
)
```
The production code (`list_admin_reports` and `count_admin_reports`) uses a **top-level** CTE (`WITH RECURSIVE org_subtree AS (...) SELECT ...`), not an inline CTE-in-subquery. PostgreSQL 11 and earlier reject inline CTEs inside `IN(...)` subqueries, which is documented at line 247 as the reason for the top-level approach. The test passes because it only checks that the string `"org_subtree"` appears somewhere, but it validates a SQL structure that the production code explicitly avoids. A reader consulting this test to understand the production SQL pattern will be misled.

**Fix:** Rewrite the test to mirror the actual production SQL structure:
```rust
// Assert the WHERE clause contains a ward_id IN (...) subselect without inline CTE
assert!(full_where.contains("reports.ward_id IN ("), ...);
assert!(!full_where.contains("WITH RECURSIVE"), ...); // CTE is top-level, not inline
```
And add a separate test that validates the CTE prefix string.

### WR-05: `toggleExpand` is defined as a non-`useCallback` async function inside the component body

**File:** `frontend/app/admin/components/ReportsTable.tsx:611-624`
**Issue:** `toggleExpand` is declared as `async function toggleExpand(...)` inside the component body at line 611. It is not wrapped in `useCallback` even though it captures `expandedRows`, `duplicateRows`, `setExpandedRows`, and `setDuplicateRows`. This function is passed as `onToggleExpand` to `CardStreamRow` and `CompactRow` child components, and as `onToggle` to `DupeExpandButton`. Without `useCallback`, a new function reference is created on every render, causing all consuming children to re-render unnecessarily. `toggleFilter` (line 598) is wrapped in `useCallback` but `toggleExpand` is not, making the inconsistency a maintenance hazard: future authors will not know which pattern to follow.

**Fix:**
```tsx
const toggleExpand = useCallback(async (reportId: string) => {
  const isNowExpanding = !expandedRows[reportId];
  setExpandedRows((prev) => ({ ...prev, [reportId]: isNowExpanding }));
  if (isNowExpanding && duplicateRows[reportId] === undefined) {
    try {
      const dupes = await getDuplicatesForReport(reportId);
      setDuplicateRows((prev) => ({ ...prev, [reportId]: dupes }));
    } catch {
      setDuplicateRows((prev) => ({ ...prev, [reportId]: [] }));
    }
  }
}, [expandedRows, duplicateRows]);
```

## Info

### IN-01: `getDayLabel` timezone assumption — uses local browser time for "TODAY" / "YESTERDAY" comparison

**File:** `frontend/app/admin/components/ReportsTable.tsx:85-95`
**Issue:** `getDayLabel` computes `today` using `new Date()` (browser local time) and compares it to a date parsed from an ISO timestamp. If the admin user's browser is in a timezone that differs from UTC (all Bengaluru browsers are UTC+5:30), a report submitted at 23:30 UTC (which is 05:00 the next day IST) will be labelled under the wrong day group. This is a display issue, not a data integrity issue, but it can cause confusion when the compact-row view groups reports across midnight UTC.

**Fix:** Normalise both sides of the comparison to UTC before computing the diff:
```typescript
function getDayLabel(isoString: string): string {
  const date = new Date(isoString);
  const now = new Date();
  // Compare calendar days in UTC to avoid timezone boundary issues
  const todayUTC = Date.UTC(now.getUTCFullYear(), now.getUTCMonth(), now.getUTCDate());
  const dUTC = Date.UTC(date.getUTCFullYear(), date.getUTCMonth(), date.getUTCDate());
  const diff = todayUTC - dUTC;
  if (diff === 0) return "TODAY";
  if (diff === 86400000) return "YESTERDAY";
  // ...
}
```

### IN-02: `update_last_login` does not check `rows_affected` — silently no-ops on unknown user ID

**File:** `backend/src/db/admin_queries.rs:99-105`
**Issue:** `update_last_login` executes `UPDATE admin_users SET last_login_at = NOW() WHERE id = $1` and discards the result. If called with a UUID that does not correspond to any row (e.g., a race between login and deactivation), the function returns `Ok(())` silently. The login handler calls this after successful credential verification, so the window for a missing row is narrow, but the silent discard means telemetry/logging will not capture this event. This is not a security issue but is a missed opportunity for an audit log entry.

**Fix:** Log a warning when `rows_affected() == 0`:
```rust
let result = sqlx::query(...)...execute(pool).await?;
if result.rows_affected() == 0 {
    tracing::warn!(user_id = %user_id, "update_last_login: no row updated — user may have been deactivated");
}
Ok(())
```

### IN-03: `groupByDay` uses string label as a de-duplication key — collides on "TODAY" across different actual dates

**File:** `frontend/app/admin/components/ReportsTable.tsx:97-109`
**Issue:** `groupByDay` uses the string label returned by `getDayLabel` (e.g., `"TODAY"`, `"YESTERDAY"`, `"JUN 1"`) as the key in the `seen` map. If the `reports` array spans more than one page of data loaded at different times (e.g., a live refresh that shifts which day is "TODAY"), two different actual dates could produce the same label. More concretely, a report from 1 June and one from 2 June will never both be labelled "TODAY" simultaneously, but if the label `"JUN 1"` appears for a report from March and another report from June (across multiple years), they would be merged incorrectly. While the current date format `"MMM DD"` (no year) means a collision requires multi-year data in the same page, this is a latent bug worth noting.

**Fix:** Key the `seen` map on the full ISO date string (`YYYY-MM-DD`) rather than the display label, and use the display label only for rendering:
```typescript
function groupByDay(reports: Report[]): { label: string; isoDate: string; items: Report[] }[] {
  const groups: { label: string; isoDate: string; items: Report[] }[] = [];
  const seen: Record<string, number> = {};
  for (const r of reports) {
    const d = new Date(r.created_at);
    const isoDate = `${d.getUTCFullYear()}-${String(d.getUTCMonth()+1).padStart(2,'0')}-${String(d.getUTCDate()).padStart(2,'0')}`;
    if (seen[isoDate] === undefined) {
      seen[isoDate] = groups.length;
      groups.push({ label: getDayLabel(r.created_at), isoDate, items: [] });
    }
    groups[seen[isoDate]].items.push(r);
  }
  return groups;
}
```
