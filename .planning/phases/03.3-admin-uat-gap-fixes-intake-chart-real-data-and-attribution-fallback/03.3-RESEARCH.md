## Summary

Phase 03.3 closes two confirmed-bug UAT findings from Phase 03.2. Both root causes have been precisely identified in the codebase. No ambiguity exists about what to change or where.

**BUG-03.2-B** is a pure one-line SQL fix. `backend/src/db/admin_queries.rs:546` selects `au.display_name AS changed_by_name` with no fallback. All current admin accounts have `display_name = NULL` (seeded with no display name). Changing the line to `COALESCE(au.display_name, au.email) AS changed_by_name` ensures the admin's email appears when no display name is set. No migration, no frontend change, no new struct.

**BUG-03.2-A** is a backend + frontend pair. The backend needs a new `GET /api/admin/stats/intake?days=N` endpoint returning per-day report counts. The frontend needs a `useEffect` that fires when `activePeriod` changes, calls the new endpoint, zero-fills sparse days, and passes the resulting array to `<Sparkbars values={...}>`. The existing period button wiring (`activePeriod` state) is already complete and correct from Phase 03.2 — only the data source changes.

**Primary recommendation:** Wave 1 = BUG-03.2-B (one-liner SQL + SQL string testable unit test). Wave 2 = BUG-03.2-A (new backend handler + new frontend effect + new adminApi function). Ship BUG-03.2-B first because it is isolated and risk-free, keeping Wave 2's diff clean.

/// Returned by GET /api/admin/stats/intake.

**New DB function:**
```rust
/// Per-day report counts for the last `days` calendar days (inclusive today, UTC).
///
/// Returns one row per calendar day that has at least one submission.
/// Days with zero submissions are NOT returned — the caller zero-fills the gap.
pub async fn get_intake_stats(pool: &PgPool, days: i32) -> Result<Vec<IntakeDayCount>, AppError> {
    let rows = sqlx::query(
        r#"
        SELECT
            date_trunc('day', created_at AT TIME ZONE 'UTC')::DATE::TEXT AS day,
            COUNT(*)::BIGINT AS count
        FROM reports
        WHERE created_at >= NOW() - ($1 || ' days')::INTERVAL
        GROUP BY 1
        ORDER BY 1
        "#,
    )
    .bind(days)
    .fetch_all(pool)
    .await?;

    Ok(rows
        .iter()
        .map(|r| IntakeDayCount {
            day: r.get::<String, _>("day"),
            count: r.get::<i64, _>("count"),
        })
        .collect())
}
```

**Important note on INTERVAL binding:** PostgreSQL cannot bind a plain integer directly as an INTERVAL. The pattern `($1 || ' days')::INTERVAL` casts the string concatenation to INTERVAL and is the established approach for parameterised intervals without compile-time macros. ### Pattern 1: Runtime parameterised interval (PostgreSQL)

**What:** Binding an integer days count as a PostgreSQL INTERVAL for date range filtering.
**When to use:** When the query uses `sqlx::query(...)` (runtime, not compile-time macro) and the interval must be parameterised.

```rust
// Source: [ASSUMED — established SQLx pattern for runtime INTERVAL binding]
sqlx::query(
    r#"
    SELECT date_trunc('day', created_at AT TIME ZONE 'UTC')::DATE::TEXT AS day,
           COUNT(*)::BIGINT AS count
    FROM reports
    WHERE created_at >= NOW() - ($1 || ' days')::INTERVAL
    GROUP BY 1
    ORDER BY 1
    "#,
)
.bind(days)  // i32
```

### Pattern 2: Zero-fill sparse day series (TypeScript)

**What:** Convert a sparse `{day: string, count: number}[]` into a dense `number[]` with a slot per calendar day, oldest first.
**When to use:** Whenever backend returns only days with data > 0 and the chart needs a fixed-length array.

```typescript
// Source: [ASSUMED — standard date iteration pattern]
const today = new Date();
const filled: number[] = [];
for (let i = dayCount - 1; i >= 0; i--) {
  const d = new Date(today);
  d.setUTCDate(d.getUTCDate() - i);
  const key = d.toISOString().slice(0, 10); // "YYYY-MM-DD"
  const match = rows.find((r) => r.day === key);
  filled.push(match ? match.count : 0);
}
```

### Anti-Patterns to Avoid

- **Bind i32 directly as INTERVAL:** `WHERE created_at >= NOW() - $1` where `$1` is an integer will fail at runtime. Always cast: `($1 || ' days')::INTERVAL`.
- **Using compile-time `query!` macro for intake query:** The codebase deliberately uses `sqlx::query(...)` (runtime) everywhere in admin_queries.rs to keep `cargo test` free of a live DB. Do not switch to `query!` or `query_as!` macros.
- **Setting `Content-Type: multipart/form-data` manually:** Not applicable here (JSON endpoint), but relevant for any new multipart handler.
- **Mutating `activePeriod` inside the intake useEffect:** The effect already depends on `activePeriod`. Calling `setActivePeriod` inside it creates an infinite loop.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Zero-fill day series | Custom day-of-week calendar logic | Simple UTC date loop with `toISOString().slice(0,10)` | Timezone-safe, no library needed |
| INTERVAL parameterisation | String interpolation in SQL (`format!`) | `($1 || ' days')::INTERVAL` bind pattern | Prevents SQL injection |
| Per-day aggregation | Application-side counting over all report rows | `date_trunc` + `GROUP BY` in SQL | O(1) DB work vs O(N) app work |

## Common Pitfalls

### Pitfall 1: PostgreSQL INTERVAL with integer bind
**What goes wrong:** `WHERE created_at >= NOW() - $1` rejects an integer at runtime because PostgreSQL cannot subtract an integer from a timestamp without an explicit cast.
**Why it happens:** PostgreSQL's `-` operator on timestamps requires an INTERVAL, not a plain integer.
**How to avoid:** Use `($1 || ' days')::INTERVAL` — concatenate the integer as text and cast.
**Warning signs:** `sqlx::Error::Database` with "operator does not exist: timestamp - integer" in logs.

### Pitfall 2: Local timezone vs UTC in date truncation
**What goes wrong:** `date_trunc('day', created_at)` truncates to local server time, which could split a UTC day incorrectly on a server with a non-UTC timezone setting.
**How to avoid:** Use `date_trunc('day', created_at AT TIME ZONE 'UTC')::DATE::TEXT` to force UTC.
**Warning signs:** Off-by-one-day discrepancies in bar heights on reports submitted near midnight UTC.

### Pitfall 3: COALESCE with three-argument JOIN
**What goes wrong:** Writing `COALESCE(display_name, email)` without the table alias picks up the wrong column scope if both tables happen to have a column by that name.
**How to avoid:** Always qualify: `COALESCE(au.display_name, au.email)`.
**Warning signs:** Compilation error or wrong column selected.

### Pitfall 4: Test mock does not include `getIntakeStats`
**What goes wrong:** `dashboard.test.tsx` mocks `adminApi` with an explicit object. After adding `getIntakeStats`, the mock object must include it or the test throws "not a function".
**How to avoid:** Add `getIntakeStats: jest.fn()` to the `jest.mock("../lib/adminApi", ...)` factory in `dashboard.test.tsx`.
**Warning signs:** Jest test fails with `TypeError: getIntakeStats is not a function`.

### Pitfall 5: `intakeData` renders 0 bars while loading (flash)
**What goes wrong:** `intakeData` starts as `[]`. `Sparkbars` receives an empty array and renders nothing until the first fetch completes.
**How to avoid:** Use the inline fallback in the `values` prop: `intakeData.length > 0 ? intakeData : Array(dayCount).fill(0)`. This shows flat-zero bars instead of a blank chart during loading.

## Open Questions

1. **INTERVAL parameterisation syntax**
   - What we know: `($1 || ' days')::INTERVAL` is the standard SQLx runtime approach for integer-to-INTERVAL conversion.
   - What's unclear: Whether the Postgres version in use supports this cast (it should for any Postgres ≥ 9.1).
   - Recommendation: Verify with `cargo check` during Wave 2 implementation. If it fails, fallback is `INTERVAL '1 day' * $1` (multiply days scalar by unit interval).

2. **`intakeData` initial state and Sparkbars empty array behaviour**
   - What we know: `Sparkbars` renders zero bars when `values=[]` because `Math.max(...[], 1)` returns 1 and the map iterates zero elements.
   - What's unclear: Whether the zero-bar visual is acceptable during the first load.
   - Recommendation: Use the fallback `Array(dayCount).fill(0)` in the JSX prop so flat-zero bars appear immediately on mount.
