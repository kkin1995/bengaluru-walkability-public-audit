## Critical Issues

### CR-01: INTAKE_SQL — PostgreSQL type error at runtime (integer `||` text without cast)

**File:** `backend/src/db/admin_queries.rs:881`

**Issue:** `INTAKE_SQL` constructs an interval by concatenating the bound `$1` parameter
(an `i32`) with the string literal `' days'`:

```sql
WHERE created_at >= NOW() - ($1 || ' days')::INTERVAL
```

`sqlx` sends `$1` with type OID `int4` (PostgreSQL integer). The `||` operator in
PostgreSQL is text concatenation and does not accept an integer left operand — it will
raise:

```
ERROR: operator does not exist: integer || unknown
HINT: No operator matches the given name and argument types.
```

This means every call to `GET /api/admin/stats/intake` will return a 500 Internal Server
Error. The unit test at line 1627 only inspects the SQL string for the presence of `$1`
— it does not catch the type mismatch because no real database is involved.

**Fix:** Cast `$1` to text before concatenation, or use `make_interval`:

```rust
// Option A — explicit cast (minimal change)
const INTAKE_SQL: &str = "SELECT \
    date_trunc('day', created_at AT TIME ZONE 'UTC')::DATE::TEXT AS day, \
    COUNT(*)::BIGINT AS count \
    FROM reports \
    WHERE created_at >= NOW() - ($1::TEXT || ' days')::INTERVAL \
    GROUP BY 1 \
    ORDER BY 1";

// Option B — cleaner, no string building
const INTAKE_SQL: &str = "SELECT \
    date_trunc('day', created_at AT TIME ZONE 'UTC')::DATE::TEXT AS day, \
    COUNT(*)::BIGINT AS count \
    FROM reports \
    WHERE created_at >= NOW() - make_interval(days => $1) \
    GROUP BY 1 \
    ORDER BY 1";
```

Option B (`make_interval`) is preferable: it binds `$1` as `int4` directly, avoids the
text concatenation entirely, and is unambiguous. Option A requires the `::TEXT` cast.

### CR-02: Missing `WHERE` keyword in `list_admin_reports` and `count_admin_reports` when `org_id` is `Some` and no filter conditions are active

**File:** `backend/src/db/admin_queries.rs:248-269` (count), `326-346` (list)

**Issue:** `build_report_where_clause` returns an empty string when no filter parameters
are supplied. The org-scoping CTE is appended directly as:

```
" AND reports.ward_id IN (WITH RECURSIVE org_subtree AS (...) ...)"
```

When concatenated with an empty `where_clause`, the resulting SQL is:

```sql
SELECT COUNT(*)
FROM reports
LEFT JOIN wards ON wards.id = reports.ward_id
 AND reports.ward_id IN (...)
```

The `AND` appears without a preceding `WHERE`, which is a SQL syntax error. PostgreSQL
will reject this query with:

```
ERROR: syntax error at or near "AND"
```

This bug fires for any org-scoped admin on the default page load (no filters selected),
which is the most common case. Both `count_admin_reports` and `list_admin_reports` are
affected identically.

The unit tests at lines 1322–1341 build the SQL without an `org_id`, so they do not
exercise this code path.

**Fix:** When the `where_clause` is empty but `org_clause` is non-empty, prefix the
`org_clause` with `WHERE` instead of `AND`:

```rust
// In both count_admin_reports and list_admin_reports:
let full_where = match (where_clause.is_empty(), org_clause.is_empty()) {
    (true, true) => String::new(),
    (true, false) => {
        // org_clause begins with " AND ..." — replace with " WHERE "
        format!("WHERE{}", &org_clause[" AND".len()..])
    }
    (false, _) => format!("{}{}", where_clause, org_clause),
};
```

Alternatively, build the org clause unconditionally starting with ` AND` and let the
function prefix it correctly:

```rust
let full_where = if where_clause.is_empty() && !org_clause.is_empty() {
    // Trim the leading " AND" and replace with WHERE
    format!("WHERE {}", org_clause.trim_start_matches(" AND ").trim_start())
} else {
    format!("{}{}", where_clause, org_clause)
};
```

### WR-01: `org_id` absent from `AdminUserResponse` causes silent frontend type mismatch

**File:** `backend/src/models/admin.rs:110-123` and `frontend/app/admin/lib/adminApi.ts:15-25`

**Issue:** The frontend `AdminUser` TypeScript interface declares `org_id: string | null`
(line 24 of `adminApi.ts`). The backend `AdminUserResponse` struct does not include an
`org_id` field (confirmed: the struct ends at `is_super_admin`). Consequently, all
responses from `GET /api/admin/auth/me`, `GET /api/admin/users`, and `POST
/api/admin/users` will contain JSON without an `org_id` key.

TypeScript will not catch this at compile time because `string | null` is satisfied by
`undefined` only at runtime (TypeScript structural typing treats the absent field as
`undefined`, not `null`). Live code that gates on `user.org_id` (e.g.
`frontend/app/admin/users/page.tsx:221` calling `resolveOrgName(user.org_id, orgs)` and
line 235 showing "UNASSIGNED" if falsy) will silently treat all org-scoped admins as
unassigned.

**Fix:** Add `org_id` to `AdminUserResponse` and `into_response()`:

```rust
// models/admin.rs — add to AdminUserResponse
pub org_id: Option<Uuid>,

// AdminUser::into_response() — add the field mapping
pub fn into_response(self) -> AdminUserResponse {
    AdminUserResponse {
        // ... existing fields ...
        org_id: self.org_id,
    }
}
```

### WR-02: `statusActionLabel` references renamed status value `"under_review"`

**File:** `frontend/app/admin/page.tsx:25`

**Issue:** The function `statusActionLabel` checks `status === "under_review"` (line 25).
The Phase 03 status enum renamed `"under_review"` to `"acknowledged"` in migration 008
(documented in `D-04`, enforced by the backend `validate_status` function which explicitly
rejects `"under_review"`). No report in the database will ever carry the status
`"under_review"` after the migration runs. The branch is permanently dead code, and the
correct label mapping for `"acknowledged"` is never produced by this function.

**Fix:** Replace the renamed value and handle the full 6-value enum:

```typescript
function statusActionLabel(status: string): string {
  if (status === "resolved" || status === "closed") return "Resolved";
  if (status === "acknowledged" || status === "assigned" || status === "in_progress")
    return "Under review";
  return "New"; // "open"
}
```

### WR-03: `critical` severity excluded from dashboard severity distribution

**File:** `frontend/app/admin/page.tsx:124-130`

**Issue:** The severity composition section computes percentages using only `high`,
`medium`, and `low` counts:

```typescript
const totalSeverity = highCount + mediumCount + lowCount || 1;
```

The backend `StatsResponse` includes `by_severity` with four keys: `low`, `medium`,
`high`, and `critical` (seeded in `get_report_stats` at `admin_queries.rs:819-823`). The
`critical` key is silently ignored. For any deployment with critical-severity reports:

1. The percentage bars do not account for critical reports in the denominator, making
   percentages incorrectly inflated.
2. Critical reports have no visual representation in the distribution section, misleading
   operators about the severity breakdown.

**Fix:** Include `critical` in the calculation and add a row:

```typescript
const criticalCount = stats?.by_severity?.critical ?? 0;
const totalSeverity = criticalCount + highCount + mediumCount + lowCount || 1;
const criticalPct = Math.round((criticalCount / totalSeverity) * 100);
// Adjust lowPct: 100 - criticalPct - highPct - mediumPct
```

### WR-04: Stale doc comments in `admin.rs` describe `AppError::Forbidden(String)` (tuple variant) but the actual type is a unit variant

**File:** `backend/src/handlers/admin.rs:26-34` and `1093-1095`

**Issue:** The file-level comment block (lines 26-34) instructs the implementation agent
to add `AppError::Forbidden(String)` with a payload to `errors.rs`. The actual
implementation (confirmed in `errors.rs`) defines `AppError::Forbidden` as a **unit
variant** with no payload. The comment is never accurate.

Additionally, the `is_forbidden` helper doc at line 1095 instructs:
```
matches!(err, AppError::Forbidden(_))
```
The `(_)` pattern matches a tuple variant. For the actual unit variant, the correct
pattern — which the code at line 1099 correctly uses — is `matches!(err,
AppError::Forbidden)` without the `_`. Anyone reading the doc comment will be confused,
and a future refactor following the doc instructions would introduce a compile error.

**Fix:** Update the stale comments to match reality:

```rust
// File header: remove or correct the Forbidden(String) instruction block.
// is_forbidden helper doc: replace "matches!(err, AppError::Forbidden(_))"
//   with "matches!(err, AppError::Forbidden)"
```

### IN-01: Mobile layout "+N today" label displays total open count, not today's submissions

**File:** `frontend/app/admin/page.tsx:357`

**Issue:** The mobile hero card displays:

```tsx
{statsForCards ? `+${statsForCards.submitted} today` : "—"}
```

`statsForCards.submitted` is mapped from `stats.by_status.open` — the cumulative count
of all reports with status `"open"`, not the count of reports submitted today. The label
"+N today" is factually incorrect for any deployment with more than zero open reports

**Fix:** Either remove the "today" label and show the open count without that qualifier,
or source a real "today's submissions" count from the intake endpoint. The `intakeData`
array already contains yesterday-to-today counts and the last element (`intakeData.at(-1)
?? 0`) would give today's actual submission count.

### IN-02: `lowPct` can be negative due to `Math.round` accumulation

**File:** `frontend/app/admin/page.tsx:130`

**Issue:** `lowPct` is computed as `100 - highPct - mediumPct`. Because `highPct` and
`mediumPct` are independently rounded, their sum can exceed 100 in edge cases (e.g.
`highCount = 1, mediumCount = 1, lowCount = 1` → each rounds to 33%, sum = 99; but with
`highCount = 2, mediumCount = 2, lowCount = 1` → each rounds to 40%, 40%, sum = 80, low
= 20; borderline cases can differ). The most reliable failure mode: if `critical` severity
is included and rounding of three large values produces `highPct + mediumPct > 100`,
`lowPct` will be negative, making the progress bar `width: "-N%"` which CSS renders as
`0%` rather than crashing.

This does not crash but produces visually wrong bars. After fixing WR-03 (adding
`critical`), recompute `lowPct` as `Math.max(0, 100 - criticalPct - highPct - mediumPct)`
to defensively guard against negative values.
