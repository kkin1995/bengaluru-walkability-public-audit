## BUG-03.2-A: INTAKE chart sparkbars show stub data unrelated to actual reports

**Page:** `/admin` (dashboard)
**Observed:** Clicking 7D/14D/30D correctly changes the active button and bar count. But the
bar heights (3–9) are meaningless — the system has only 1 real report yet the chart shows
bars at heights of 3, 5, 8, 9. The 30D view visibly repeats the same 14-bar pattern twice.
**Expected:** The sparkbars reflect actual per-day report intake counts for the selected
period window. Empty days show height 0; a day with 1 submission shows a bar proportional
to 1. A system with 1 total report should show at most 1 bar with height > 0.
**Root cause:** `sparkbarsValues` is derived from `STUB_SPARKBARS` — a hardcoded
`[3,5,2,8,6,4,9,7,5,3,6,8,4,5]` constant sliced/padded for the selected period. No real
data is fetched. The period wiring (useState → Sparkbars) is complete and reusable; only
the data source needs replacing.
**Fix direction:**
- Backend: `GET /api/admin/stats/intake?days=N` — aggregate query returning per-day counts
  (`SELECT date_trunc('day', created_at) AS day, COUNT(*) AS count FROM reports WHERE
  created_at >= NOW() - INTERVAL '$1 days' GROUP BY 1 ORDER BY 1`).
- Frontend: replace the `sparkbarsValues` IIFE in `frontend/app/admin/page.tsx:103-115`
  with a `useEffect` that fetches the new endpoint when `activePeriod` changes, merging
  sparse days with 0-fill, and passing the result to `<Sparkbars values={...}>`.
**Category:** confirmed-bug
**Scope:** backend `backend/src/handlers/admin.rs` + `backend/src/db/admin_queries.rs`;
frontend `frontend/app/admin/page.tsx`
**Ref:** 03.2 test 1

## BUG-03.2-B: Status history attribution always shows "—" (BY field always empty)

**Page:** `/admin/reports/[id]`
**Observed:** Status history renders correctly — correct entry count, correct statuses,
correct dates, no "Invalid Date", no "SYSTEM". But every entry shows `BY · —` regardless
of which admin made the change.
**Expected:** `BY · <admin name or email>` — the attribution should identify the real
admin who performed each status change.
**Root cause:** `backend/src/db/admin_queries.rs:546` selects `au.display_name AS
changed_by_name` with no fallback. All current admin accounts (including the seeded admin)
have `display_name = NULL`. The `changed_by` UUID is correctly stored in `status_history`
rows (verified: handlers at `admin.rs:502, 704, 750` extract it from JWT), so the LEFT JOIN
finds the right `admin_users` row — but `display_name` is NULL, so the whole field returns
NULL and the frontend shows `—`.
**Fix direction:**
- Backend one-liner: change line 546 from
  `au.display_name AS changed_by_name`
  to
  `COALESCE(au.display_name, au.email) AS changed_by_name`
  so the admin's email is shown when no display name has been set.
- No frontend change needed — `changed_by_name` becomes non-null, `|| "—"` fallback stops
  firing.
**Category:** confirmed-bug
**Scope:** backend `backend/src/db/admin_queries.rs:546` only
**Ref:** 03.2 test 2
