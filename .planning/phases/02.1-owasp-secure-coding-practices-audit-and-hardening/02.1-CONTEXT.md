# Phase 02.1: OWASP Secure Coding Practices Audit and Hardening - Context

**Gathered:** 2026-04-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Systematic identification and remediation of OWASP Top 10 security violations across the Rust/Axum + Next.js stack before GBA soft launch. Scope is bounded to the two surfaces genuinely exposed at launch: the **public anonymous submission path** and the **admin JWT authentication path**. This produces a documented threat model tied to OWASP A01, A03, A07, and A10.

New capabilities (public map features, export, analytics, government workflow) are NOT part of this phase.

</domain>

<decisions>
## Implementation Decisions

### Audit Scope
- **D-01:** Scope = critical attack-surface only: public `POST /api/reports` submission path + admin JWT auth path. NOT a full OWASP Top 10 checklist scan.
- **D-02:** Relevant OWASP categories: A01 (Broken Access Control), A03 (Injection), A05 (Security Misconfiguration), A06 (Vulnerable Components), A07 (Identification and Authentication Failures), A10 (SSRF/request forgery adjacent).
- **D-03:** Known documented findings from CONCERNS.md are the starting inventory — they are pre-triaged and require no new discovery overhead. All 5 documented security findings must be addressed or formally accepted with rationale.
- **D-04:** Phase produces a documented threat model (THREAT-MODEL.md or equivalent section in CONTEXT) that Phase 3 and Phase 4 can reference.

### PII Exposure — submitter_name
- **D-05:** `submitter_name` must be **stripped from the public unauthenticated API responses** (`GET /api/reports` and `GET /api/reports/:id`). It remains accessible via the admin-only endpoints.
- **D-06:** Implementation: remove `submitter_name` from `ReportResponse` struct in `backend/src/models/report.rs` — identical pattern to the existing `submitter_contact` exclusion. Add a unit test mirroring `test_response_omits_submitter_contact`.
- **D-07:** Post-launch backlog item: opt-in `name_public` consent flag (DB column + form checkbox) for voluntary attribution. Defer to post-launch; not in scope for this phase.

### COOKIE_SECURE and TLS
- **D-08:** `COOKIE_SECURE` must default to `true` in `docker-compose.yml`. Local dev requires explicit `COOKIE_SECURE=false` opt-out. Current default-false is a known documented risk (CONCERNS.md).
- **D-09:** `nginx/nginx.conf` must include a commented HTTPS block with Let's Encrypt setup instructions OR explicit documentation that TLS termination is expected at an upstream load balancer/CDN. The current lack of any TLS documentation is a security gap.

### Login Error Information Leakage
- **D-10:** Strip the `body.message` fallback from the catch-all error branch in `frontend/app/admin/login/page.tsx`. Only per-status generic messages (401, 429, 5xx) should be surfaced to unauthenticated users. This closes FINDING-010.

### Password Validation Gap
- **D-11:** Align the client-side password threshold in `frontend/app/admin/profile/page.tsx` from `< 8` to `< 12` to match the server-side contract in `backend/src/handlers/admin.rs:166`. This is a UX inconsistency, not a security bypass (server always enforces the 12-char minimum), but it creates a confusing rejection path if bypassed.

### require_role Dual Implementation
- **D-12:** The `require_role` in `backend/src/handlers/admin.rs` (strict equality) must be removed or clearly documented as intentionally different from the correct implementation in `backend/src/middleware/auth.rs` (admin-is-superset). Downstream: all handlers must import from `crate::middleware::auth`. This closes the dual-implementation confusion documented in CONCERNS.md Fragile Areas.

### serde_json unwrap() in Production Handlers
- **D-13:** Replace `.unwrap()` on `serde_json::to_value(...)` calls in `backend/src/handlers/admin.rs` (lines ~390, ~553) with `map_err(|e| AppError::Internal(e.to_string()))?` to eliminate silent panic paths in production handlers.

### CSP unsafe-inline Hardening
- **D-14:** Remove `unsafe-inline` from `style-src` in `nginx/nginx.conf`. Tailwind CSS v3 generates a static stylesheet (no inline styles at runtime) — this is achievable without app changes.
- **D-15:** `script-src 'unsafe-inline'` is **accepted as a known risk** for this phase. Rationale: no `dangerouslySetInnerHTML`, no user-generated HTML rendered raw, EXIF stripping is a compensating control. Full remediation requires per-request nonces from Next.js middleware with nginx header propagation — non-trivial to validate on a pre-launch timeline.
- **D-16:** File a tracked issue for the nonce implementation roadmap (post-launch). Document the accepted risk inline in `nginx.conf` with a reference to the issue.
- **D-17:** The `https://unpkg.com` CDN source in `img-src` and `style-src` (Leaflet icons) is a known risk. Post-launch: copy Leaflet icon assets to `frontend/public/leaflet/` and remove the CDN dependency. Document inline.

### Dependency Vulnerability Scanning
- **D-18:** Run `cargo audit` and `npm audit --audit-level=high` as part of this phase. Fix any high/critical CVEs that have an available upgrade path.
- **D-19:** Wire both audits into the existing GitHub Actions CI pipeline (`ci.yml`) — two new job steps in the existing `backend-checks` and `frontend-checks` jobs respectively. PRs must not introduce new high/critical CVEs.
- **D-20:** Add an `audit.toml` (backend) and `.nsprc` or `npm audit` allowlist (frontend) for any CVEs with no available fix path, so CI is not permanently blocked by unresolvable advisories.

### Claude's Discretion
- Exact order of plan breakdown (single plan vs. multiple — planner decides based on scope of changes)
- Whether COOKIE_SECURE fix and TLS documentation are in the same plan as the PII fix or separate
- Whether the threat model output is a standalone file or a section within another artifact
- Exact nginx CSP string for style-src after removing unsafe-inline (planner handles the Tailwind verification)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `backend/src/models/report.rs` `ReportResponse` struct + `test_response_omits_submitter_contact` unit test: exact pattern to replicate for `submitter_name` removal + new unit test
- `backend/src/middleware/auth.rs` `require_role`: the correct implementation that all handlers should import from
- `.github/workflows/ci.yml` existing `backend-checks` and `frontend-checks` jobs: extension points for `cargo audit` and `npm audit` steps

### Established Patterns
- DB struct vs Response struct separation: DB model carries all data; `*Response` struct is the safe serializable shape. The `submitter_contact` exclusion is the precedent to follow.
- `AppError` enum: all error paths return `AppError` — `map_err(|e| AppError::Internal(...))` is the correct replacement for `.unwrap()` in handler paths
- Nginx location blocks: admin and public CSP are configured in separate `location` blocks — the CSP change only affects the public block's `style-src`

### Integration Points
- `backend/src/models/report.rs` → remove `submitter_name` from `ReportResponse`; verify admin queries still select it
- `docker-compose.yml` → change `COOKIE_SECURE` default from `false` to `true`; update `docker-compose.dev.yml` or `.env.example` to set `COOKIE_SECURE=false` for local dev
- `nginx/nginx.conf` → remove `unsafe-inline` from `style-src`; add TLS documentation comment; add `script-src` accepted-risk comment with issue reference
- `frontend/app/admin/login/page.tsx` → remove `body.message` from catch-all error branch
- `frontend/app/admin/profile/page.tsx` → change password threshold from `< 8` to `< 12`
- `backend/src/handlers/admin.rs` → replace `.unwrap()` on `serde_json::to_value`; remove or consolidate duplicate `require_role`
- `.github/workflows/ci.yml` → add `cargo audit` step + `npm audit --audit-level=high` step

</code_context>

<specifics>
## Specific Ideas

- The `submitter_contact` exclusion pattern (struct field absent + dedicated unit test) is the exact template for the `submitter_name` fix — do not deviate from this precedent
- `COOKIE_SECURE` fix: default to `true` in docker-compose, not `false`. Dev override goes in `docker-compose.dev.yml` or `.env.example` comments, not production config.
- CSP nonce roadmap: document as a tracked issue, not as vague "future work" — include the specific constraint (nginx must forward the nonce header from Next.js middleware response)
- Dependency audit ignore files: create `audit.toml` for Rust and document npm audit allowlist approach; do not skip CI on blanket ignore

</specifics>

<deferred>
## Deferred Ideas

- **submitter_name opt-in consent** — opt-in `name_public` bool (DB column + form checkbox + conditional public exposure). Correct long-term design for DPDP Act 2023 compliance. Post-launch P1.
- **CSP nonce implementation** — per-request nonces via Next.js middleware + nginx header propagation. Post-launch; requires end-to-end CI validation of the nginx propagation path.
- **Leaflet icon CDN removal** — copy icon assets to `frontend/public/leaflet/` and remove `unpkg.com` from `img-src`/`style-src`. Post-launch cleanup (currently an accepted risk).
- **Live DB integration tests** — backend tests currently run without a DB; real SQL correctness is untested in CI. Noted in CONCERNS.md Test Coverage Gaps. A dedicated phase or post-launch maintenance item.

</deferred>
