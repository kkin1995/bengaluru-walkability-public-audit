    ```sql
    -- 008_workflow_rename.sql
    -- Rename legacy enum values to Phase 3 naming convention.
    -- RENAME VALUE runs safely inside a transaction (sqlx default).
    ALTER TYPE report_status RENAME VALUE 'submitted' TO 'open';
    ALTER TYPE report_status RENAME VALUE 'under_review' TO 'acknowledged';
    ```

    Create backend/migrations/009_workflow_add_values.sql — ADD VALUE cannot run inside a transaction block. sqlx 0.7 handles this by detecting ADD VALUE statements and running the migration outside a transaction automatically. Add IF NOT EXISTS guards for idempotency. Then add the three new columns:
    ```sql
    -- 009_workflow_add_values.sql
    -- Add new report_status enum values.
    -- ADD VALUE cannot run inside a transaction; sqlx 0.7 handles this automatically.
    ALTER TYPE report_status ADD VALUE IF NOT EXISTS 'assigned'    AFTER 'acknowledged';
    ALTER TYPE report_status ADD VALUE IF NOT EXISTS 'in_progress' AFTER 'assigned';
    ALTER TYPE report_status ADD VALUE IF NOT EXISTS 'closed'      AFTER 'resolved';

    -- Final enum order: open → acknowledged → assigned → in_progress → resolved → closed

    ALTER TABLE reports
      ADD COLUMN IF NOT EXISTS resolution_photo_path  TEXT,
      ADD COLUMN IF NOT EXISTS resolution_notes       TEXT,
      ADD COLUMN IF NOT EXISTS assigned_org_id        UUID REFERENCES organizations(id) ON DELETE SET NULL;

    CREATE INDEX IF NOT EXISTS idx_reports_assigned_org_id ON reports(assigned_org_id);
    ```

    NOTE: If sqlx 0.7 does not auto-detect ADD VALUE and the migration fails with "cannot run inside a transaction block", restructure 009 by placing ONLY the ADD VALUE statements first (before any ALTER TABLE), and verify against actual error output. The ALTER TABLE ADD COLUMN statements CAN run inside transactions — only ADD VALUE cannot. If needed, split into 009 (ADD VALUE only) and 010 (ALTER TABLE + CREATE INDEX), but try the combined file first.
