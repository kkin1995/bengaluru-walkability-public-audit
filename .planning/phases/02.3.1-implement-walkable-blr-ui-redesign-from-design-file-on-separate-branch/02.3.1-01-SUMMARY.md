## Decisions Made

- **data-* attributes on primitives:** jsdom strips `color: var(--muted)`, `background: var(--accent)` etc. from computed style and raw style attributes — they simply do not appear in `element.style` or `getAttribute("style")`. Added `data-tone`, `data-variant`, `data-size`, `data-component` attributes so unit tests can assert on which variant is applied without fighting jsdom's CSS variable handling.
- **body bg-gray-50/text-gray-900 removed:** These Tailwind classes on `<body>` in layout.tsx would override `background: var(--bg)` and `color: var(--ink)` from globals.css. Removed and replaced with `min-h-screen antialiased` (which do not conflict with design system).
- **next/font/google mock structure:** Mock returns `{ variable: '__FontName_variable', className: '__FontName_className', style: { fontFamily: '...' } }` — matches the shape Next.js generates at build time so layout.tsx imports without error in tests.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Added next/font/google Jest mock**
- **Found during:** Task 2 (layout.tsx TDD — existing layout.test.ts failed to import layout.tsx after adding next/font/google)
- **Issue:** `next/font/google` performs build-time font fetching; calling `Inter({ ... })` at module level in layout.tsx causes Jest to throw `Cannot call next/font/google at runtime` when layout.tsx is imported in tests
- **Fix:** Created `frontend/__mocks__/next/font/google.js` returning the correct `{ variable, className, style }` shape, and added `"^next/font/google$"` to `jest.config.js` moduleNameMapper
- **Files modified:** `frontend/__mocks__/next/font/google.js` (new), `frontend/jest.config.js`
- **Verification:** All 24 existing layout tests pass after mock was added
- **Committed in:** `3ab190a` (Task 2 feat commit)

**2. [Rule 1 - Bug] Switched test assertions from element.style to data attributes / getAttribute("style")**
- **Found during:** Task 3 GREEN phase (Btn, Pill, SectionLabel tests failing)
- **Issue:** jsdom's CSS implementation silently discards inline style properties whose value is `var(--token)` for certain CSS property types (background, color, border). `btn.style.background` returns `""` even when `style={{ background: "var(--accent)" }}` was set on the element. `var(--font-mono)` in font-family IS preserved, as are numeric properties like `minHeight: 44`.
- **Fix:** Added `data-variant`, `data-size` to Btn; `data-tone` to Pill; `data-component` to SectionLabel. Updated test assertions to use `getAttribute("data-*")` for variant/tone checks, `getAttribute("style")` for raw string checks, and `element.style.*` only for concrete numeric values (minHeight, opacity, letterSpacing, fontSize, textTransform).
- **Files modified:** `Btn.tsx`, `Pill.tsx`, `SectionLabel.tsx`, `Btn.test.tsx`, `Pill.test.tsx`, `SectionLabel.test.tsx`
- **Verification:** 82/82 tests pass; full 690-test suite green
- **Committed in:** `60b2fef` (Task 3 feat commit)

## Issues Encountered

- jsdom CSS variable handling is more restrictive than expected: `color: var(--muted)` is stripped from both `element.style` and `getAttribute("style")`. `font-family: var(--font-mono)` is preserved. `background: var(--accent)` is stripped. Numeric CSS properties (minHeight, opacity, letterSpacing) always work. The data-attribute pattern resolves this cleanly and adds semantic test value (tests now document which variant/tone a component renders, not just that some background color was set).
