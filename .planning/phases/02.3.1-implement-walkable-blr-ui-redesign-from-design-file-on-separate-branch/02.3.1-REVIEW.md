## Warnings

### WR-01: Unhandled promise rejection and stuck loading state in `handleFile`

**File:** `frontend/app/report/page.tsx:173-175`

**Issue:** `handleInputChange` calls `handleFile(file)` without `await` and without catching rejection. `handleFile` is `async` and calls `compressImage`, which can reject when `img.onerror` fires (corrupt file, unsupported format, browser memory limit). If that rejection propagates, two things happen: (1) the user is left staring at "Processing…" indefinitely because `setPhotoProcessing(false)` is never called, and (2) the blob URL created for the preview (`photoPreviewUrl`) may not be cleaned up depending on where in the function the rejection occurs.

```typescript
// current — fire-and-forget on an async function that can throw
function handleInputChange(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (file) handleFile(file);   // ← rejection is silently swallowed by the event loop
}
```

**Fix:** Catch the rejection explicitly so the error state is always surfaced and `photoProcessing` is always cleared:

```typescript
function handleInputChange(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (!file) return;
  handleFile(file).catch(() => {
    setPhotoProcessing(false);
    setError("Could not read photo. Please try a different image.");
  });
}
```

### WR-02: Blob URL leak in `compressImage` when image fails to load

**File:** `frontend/app/report/page.tsx:78-96`

**Issue:** `compressImage` creates a blob URL on line 78 (`URL.createObjectURL(file)`) and revokes it on line 85 — but only after the `await new Promise` resolves successfully. When `img.onerror` fires the promise rejects, the function throws, execution never reaches line 85, and the blob URL is leaked for the lifetime of the page. This is a memory issue on devices that submit many corrupt or unreadable images.

```typescript
// current
const url = URL.createObjectURL(file);
const img = document.createElement("img");
await new Promise<void>((resolve, reject) => {
  img.onload = () => resolve();
  img.onerror = reject;   // ← if this fires, url is never revoked
  img.src = url;
});
URL.revokeObjectURL(url);  // ← unreachable on rejection
```

**Fix:** Use a `finally` block to guarantee revocation:

```typescript
const url = URL.createObjectURL(file);
const img = document.createElement("img");
try {
  await new Promise<void>((resolve, reject) => {
    img.onload = () => resolve();
    img.onerror = reject;
    img.src = url;
  });
} finally {
  URL.revokeObjectURL(url);
}
```

### WR-03: `activeFilter` state in map page is never forwarded to `ReportsMap` — filter UI is non-functional

**File:** `frontend/app/map/page.tsx:45, 58`

**Issue:** The map page maintains `activeFilter` state and renders a tab strip of category filter chips that update it on click. However, `ReportsMap` is rendered with only `apiUrl={API_BASE_URL}` — the `activeFilter` value is never passed down. Clicking any filter chip updates the chip's active visual style but does not actually filter the map markers. Users clicking "Damaged" or "Lighting" will see no change in the map content, which is a confusing broken interaction.

```tsx
// current — activeFilter never reaches the map
<ReportsMap apiUrl={API_BASE_URL} />
```

**Fix:** If the filter feature is intentionally deferred (like the language toggle), the chip strip must be hidden or a "Coming soon" state added. If it is meant to be functional, pass the filter down:

```tsx
// Option A: pass filter (requires ReportsMap to accept and use a categoryFilter prop)
<ReportsMap apiUrl={API_BASE_URL} categoryFilter={activeFilter === "all" ? undefined : activeFilter} />

// Option B: remove the chip strip until the feature is built
// (remove the FILTERS constant and the chip strip div entirely)
```

### WR-04: `maximumScale: 1` in viewport config disables pinch-to-zoom — accessibility violation

**File:** `frontend/app/layout.tsx:39`

**Issue:** Setting `maximumScale: 1` (which emits `maximum-scale=1` in the viewport meta tag) prevents users from pinch-zooming on iOS and Android. This is a WCAG 2.1 Success Criterion 1.4.4 (Resize Text) failure and is explicitly prohibited by Apple's accessibility guidelines. Older users and users with low vision who zoom the browser to read text will have that ability removed.

```typescript
// current
export const viewport: Viewport = {
  themeColor: "#2563eb",
  width: "device-width",
  initialScale: 1,
  maximumScale: 1,   // ← disables pinch zoom
};
```

**Fix:** Remove `maximumScale` entirely. The Next.js `Viewport` type accepts it but does not require it. Removing it restores browser-default zoom behaviour without affecting the visual layout at 1:1 scale:

```typescript
export const viewport: Viewport = {
  themeColor: "#2563eb",
  width: "device-width",
  initialScale: 1,
  // maximumScale removed — allows browser zoom per WCAG 1.4.4
};
```

### IN-01: Canvas 2D context null assertion is unsafe on low-memory devices

**File:** `frontend/app/report/page.tsx:89`

**Issue:** `canvas.getContext("2d")!` uses a non-null assertion. On some browsers (particularly older Android WebViews under memory pressure), `getContext("2d")` can return `null`. If it does, the `!` causes a runtime crash rather than a handled error.

**Fix:**
```typescript
const ctx = canvas.getContext("2d");
if (!ctx) return null;  // fall through to "too large to compress" error path
ctx.drawImage(img, 0, 0);
```

### IN-03: Font mock's `variable` field ignores `options.variable` — misleading comment

**File:** `frontend/__mocks__/next/font/google.js:17-19`

**Issue:** The JSDoc comment on line 10 says `variable: the CSS variable name (matches what was passed in options.variable)`. The implementation reads `options.variable` into a local `variable` binding on line 17 but then ignores it on line 19, always returning `__${name}_variable` instead. The comment is incorrect. This does not affect test correctness (tests using the mock still get a stable class name) but will mislead future developers maintaining the mock.

**Fix:** Either use the value or remove the dead read:

```javascript
// Option A: actually use options.variable
return {
  variable: (options && options.variable) ? options.variable : `--font-${name.toLowerCase()}`,
  // ...
};

// Option B: remove the dead read and fix the comment
function makeFont(name) {
  return function fontFactory(_options) {
    return {
      variable: `__${name}_variable`,  // stable test stub; does not reflect real CSS var name
      // ...
    };
  };
}
```

### IN-04: Language toggle `div` has `aria-label` but is not interactive — misleading to assistive technology

**File:** `frontend/app/page.tsx:91-104`

**Issue:** The language toggle is rendered as a `<div aria-label="Language toggle (display only)">`. A bare `div` with an `aria-label` but no `role` is not exposed as a widget to screen readers in most browser/AT combinations, so the label goes unannounced. More importantly, sighted keyboard users have no way to know it is intentionally non-interactive. If it is truly display-only (deferred), the element should not carry a label that implies it is a control.

**Fix:** Remove `aria-label` from the decorative div and add an `aria-hidden="true"` attribute instead, matching the pattern used for map dots on the same page:

```tsx
<div
  aria-hidden="true"
  style={{ /* ... */ }}
>
  <Icon name="globe" size={14} /> EN · ಕ
</div>
```
