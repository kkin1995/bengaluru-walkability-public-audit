## Warnings

### WR-01: Blob URL created in `ReportCTA` is leaked when the user abandons `/report` before mounting

**File:** `frontend/app/components/ReportCTA.tsx:49`

**Issue:** `ReportCTA.handleChange` calls `URL.createObjectURL(file)` and places the
resulting blob URL into the store:

```typescript
const previewUrl = URL.createObjectURL(file);
// ...
storePendingPhoto({ file: finalFile, previewUrl, lat, lng, locationSource, gpsConfirmed });
router.push("/report");
```

If the user taps the back button or navigates away between the `router.push` call and
the `useEffect` in `report/page.tsx` running `consumePendingPhoto`, the pending store
entry is never consumed. The next mount of `ReportCTA` overwrites `_pending` without
revoking the previous blob URL (the store has no cleanup path). In a session where the
user taps the CTA, abandons, then taps again multiple times, blob URLs accumulate for
the lifetime of the browser tab.

More concretely: `storePendingPhoto` (photo-store.ts line 16) simply assigns
`_pending = p`. If a previous pending exists, its `previewUrl` blob is silently
discarded without `URL.revokeObjectURL`.

**Fix:** Revoke the previous pending URL before overwriting in `storePendingPhoto`:

```typescript
// photo-store.ts
export function storePendingPhoto(p: PendingPhoto): void {
  if (_pending) {
    URL.revokeObjectURL(_pending.previewUrl); // release previous blob before overwrite
  }
  _pending = p;
}
```

### WR-02: `compressImage` is duplicated verbatim in `ReportCTA.tsx` and `report/page.tsx`

**File:** `frontend/app/components/ReportCTA.tsx:12-36` and `frontend/app/report/page.tsx:78-102`

**Issue:** The `compressImage` function and `MAX_BYTES = 10 * 1024 * 1024` constant are
copy-pasted exactly between the two files. A future change to compression logic (quality
ladder, size limit, output format) must be made in two places. The copies already diverge
in their error-handling: `ReportCTA` falls back to `router.push("/report")` silently on
failure, while `report/page.tsx` shows an error message. This creates a subtly different
experience depending on which path the user took.

**Fix:** Extract to `frontend/app/lib/compress-image.ts` and import from both sites:

```typescript
// frontend/app/lib/compress-image.ts
export const MAX_PHOTO_BYTES = 10 * 1024 * 1024;

export async function compressImage(file: File): Promise<Blob | null> {
  if (file.size <= MAX_PHOTO_BYTES) return file;
  const url = URL.createObjectURL(file);
  const img = document.createElement("img");
  try {
    await new Promise<void>((resolve, reject) => {
      img.onload = () => resolve();
      img.onerror = reject;
      img.src = url;
    });
  } finally {
    URL.revokeObjectURL(url);
  }
  const canvas = document.createElement("canvas");
  canvas.width = img.naturalWidth;
  canvas.height = img.naturalHeight;
  const ctx = canvas.getContext("2d");
  if (!ctx) return null;
  ctx.drawImage(img, 0, 0);
  for (const quality of [0.85, 0.75, 0.65, 0.55, 0.45, 0.4]) {
    const blob = await new Promise<Blob | null>((resolve) =>
      canvas.toBlob(resolve, "image/jpeg", quality)
    );
    if (blob && blob.size <= MAX_PHOTO_BYTES) return blob;
  }
  return null;
}
```

### WR-03: `require("exifr")` inside async handlers silently fails if the module shape changes

**File:** `frontend/app/components/ReportCTA.tsx:57-67` and `frontend/app/report/page.tsx:155-165`

**Issue:** Both files use `const exifrModule = require("exifr")` inside an async
function, with the fallback `exifrModule.default ?? exifrModule`. This pattern was
preserved from `PhotoCapture.tsx` for Jest compatibility. In production it works, but
there are two latent risks:

1. If `exifr` moves to ESM-only, the dynamic `require` will throw. The outer `catch {}`
   swallows it, and GPS extraction silently fails — `locationSource` stays `"manual_pin"`
   and `gpsConfirmed` stays `false`. The user sees "Locating…" on the category step
   thumbnail with no explanation. The manual-adjust nudge only appears at the confirm
   step, one step later.

2. The empty `catch {}` gives zero observability — no log, no error state, no fallback
   copy. On devices where `exifr` initialization fails (older WebKit), this is a silent
   degradation.

**Fix:** At minimum, log on GPS failure so it is visible in production monitoring. For
the `ReportCTA` path specifically, consider setting a flag that signals to `/report`
that GPS was unavailable so the confirm step can immediately prompt the user to adjust:

```typescript
try {
  // ... exifr extraction
} catch (err) {
  console.warn("[ReportCTA] EXIF extraction failed:", err);
  // GPS stays null — manual pin fallback remains active
}
```

### WR-04: Contact accordion spacebar keydown does not prevent default scroll

**File:** `frontend/app/report/page.tsx:840`

**Issue:** The contact accordion trigger handles keyboard interaction with:

```tsx
onKeyDown={(e) => { if (e.key === "Enter" || e.key === " ") setShowContact((v) => !v); }}
```

When the user presses Space, the page also scrolls (the default browser behaviour for
Space on a non-button element). The accordion toggles correctly, but the viewport jumps
simultaneously. This creates a jarring UX on mobile browsers.

Additionally, using `role="button"` on a `div` is the correct ARIA pattern when a
`button` element is not used, but a native `<button type="button">` handles Space and
Enter natively (no `onKeyDown` needed), suppresses scroll automatically, and receives
the `:focus-visible` ring without extra CSS. The test at `report-page.test.tsx:372`
already queries `getByRole("button", { name: /Add contact for follow-up/i })`, so
replacing the `div` with a `<button>` will keep tests green.

**Fix — minimal (suppress scroll):**
```tsx
onKeyDown={(e) => {
  if (e.key === "Enter" || e.key === " ") {
    e.preventDefault();
    setShowContact((v) => !v);
  }
}}
```

**Fix — preferred (use native button):**
```tsx
<button
  type="button"
  aria-expanded={showContact}
  aria-label="Add contact for follow-up"
  onClick={() => setShowContact((v) => !v)}
  style={{
    marginTop: 16,
    display: "flex",
    alignItems: "center",
    justifyContent: "space-between",
    width: "100%",
    padding: "14px 4px",
    fontSize: 14,
    color: "var(--muted)",
    cursor: "pointer",
    background: "transparent",
    border: "none",
  }}
>
```

### WR-05: `crossOrigin=""` on Leaflet CSS link is an invalid attribute value

**File:** `frontend/app/layout.tsx:60`

**Issue:**
```tsx
<link
  rel="stylesheet"
  href="https://unpkg.com/leaflet@1.9.4/dist/leaflet.css"
  integrity="sha256-p4NxAoJBhIIN+hmNHrzRCf9tD/miZyoHS5obTRR9BMY="
  crossOrigin=""
/>
```

The valid values for the HTML `crossorigin` attribute are `"anonymous"` and
`"use-credentials"`. An empty string is not a valid enumerated value. The spec says
invalid values must be treated as `"anonymous"`, and most browsers do so — but the
behaviour is implementation-defined. More importantly, Subresource Integrity (the
`integrity` attribute) requires the fetched resource to pass CORS. If a browser treats
`crossOrigin=""` as "absent" rather than "anonymous", the SRI check will fail and the
Leaflet stylesheet will be blocked. Failure would manifest as an unstyled map with no
console error that points directly at the root cause.

**Fix:**
```tsx
crossOrigin="anonymous"
```

### IN-03: Canvas `getContext("2d")` non-null assertion can crash on low-memory devices

**File:** `frontend/app/report/page.tsx:94` and `frontend/app/components/ReportCTA.tsx:28`

**Issue:** Both copies of `compressImage` use `canvas.getContext("2d")!`. On some
older Android WebViews under memory pressure, `getContext("2d")` returns `null`. The
non-null assertion causes an unhandled `TypeError` that surfaces as a crash rather than
the controlled "photo too large" error path.

**Fix** (also part of WR-02's suggested extraction):
```typescript
const ctx = canvas.getContext("2d");
if (!ctx) return null; // falls through to "too large" error branch
ctx.drawImage(img, 0, 0);
```

### IN-04: `photo-store.ts` comment inaccurately claims "never imported on server"

**File:** `frontend/app/lib/photo-store.ts:2-3`

**Issue:** The comment reads: "Browser-only module singleton — NOT SSR-safe (never
imported on server)." However, `report/page.tsx` is a `"use client"` component that
imports `consumePendingPhoto` at the top level. In Next.js 14 App Router, `"use
client"` components are still pre-rendered on the server for the initial HTML shell, so
the module *is* imported server-side. The module-level `let _pending` is instantiated
on the server. This is not a runtime bug (the store is empty server-side and the mount
effect only runs in the browser), but the comment is incorrect and could mislead a
future developer into relying on the "never imported on server" guarantee.

**Fix:** Update the comment:
```typescript
// photo-store.ts
// Browser singleton for passing a processed photo from the home CTA to /report.
// The module IS imported during SSR (via "use client" pre-render) but _pending is
// always null server-side — storePendingPhoto is only reachable from browser code.
```
