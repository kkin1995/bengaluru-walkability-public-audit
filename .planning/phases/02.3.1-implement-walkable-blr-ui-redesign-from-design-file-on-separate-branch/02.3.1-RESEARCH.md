## Summary

The existing codebase is a clean Next.js 14 App Router project with a 4-step wizard on a single `"use client"` page (`/report/page.tsx`). The wizard manages all state in a single `FormState` object via `useState` with a `step` counter. The redesign collapses this 4-step flow (Photo → Location → Category → Details) into a 2-step flow (Category → Confirm), which is a structural change but not a fundamental architectural one.

The project uses Tailwind CSS exclusively for styling. The design system uses only CSS custom properties (CSS variables), which are completely orthogonal to Tailwind — adding them to `globals.css` does not conflict with any existing Tailwind class. The new UI primitives (Bi, Icon, Btn, Pill, SectionLabel) are pure TSX components that emit inline styles or small CSS classes, so they do not require any changes to Tailwind configuration.

The new design system's fonts (Inter, JetBrains Mono, Noto Sans Kannada) must be loaded via Google Fonts. The correct pattern in Next.js 14 App Router is `next/font/google`, which self-hosts font files and adds `<link>` tags in the `<head>` at build time — this is the required pattern since the CLAUDE.md architecture mandates no direct `<link>` tag injection for fonts. However, because the existing `layout.tsx` uses a manual `<link>` tag for Leaflet CSS (it's not a font), the pattern is already established that `<head>` is used for external stylesheets. The fonts can be added via either `next/font` (preferred, type-safe, self-hosted) or via a `<link>` tag in `layout.tsx`. Both work; `next/font` is idiomatic Next.js 14.

**Primary recommendation:** Implement the redesign as a new parallel page structure (`/` replaced, `/report` refactored to 2-step, `/map` wrapped in new layout) on the `ui-redesign` branch, keeping the existing `report/page.tsx` logic intact as a reference but replacing its JSX entirely. Use `next/font/google` for fonts, additive CSS variables in `globals.css`, and new UI primitives in `app/components/ui/`.

### Pattern 2: next/font/google with CSS Variable Mode
**What:** Load Inter, JetBrains Mono, Noto Sans Kannada via `next/font/google`, expose as CSS variables, then reference those variables in the design system's `--font-sans` etc.
**When to use:** In `layout.tsx` — applied once at root level.

```typescript
// frontend/app/layout.tsx
import { Inter, JetBrains_Mono, Noto_Sans_Kannada } from 'next/font/google';

const inter = Inter({
  subsets: ['latin'],
  weight: ['400', '500', '600', '700'],
  variable: '--font-inter',
  display: 'swap',
});

const jetbrainsMono = JetBrains_Mono({
  subsets: ['latin'],
  weight: ['400', '500'],
  variable: '--font-jetbrains-mono',
  display: 'swap',
});

const notoSansKannada = Noto_Sans_Kannada({
  subsets: ['kannada'],
  weight: ['400', '500', '600'],
  variable: '--font-noto-sans-kannada',
  display: 'swap',
});

// Apply to html element:
<html lang="en" className={`${inter.variable} ${jetbrainsMono.variable} ${notoSansKannada.variable}`}>
```

Then in `globals.css`, `--font-sans` references `var(--font-inter)` which is the CSS variable name set by next/font.

**Confidence:** HIGH — this is the canonical `next/font` pattern documented by Next.js.

### Pattern 3: 2-Step Report Flow — State Management
**What:** The current flow is 4 steps in a single page with `useState`. The new flow is 2 steps: (1) Category picker + photo review, (2) Confirm + submit. State must pass between steps.

**Current state shape (from report/page.tsx):**
```typescript
interface FormState {
  file: File | null;
  lat: number;
  lng: number;
  locationSource: "exif" | "manual_pin";
  gpsConfirmed: boolean;
  category: string;
  severity: string;
  description: string;
  name: string;
  contact: string;
}
```

**New flow:** The file picker (OS camera delegation) triggers on the home page CTA. After the user selects a photo, the app navigates to the category screen. Category selection then moves to confirm screen. The app currently handles this entirely within `/report/page.tsx` via step state.

**Recommended approach (discretion area):** Keep the 2-step flow in a single `"use client"` page at `/report/page.tsx` with `step` state (0=category, 1=confirm, success=submitted). This is simpler than separate routes and avoids cross-route state serialization problems with `File` objects (which cannot be passed via URL params or Next.js router state). `File` objects cannot be serialized to JSON, so URL search params and `router.push()` state are not viable for passing the selected photo.

**Alternative:** Two separate routes (`/report/category`, `/report/confirm`) with shared state via React Context or localStorage. This adds complexity with no user-visible benefit.

**Recommendation:** Single page, 2-step `useState` pattern — mirrors the current implementation pattern exactly.

### Pattern 4: PhotoCapture — File Input with OS Camera Delegation
**What:** The design removes the in-app viewfinder. The OS camera is delegated to via `<input type="file" accept="image/*" capture="environment">`. This is already implemented in `PhotoCapture.tsx` with the label-wrapping pattern (critical for iOS Safari — from Phase 02.3 locked decision).

**Key existing logic to preserve verbatim:**
- `exifr.gps(file)` called on original file BEFORE compression (Phase 02.3 decision)
- `compressImage()` reduces oversized files
- Two separate `<label>`-wrapped inputs: one with `capture="environment"` (camera), one without (gallery)
- `sr-only` class on inputs — labels are the visible clickable targets

The redesign replaces the visual shell of `PhotoCapture` but the `handleFile`, `handleInputChange`, and internal logic is untouched.

**Home page flow:** The OS camera is triggered from the home page CTA button. The CTA is a `<label>` element wrapping a hidden `<input type="file" capture="environment">`. On photo selection, EXIF extraction happens, then the user is shown the Category screen. This means the file-picker logic moves from `PhotoCapture.tsx` into the home page or a shared hook.

**Options for photo capture trigger location:**
1. Keep `PhotoCapture` as a logic component, render it invisibly on the home page, trigger programmatically — complex
2. Inline the file input + EXIF logic in the report page, triggered from home page via navigation — clean
3. Create a `usePhotoCapture` hook that encapsulates the logic and can be used on any page

**Recommended:** Option 2 — the home page has a `<label>` wrapping a hidden `<input type="file" capture="environment">`. On file selection, EXIF is extracted, and the state is set (same `handlePhoto` logic). The label triggers the OS camera. This matches how the design prototype works.

### Pattern 5: Leaflet/ReportsMap — SSR Disabling (confirmed working)
**What:** `ReportsMap` is already wrapped with `dynamic(() => import(...), { ssr: false })`. The new `/map` page must preserve this pattern.

The current `/map/page.tsx` is a server component (no `"use client"` directive, uses `force-dynamic`). The `ReportsMap` is dynamically imported. This pattern must be preserved.

The new map page wraps `ReportsMap` in the new overlay layout (floating top bar, filter chips, floating CTA). This wrapper is presentational — the map itself remains `ReportsMap` as-is.

### Anti-Patterns to Avoid
- **Replacing Tailwind classes in admin pages:** The redesign only touches citizen-facing pages. Admin pages (`/admin/*`) continue to use Tailwind. Do not rename or remove Tailwind utility classes.
- **Putting CSS variables on `.screen` instead of `:root`:** The design prototype uses a `.screen` wrapper class inside a phone frame. In the actual Next.js app, variables must be on `:root` to apply globally.
- **Setting `font-family` on `<body>` via Tailwind:** The design system sets `body { font-family: var(--font-sans); }` in its CSS. This conflicts with Tailwind's `font-sans` utility. The resolution: add `body { font-family: var(--font-sans); }` inside the `:root` block's companion CSS rules in `globals.css`. Do not use `className="font-sans"` on `<body>` in `layout.tsx` for redesigned pages.
- **Using `oklch()` colors without checking browser support:** `oklch()` is supported in all modern browsers (Chrome 111+, Firefox 113+, Safari 15.4+). Since this is a PWA targeting modern mobile browsers (citizens in Bengaluru on Android/iOS), this is acceptable. Confirmed HIGH confidence.
- **Using `next/font` with `import` inside a component file:** `next/font/google` imports must be at the module level in `layout.tsx` or a dedicated fonts file — not inside component render functions.

## Common Pitfalls

### Pitfall 1: `File` Object Cannot be Passed via URL/Router State
**What goes wrong:** Attempting to store the selected `File` in URL search params or Next.js router `push()` state to pass it from the home page trigger to the report page.
**Why it happens:** `File` is not serializable. `router.push('/report?file=...')` will not work.
**How to avoid:** Keep photo selection and report flow on the same page (`/report/page.tsx`) using `useState`. The home page CTA navigates to `/report`; the report page immediately renders the file input. Alternatively, the CTA on the home page IS the file input (label-wrapped).
**Warning signs:** `"File object not serializable"` errors, or photo arriving as `undefined` on the confirm screen.

### Pitfall 2: `oklch()` Color Values and CSS Variable References
**What goes wrong:** Referencing `var(--accent)` in a context that renders server-side and injects into inline styles — this is fine. But if you use `oklch()` in Tailwind's `theme.extend.colors`, Tailwind will fail to process it unless PostCSS has the right plugins.
**Why it happens:** Tailwind processes colors at build time; `oklch()` is a runtime CSS feature.
**How to avoid:** Never put `oklch()` values in `tailwind.config.ts`. Use them only in `globals.css` CSS variables and inline TSX style props. All the design system primitives (Btn, Pill, etc.) use inline style objects — this is safe.
**Warning signs:** Tailwind build errors mentioning `oklch`.

### Pitfall 3: `next/font` Import Rules
**What goes wrong:** Calling `Inter({ ... })` inside a component function, getting a Next.js build error: `next/font must be used in `app/layout.tsx` or `pages/_app.tsx``.
**Why it happens:** `next/font` performs font loading at build time; it must be at the module top level in a root layout or `_app`.
**How to avoid:** Define all three font instances at module level in `app/layout.tsx`. Apply their `.variable` classes to the `<html>` element.
**Warning signs:** `Error: next/font called at runtime` build error.

### Pitfall 4: `font-feature-settings` on Body Conflicts with Tailwind
**What goes wrong:** The design system sets `font-feature-settings: "cv02", "cv03", "cv04", "cv11"` on `body`. If `layout.tsx` also applies Tailwind `antialiased` via `className="antialiased"`, there is no conflict (antialiased is about font smoothing). However, if the body CSS in `globals.css` sets `font-family: var(--font-sans)`, this will override Tailwind's default font-family for all pages including admin.
**Why it happens:** `body` CSS rules in `globals.css` are global.
**How to avoid:** Scope the `body { font-family: var(--font-sans); }` rule to the new screen pages only, OR accept that admin pages also get Inter (which is fine since admin also uses a sans-serif). The decision should be explicit.
**Recommendation:** Apply `body { font-family: var(--font-sans); }` globally — Inter is a better default than the Tailwind system stack, and admin pages are not adversely affected.

### Pitfall 5: Leaflet SSR / Dynamic Import in New Map Page
**What goes wrong:** The new `/map/page.tsx` may be refactored to a `"use client"` component (because it has interactive filter chips), causing `ReportsMap` to be rendered on the server.
**Why it happens:** `dynamic(..., { ssr: false })` only prevents SSR when the parent is NOT a client component. If the page is `"use client"`, `dynamic` with `ssr: false` still works — React skips SSR for that subtree.
**How to avoid:** Keep `dynamic(..., { ssr: false })` on `ReportsMap` regardless of whether the parent is a server or client component. This is already the pattern in the codebase.
**Warning signs:** `ReferenceError: window is not defined` during `next build`.

### Pitfall 6: Honeypot Field Must Be Preserved
**What goes wrong:** The new report page omits the off-screen honeypot `<input name="website">` field from the form submit payload.
**Why it happens:** The design prototype doesn't show it (it's invisible by design).
**How to avoid:** The honeypot (ABUSE-02) must be preserved in any rewrite of `report/page.tsx`. It is a security requirement, not a UI element.
**Warning signs:** `honeypot` field missing from FormData sent to backend — backend still accepts (fake success), but abuse protection is gone.

### Pitfall 7: Existing PhotoCapture Tests Break When UI Shell Changes
**What goes wrong:** The PhotoCapture test queries for `screen.getByText(/take photo/i)` and `screen.getByText(/upload from gallery/i)`. If the new UI uses different label text, tests fail.
**Why it happens:** Tests are tied to specific rendered text. The new design uses the same text ("Take Photo", "Upload from Gallery") but in the new UI context.
**How to avoid:** Check test assertions against new component text before changing labels. The CONTEXT.md confirms the same action labels are used.
**Test file:** `frontend/app/components/__tests__/PhotoCapture.test.tsx` (356 lines, comprehensive). The label-wrapping structure (`input[capture="environment"]` inside a `<label>`) must be preserved — tests assert `cameraInput.closest("label")`.

## Open Questions

1. **Home page photo trigger: file input inline or navigate to `/report`?**
   - What we know: Design shows CTA on home page triggers OS camera. After photo selection, app shows category screen. The category screen and confirm screen are step 1/step 2.
   - What's unclear: Does the file picker live on the home page (triggering navigation on selection), or does clicking the home CTA navigate to `/report` which immediately presents the file picker?
   - Recommendation: Clicking the home CTA navigates to `/report`, which immediately renders the file input (step -1 or step 0 = photo selection state). No change to routing; the category picker only appears after a photo is selected. This avoids File object serialization issues entirely.

2. **Confirm screen "Adjust" location button — LocationMap or placeholder?**
   - What we know: Design shows a 120px mini-map with a "Adjust" button. The existing `LocationMap` component provides this interactive functionality.
   - What's unclear: The CONTEXT.md says GPS is trusted silently. The Adjust button is in scope (it's in the design). But full Adjust flow (interactive pin-drag) may be over-engineered for this phase.
   - Recommendation: Show the mini-map tile placeholder (`.map-tile` CSS class) with the Adjust button. Clicking Adjust opens `LocationMap` (already exists). This matches the design exactly.

3. **Do new pages use Tailwind classes or pure CSS variables?**
   - What we know: The design prototypes use inline styles and CSS custom properties exclusively. The new primitives (Btn, Pill, etc.) use inline style objects.
   - What's unclear: Should new page-level layout use Tailwind (`flex`, `px-4`) or pure CSS?
   - Recommendation: Use Tailwind for layout utilities (`flex`, `gap`, `px-`, `overflow-`) on page-level wrappers, and CSS variables + inline styles for color/typography on branded elements. This is practical and avoids rewriting all layout logic.
