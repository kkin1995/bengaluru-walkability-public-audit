# Phase 02.3.2: Code Review Report

**Reviewed:** 2026-04-25T00:00:00Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

This phase implemented three design pieces: the gallery escape hatch in `ReportCTA.tsx`, the `CategoryGrid` redesign, and the map filter chip strip in `map/page.tsx` with supporting `ReportsMap.tsx` props. The implementation is largely correct and matches the UI spec. No critical security or data-loss issues were found.

Four warnings were identified: a `previewUrl` object URL leak on the compression-failure path (both handlers), a same-file re-selection bug that silently swallows a second pick of the same photo, a spec mismatch in chip count display for zero-count categories, and a non-functional filter icon button rendered with `cursor: pointer` and `aria-label` that has no `onClick` handler. Three info items flag code duplication, a non-null assertion on canvas context, and Leaflet icons loaded from an external CDN.

## Warnings

### WR-01: Object URL leaked when image compression fails

**File:** `frontend/app/components/ReportCTA.tsx:50` and `:111`

**Issue:** In both `handleChange` and `handleGalleryChange`, `previewUrl = URL.createObjectURL(file)` is called immediately after file selection. On the compression-failure path (when `compressImage` returns `null`), the function calls `router.push("/report")` without calling `URL.revokeObjectURL(previewUrl)` or passing `previewUrl` to `storePendingPhoto`. The object URL is created and then orphaned for the lifetime of the browser tab.

The leak occurs at lines 87-90 (`handleChange`) and 146-148 (`handleGalleryChange`):
```ts
// previewUrl was just created (line 50 / 111) but is never revoked here
setProcessing(false);
router.push("/report");
return;
```

**Fix:** Revoke the URL on the failure path before navigating away:
```ts
if (!compressed) {
  URL.revokeObjectURL(previewUrl);   // add this
  setProcessing(false);
  router.push("/report");
  return;
}
```

### WR-02: Same-file re-selection silently fails after an error

**File:** `frontend/app/components/ReportCTA.tsx:188-203` and `:238-244`

**Issue:** Neither the camera input (`inputRef`) nor the gallery input (`galleryRef`) resets `input.value` after processing. The browser only fires `onChange` when the selected file changes. If compression fails and the user navigates back to the home page and tries to pick the exact same photo again, `onChange` will not fire. The UI appears functional (the input is clickable) but the handler is never invoked, leaving the user stuck with no feedback.

**Fix:** Clear the input value at the start of each handler so subsequent picks always trigger `onChange`:
```ts
async function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (!file) return;
  // Reset so re-selecting the same file fires onChange next time
  e.target.value = "";
  setProcessing(true);
  // ... rest of handler unchanged
}
```
Apply the same fix to `handleGalleryChange`.

### WR-03: Map filter icon button is non-functional but styled as interactive

**File:** `frontend/app/map/page.tsx:144-163`

**Issue:** The circular filter icon button in the top overlay bar has `cursor: pointer`, `aria-label="Filter reports"`, and a visible icon, but has no `onClick` handler. A user (and screen-reader) is led to believe it is interactive. Clicking it does nothing. This is distinct from the chip strip (which is fully functional) — the filter icon was not mentioned in the deferred list in `CONTEXT.md`, and the UI spec's Frame 05 section does not describe it as intentionally passive.

```tsx
<button
  type="button"
  className="press"
  aria-label="Filter reports"
  // no onClick — silently does nothing
  style={{ ..., cursor: "pointer" }}
>
  <Icon name="filter" size={18} />
</button>
```

**Fix:** Either wire it up (e.g., scroll the chip strip into focus) or, if intentionally deferred, remove `cursor: pointer` and add `aria-hidden="true"` plus `tabIndex={-1}` so it does not appear interactive to assistive technology:
```tsx
<div
  aria-hidden="true"
  style={{ ..., cursor: "default", pointerEvents: "none" }}
>
  <Icon name="filter" size={18} />
</div>
```

### WR-04: Chip count for zero-report categories deviates from spec

**File:** `frontend/app/map/page.tsx:22-31`

**Issue:** The UI spec (02.3.2-UI-SPEC.md line 262) states: "When count is 0, still show `Damaged · 0`." The `chipLabel` function uses `n != null` as the guard:

```ts
const n = counts[chip.value];
return n != null ? `${chip.label} · ${n}` : chip.label;
```

`counts` is built by a `reduce` over loaded reports. A category with zero reports never appears as a key in `counts`, so `counts[chip.value]` is `undefined`. The guard `undefined != null` is `false`, so it falls through to the bare label — "Damaged" instead of "Damaged · 0". After data loads, zero-count chips show no count at all, contradicting the spec and creating an inconsistent visual rhythm across the strip.

**Fix:** Compute counts against the full category list so zero entries are explicit, or default missing keys to 0:
```ts
const n = counts[chip.value] ?? 0;
return `${chip.label} · ${n}`;
// For the "all" chip:
if (chip.value === "all") return `All · ${total}`;
```

## Info

### IN-01: `handleChange` and `handleGalleryChange` are near-identical duplicates

**File:** `frontend/app/components/ReportCTA.tsx:44-104` and `:106-162`

**Issue:** Both handlers are ~57 lines each and differ only in their name. The EXIF extraction block, compression loop, `storePendingPhoto` call, and `router.push` are duplicated verbatim. The phase context (D-06, D-07) notes the gallery path "must replicate this same pipeline," which explains the initial implementation, but the duplication creates a maintenance risk — any fix to one handler must be manually mirrored to the other.

**Fix:** Extract a shared helper and call it from both handlers:
```ts
async function processFileAndNavigate(file: File) {
  setProcessing(true);
  const previewUrl = URL.createObjectURL(file);
  // ... shared EXIF + compression + storePendingPhoto + router.push logic
  setProcessing(false);
}

async function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (!file) return;
  e.target.value = "";
  await processFileAndNavigate(file);
}

async function handleGalleryChange(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (!file) return;
  e.target.value = "";
  await processFileAndNavigate(file);
}
```

### IN-02: Non-null assertion on `canvas.getContext("2d")`

**File:** `frontend/app/components/ReportCTA.tsx:28`

**Issue:** `canvas.getContext("2d")!.drawImage(img, 0, 0)` uses a TypeScript non-null assertion. While `getContext("2d")` returns `null` only in extremely rare environments (some server-side or locked-down contexts), the `!` suppresses the type-safety check entirely. If it ever returns `null` in a real browser (e.g., canvas disabled via Content Security Policy), this throws a runtime `TypeError: Cannot read properties of null` that is not caught by the surrounding `try/catch` in the callers (there is no surrounding try/catch in `compressImage` itself — callers check the return value, not exceptions).

**Fix:** Guard the context access explicitly:
```ts
const ctx = canvas.getContext("2d");
if (!ctx) return null;
ctx.drawImage(img, 0, 0);
```

### IN-03: Leaflet default icons fetched from unpkg CDN at runtime

**File:** `frontend/app/components/ReportsMap.tsx:49-55`

**Issue:** The Leaflet icon patch hard-codes three `unpkg.com` URLs. These are loaded at map mount time on every page visit. If unpkg is slow or unavailable, map markers render as broken images. This is a third-party runtime dependency that could be eliminated by bundling the icons locally.

**Fix:** Copy the three Leaflet icon images into `frontend/public/leaflet/` and reference them as local paths:
```ts
L.Icon.Default.mergeOptions({
  iconRetinaUrl: "/leaflet/marker-icon-2x.png",
  iconUrl: "/leaflet/marker-icon.png",
  shadowUrl: "/leaflet/marker-shadow.png",
});
```
The files are available in `node_modules/leaflet/dist/images/`.
