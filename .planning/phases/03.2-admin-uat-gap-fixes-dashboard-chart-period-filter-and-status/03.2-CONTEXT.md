<decisions>
## Implementation Decisions

### Bug 1: Dashboard Chart Period Filter (ISSUE-03.1-B)
- **D-01 [LOCKED]**: Fix is frontend-only — no backend changes needed. The backend `GET /api/admin/stats` endpoint likely already accepts a `?days=N` query parameter (or the frontend queries for date ranges). The component needs a `useState` for the active period and a re-fetch / recompute when period changes.
- **D-02 [LOCKED]**: Scope is limited to the admin dashboard page (`frontend/app/admin/page.tsx` or the intake chart sub-component). Do not refactor unrelated dashboard sections.
- **D-03 [Claude's Discretion]**: If the backend does not already support a period parameter on `/api/admin/stats`, a minimal backend addition is acceptable — but verify the existing API before adding one.

### Bug 2: Status History Invalid Date + SYSTEM Attribution (Phase 3.1 UAT test #7)
- **D-04 [LOCKED]**: Backend fix required: add `r.updated_at` to the `get_admin_report_by_id` SELECT in `backend/src/db/admin_queries.rs`. The `AdminReport.updated_at` field is already declared in the Rust struct — the SQL just doesn't select it.
- **D-05 [LOCKED]**: Backend fix required: implement `status_history` data in the single-report response. The `status_history` table exists (migration 002) with `report_id`, `changed_by_id`, `old_status`, `new_status`, `changed_at`, `notes`. The `admin_users` table has `display_name`. The implementation must JOIN `status_history` with `admin_users` on `changed_by_id = admin_users.id`.
- **D-06 [LOCKED]**: The status history entries must be included inline in the existing `GET /api/admin/reports/:id` response (not a separate endpoint). Adding a `status_history: Vec<StatusHistoryEntry>` field to `AdminReport` / `AdminReportResponse` is the correct approach — it avoids a second API round-trip and keeps the frontend simple.
- **D-07 [LOCKED]**: Frontend fix required: replace the hardcoded placeholder at `frontend/app/admin/reports/[id]/page.tsx` around line 502 — `formatDate(report.updated_at)` and `'· BY · SYSTEM'` — with the real `status_history` array from the API response.
- **D-08 [Claude's Discretion]**: Define a `StatusHistoryEntry` TypeScript type in `frontend/app/lib/types.ts` (or the relevant admin types file) matching the backend response shape. Render each history entry with `formatDate(entry.changed_at)` and `entry.changed_by_name` (or `entry.changed_by?.display_name`).

### Quality
- **D-09 [LOCKED]**: `cargo test` must pass after backend changes. `npm run build` and all existing frontend tests must pass.
- **D-10 [LOCKED]**: No new TypeScript errors. No new Clippy warnings in modified files.
