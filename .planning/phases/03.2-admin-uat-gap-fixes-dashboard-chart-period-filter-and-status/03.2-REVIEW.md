# Phase 03.2: Code Review Report

**Reviewed:** 2026-05-30T08:48:43Z
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Phase 03.2 adds two features: (1) real `status_history` rendering on the admin report detail
page with admin attribution, replacing a hardcoded "BY · SYSTEM" placeholder; and (2)
clickable 7D/14D/30D period filter buttons on the dashboard sparkbars chart.

The backend SQL for the new `status_history` query is structurally sound and uses
parameterized binds throughout — no injection risk. The React components use JSX
text escaping correctly — no XSS via `dangerouslySetInnerHTML`.

However, one critical correctness bug exists: every `status_history` INSERT in
`admin_queries.rs` (three call sites) omits the `old_status` column entirely. The
migration schema has `old_status report_status` as a nullable column that records
the prior state, but none of the insert statements populate it. The `changed_at`
date shown in the UI will always be correct, but the `old_status` field will always
be NULL in the database even when a prior status existed — making the audit trail
incomplete and misleading when displayed (D-05/D-06 requirement gap).

Additional warnings cover a stale enum value in `statusActionLabel`, a misleading
"+X today" label, a coverage gap for the sparkbars value change, and two minor
type-safety issues in the frontend types.

## Critical Issues

### CR-01: All `status_history` INSERTs permanently omit `old_status` — audit trail always NULL

**File:** `backend/src/db/admin_queries.rs:641-651`, `707-716`, `763-771`
**Issue:** The `status_history` table has an `old_status report_status` nullable
column (defined in `migrations/001_init.sql:73`). Every INSERT statement in this
file uses only `(report_id, new_status, note, changed_by)` — four columns — and
never reads or writes `old_status`. As a result, every row ever written to
`status_history` has `old_status = NULL` regardless of what status the report was
in before the transition.

The backend SELECT in `get_admin_report_by_id` at line 562 does read
`old_status::TEXT AS old_status`, and the frontend `StatusHistoryEntry` interface
has `old_status: string | null`. The column is modelled as optional, so no crash
occurs. But the semantic contract of the audit trail (D-05/D-06: "track every
status transition") is broken: a report moving from `open` → `acknowledged` →
`in_progress` will show three history rows all with `old_status: null`.

The correct fix requires capturing the current status of the report before (or
atomically with) updating it, then passing that value to the INSERT.

All three affected sites:

```sql
-- update_report_status (line 640)
INSERT INTO status_history (report_id, new_status, note, changed_by)
-- Should be:
INSERT INTO status_history (report_id, old_status, new_status, note, changed_by)
-- with old_status captured from a prior SELECT or RETURNING on the UPDATE.

-- resolve_report (line 706)
-- same omission

-- assign_report_org (line 764)
-- same omission (hardcodes new_status = 'assigned', never captures the old status)
```

**Fix — preferred approach:** Use a CTE to atomically capture the old status in the
same statement that performs the UPDATE:

```sql
-- update_report_status example (adapt for resolve_report and assign_report_org):
WITH updated AS (
    UPDATE reports
    SET status = $1::report_status
    WHERE id = $2
    RETURNING id, status AS new_status,
              (SELECT status FROM reports WHERE id = $2) AS old_status
              -- or: use a BEFORE-trigger column, or pass old_status from the
              -- handler after a SELECT FOR UPDATE
)
INSERT INTO status_history (report_id, old_status, new_status, note, changed_by)
SELECT $2, old_status::TEXT::report_status, new_status, $3, $4
FROM updated;
```

A simpler approach that avoids the CTE: in `update_report_status`, before the
UPDATE, do a `SELECT status FROM reports WHERE id = $1` inside the same transaction
and pass the result as an additional bind parameter to the INSERT.

## Warnings

### WR-01: `statusActionLabel` uses stale enum value `"under_review"`

**File:** `frontend/app/admin/page.tsx:25`
**Issue:** Migration `008_workflow.sql` renamed the `under_review` enum value to
`acknowledged`. The `statusActionLabel` helper at line 25 checks
`status === "under_review"` which will never match any report returned from the
current backend (reports now have statuses `open`, `acknowledged`, `assigned`,
`in_progress`, `resolved`, `closed`). The activity feed will always label
non-resolved, non-open reports as "New" instead of an appropriate label.

```typescript
// Current (buggy):
function statusActionLabel(status: string): string {
  if (status === "resolved") return "Resolved";
  if (status === "under_review") return "Under review";  // dead branch
  return "New";
}

// Fix — cover all 6 current enum values:
function statusActionLabel(status: string): string {
  if (status === "resolved" || status === "closed") return "Resolved";
  if (status === "acknowledged" || status === "assigned" || status === "in_progress")
    return "Under review";
  return "New";  // "open"
}
```

### WR-02: `corporation` column in `list_admin_reports` joined from `wards` but the detail query joins from `organizations`

**File:** `backend/src/db/admin_queries.rs:369`, `519`
**Issue:** `list_admin_reports` (line 369) uses `wards.corporation AS corporation` — a
TEXT column that exists directly on the `wards` table (added in migration
`004_ward_boundaries.sql`). `get_admin_report_by_id` (line 519) uses
`o.name AS corporation` via `LEFT JOIN organizations o ON o.id = w.org_id`.

These two fields are not guaranteed to be the same value. The `wards.corporation`
column contains a denormalized string such as "West" or "East". The
`organizations.name` column contains whatever string was seeded in `010_org_seed.sql`
(e.g. "BBMP West Zone Corporation"). A report viewed on the list page will show a
different corporation label than the same report viewed on the detail page. This
creates a data consistency discrepancy visible to admins.

**Fix:** Pick one authoritative source and use it consistently. If `wards.corporation`
is the canonical readable label, join via it in both queries. If the organizations
table is the authoritative source, add `LEFT JOIN organizations o ON o.id = w.org_id`
to `list_admin_reports` and use `o.name AS corporation` there too.

### WR-03: `+X today` mobile hero card uses current-open-count, not today's submission count

**File:** `frontend/app/admin/page.tsx:334`
**Issue:** The mobile hero card displays `+${statsForCards.submitted} today` (line 334).
`statsForCards.submitted` is mapped from `stats.by_status.open` (line 80) — the
current count of reports in `open` status. This is a snapshot of current state, not
the number of new reports submitted today. As reports are acknowledged or assigned,
this number decreases, so the label "+15 today" would actually mean "15 currently
open" not "15 submitted since midnight". The text label is semantically incorrect.

**Fix:** Either remove the "today" qualifier and label it plainly:
```tsx
{statsForCards ? `${statsForCards.submitted} open` : "—"}
```
Or add a separate per-day intake endpoint and use the real today count.

### WR-04: `get_admin_report_by_id` uses `.get::<String, _>` on nullable `image_path` — panics if NULL

**File:** `backend/src/db/admin_queries.rs:594`
**Issue:** `r.get::<String, _>("image_path")` at line 594 uses the panicking `.get()`
variant. The `reports.image_path` column is defined as `TEXT NOT NULL` in the
migration, so under normal conditions this is safe. However, the `list_admin_reports`
mapping at line 413 also uses `.get::<String, _>("image_path")` with the same
assumption. If any future migration relaxes this constraint, or if test rows with
NULL image paths are inserted, these calls will panic instead of returning an error.

The `get_duplicate_reports_for_original` function at line 464 already uses
`try_get::<String, _>("image_path").unwrap_or_default()` defensively on the same
column — showing inconsistent safety posture across query functions.

**Fix:** For consistency and defense in depth, use `try_get` with a fallback at all
three sites, matching the pattern already used in `get_duplicate_reports_for_original`:
```rust
"image_path": r.try_get::<String, _>("image_path").unwrap_or_default(),
```

### WR-05: `WardHierarchy` TypeScript interface includes `ward_number` field not present in backend JSON

**File:** `frontend/app/admin/lib/adminApi.ts:50`
**Issue:** The `WardHierarchy` interface (line 50) declares `ward_number: number | null`.
The backend `get_admin_report_by_id` function builds the `ward_hierarchy` JSON object
(lines 574–587) and does not include a `ward_number` key. The test fixture in
`page.test.tsx` line 214 also sets `ward_number: 117` in its `PHASE3_REPORT` fixture,
but this value is silently dropped by the backend and will always be `undefined` at
runtime.

This means any frontend code that reads `report.ward_hierarchy?.ward_number` will get
`undefined`, not `null` (since the key is absent), which can cause `undefined` to be
rendered as text if not guarded. The type declaration is misleading about what the API
actually returns.

**Fix (two options):**
1. Remove `ward_number` from the `WardHierarchy` interface if it is not needed in the
   UI.
2. Add `r.get::<Option<i32>, _>("ward_number")` to the `ward_hierarchy` JSON in
   `get_admin_report_by_id` — but this requires `ward_number` to be selected from
   `w.ward_number` in the SQL, which it currently is not.

## Info

### IN-01: No test verifies that sparkbars values actually change when period button is clicked

**File:** `frontend/app/admin/__tests__/dashboard.test.tsx:407-473`
**Issue:** The period filter tests (lines 407–473) verify that clicking a period
button changes the `data-tone` attribute of the corresponding Pill from `"outline"`
to `"accent"` (i.e., visual active state). They do not verify that the `values` prop
passed to `<Sparkbars>` actually changes length. The behavior tested is purely
cosmetic (CSS token switch). The core logic under `sparkbarsValues` — slicing the
stub array to 7 elements for 7D and padding to 30 for 30D — has zero test coverage.

If `Sparkbars` is mocked in the test environment, this gap is invisible. A test
asserting that the `Sparkbars` component receives `values.length === 7` after clicking
7D would close this gap.

### IN-02: `statusDotColor` default case silently maps unknown statuses to `--status-open`

**File:** `frontend/app/admin/reports/[id]/page.tsx:54`
**Issue:** The `default` branch of `statusDotColor` returns `"var(--status-open)"`.
If a new status value is added to the enum (e.g., `"escalated"`) and the switch is
not updated, it will silently display an "open" color dot instead of making the
missing case visible. This is a minor silent-failure risk as the status enum evolves.

**Fix:** A `console.warn` in the default branch would make unhandled statuses visible
during development without affecting production rendering:
```typescript
default:
  if (process.env.NODE_ENV === "development") {
    console.warn(`statusDotColor: unhandled status "${status}"`);
  }
  return "var(--status-open)";
```

### IN-03: Test fixture `FULL_REPORT` uses retired status value `"submitted"`

**File:** `frontend/app/admin/reports/[id]/__tests__/page.test.tsx:62`
**Issue:** The base `FULL_REPORT` fixture sets `status: "submitted"` (line 62).
Migration `008_workflow.sql` renamed this value to `"open"`. Tests that exercise the
status badge path will pass a value that the real backend will never return. This
does not break tests today because `StatusBadge` is rendering whatever string it
receives, but it means the tests are exercising a dead code path and will give false
assurance if `StatusBadge` ever adds validation on the status string.

**Fix:** Update the fixture to `status: "open"` to match the current enum:
```typescript
const FULL_REPORT = {
  // ...
  status: "open",   // was "submitted" — renamed in migration 008
  // ...
};
```
