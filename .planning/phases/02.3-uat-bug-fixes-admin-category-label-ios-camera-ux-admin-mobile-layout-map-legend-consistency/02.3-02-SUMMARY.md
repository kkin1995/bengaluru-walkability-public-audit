# Phase 02.3 Plan 02: iOS Camera UX Fix Summary

**Label-wrapped sr-only file inputs replace hidden-input+programmatic-click so iOS Safari correctly opens camera vs. photo library based on the capture attribute**

## Accomplishments

- Replaced `<button onClick={() => ref.click()}>` + hidden `<input>` with `<label>` wrapping `<input className="sr-only">` for both Take Photo and Upload from Gallery
- Camera label contains `<input capture="environment">` — iOS Safari respects this attribute when triggered natively via label association
- Gallery label contains `<input>` with NO capture attribute — iOS opens photo library instead of camera
- Visual design identical: same green camera button, white gallery button, icons, text, layout
- `clearPhoto()` unchanged: cameraRef and galleryRef still point to the inputs (now inside labels)
- Updated all 4 sites in tests that used `getByRole('button', { name: /take photo/i })` or `getByRole('button', { name: /upload from gallery/i })` to use `getByText` or DOM structure assertions
- Rewrote AC1.1 click-spy tests as DOM structure tests verifying label-input association
- All 17 PhotoCapture tests pass

## Decisions Made

- Label-wrapping pattern chosen because iOS Safari ignores `capture="environment"` on programmatic `.click()` — only native label click (via label association) respects the attribute. This is a well-known iOS Safari limitation.
- `sr-only` class used (not `display:none` or `hidden`) because visually-hidden inputs inside labels still work with label-click association; `display:none` / `hidden` break the association in some browsers.
- No `role="button"` on the labels — they are semantically labels. Screen readers announce their content ("Take Photo" / "Upload from Gallery") as file input labels.
