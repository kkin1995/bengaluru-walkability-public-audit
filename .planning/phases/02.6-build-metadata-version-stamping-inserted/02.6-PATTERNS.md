### `frontend/next.config.mjs` (config, build-time transform)

**Analog:** itself — modify in place.

**Current file** (`frontend/next.config.mjs`, lines 1-18):
```js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: process.env.NEXT_OUTPUT === "standalone" ? "standalone" : undefined,
  eslint: {
    ignoreDuringBuilds: true,
  },
  images: {
    remotePatterns: [
      { protocol: "http", hostname: "**" },
      { protocol: "https", hostname: "**" },
    ],
  },
};

export default nextConfig;
```

**Inject pattern** — add `env` block using `fs` + `JSON.parse` for ESM compatibility (file is `.mjs`, so `require()` is not available by default; use `fs.readFileSync` instead):
```js
import { readFileSync } from "fs";
import { fileURLToPath } from "url";
import { dirname, join } from "path";

const __dirname = dirname(fileURLToPath(import.meta.url));
const { version } = JSON.parse(
  readFileSync(join(__dirname, "package.json"), "utf8")
);

const nextConfig = {
  env: {
    NEXT_PUBLIC_APP_VERSION: version,
  },
  // ... existing keys unchanged
};
```

**Why this approach:** The file uses ES module syntax (`export default`). `require('./package.json')` is CJS-only. The `fs.readFileSync` + `JSON.parse` pattern is the standard ESM equivalent. The `__dirname` shim is needed because `import.meta.url` replaces `__dirname` in ESM.

### `frontend/app/layout.tsx` (layout, conditional render)

**Analog:** `frontend/app/admin/layout.tsx` (Server Component layout pattern) + `frontend/app/admin/components/AdminSidebar.tsx` (pathname-based conditional rendering).

**Current root layout structure** (`frontend/app/layout.tsx`, lines 42-66):
```typescript
export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const fontVars = `${inter.variable} ${jetbrainsMono.variable} ${notoSansKannada.variable}`;
  return (
    <html lang="en" className={fontVars} suppressHydrationWarning>
      <head>...</head>
      <body className="min-h-screen antialiased">{children}</body>
    </html>
  );
}
```

**Conditional footer pattern — two valid approaches:**

**Option A — Client boundary wrapper (usePathname):**
`usePathname` requires a Client Component. The pattern is to extract the conditional render into a small `"use client"` wrapper component rather than making the entire layout a Client Component. This preserves Server Component benefits for the layout itself.

Example from `AdminSidebar.tsx` lines 1-4 and 36-38:
```typescript
// Thin client wrapper — lives at frontend/app/components/FooterBoundary.tsx
"use client";
import { usePathname } from "next/navigation";
import { SiteFooter } from "./SiteFooter";

export function FooterBoundary() {
  const pathname = usePathname();
  if (pathname === "/map") return null;
  return <SiteFooter />;
}
```
Then in the Server Component layout: `<body>...<FooterBoundary /></body>`

**Option B — Route group `(citizen)` layout:**
Create `frontend/app/(citizen)/layout.tsx` wrapping `/`, `/report`, `/success` pages. Move those pages into `(citizen)/` directory. The nested layout renders `<SiteFooter />` unconditionally. The `/map` page stays outside `(citizen)/` in `app/map/`. This avoids any client boundary but requires restructuring the file tree.

**Decision hint from CONTEXT.md (D-02):** Planner decides. Option A has zero file-move cost. Option B is structurally cleaner but requires moving 3 page files.
