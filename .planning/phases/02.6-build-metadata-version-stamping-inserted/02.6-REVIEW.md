# Phase 02.6: Code Review Report

**Reviewed:** 2026-05-25T00:00:00Z
**Depth:** standard
**Files Reviewed:** 6

## Summary

This phase introduces version stamping: `next.config.mjs` reads `version` from `package.json` at build time and injects it as `NEXT_PUBLIC_APP_VERSION`. `config.ts` exports `APP_VERSION` with a safe `"0.0.0"` fallback. `SiteFooter` and `AdminSidebar` consume `APP_VERSION` for display. `FooterBoundary` gates the public footer on the current route. `layout.tsx` wires `FooterBoundary` into the root layout.

The version-stamping mechanism itself is sound. However, two pre-existing bugs in `AdminSidebar.tsx` are now fully in scope because the phase touched that file to add the version badge. One is a functional breakage (logout via `<a>` tag sends GET to a POST-only endpoint), and one is a layout bleed (public `SiteFooter` renders on all `/admin/*` pages because `FooterBoundary` only suppresses `/map`).

## Critical Issues

### CR-01: Sidebar logout uses `<a href>` (GET) against a POST-only endpoint — logout is silently broken

**File:** `frontend/app/admin/components/AdminSidebar.tsx:219` (desktop) and `:27` / `:290` (mobile tab)

**Issue:** Both the desktop sidebar logout icon (`<a href="/api/admin/auth/logout">`, line 219) and the mobile tab-bar logout entry (`href: "/api/admin/auth/logout"`, line 27, rendered at line 290) navigate the browser to that URL, issuing an HTTP GET request. The backend route is registered exclusively as `POST /api/admin/auth/logout` (`backend/src/main.rs:178`). The Next.js proxy at `app/api/admin/[...path]/route.ts` faithfully forwards the request using `request.method`, so the backend receives a GET and returns `405 Method Not Allowed`. The admin cookie is never cleared; the user is not logged out. The correct pattern already exists in `app/admin/lib/adminApi.ts:138-140` (`logout()` calls `POST`), and `profile/page.tsx:164` uses it correctly.

**Fix:**
```tsx
// Replace both <a href="/api/admin/auth/logout"> elements with a <button>
// that calls the existing adminApi.logout() and then redirects.

import { useRouter } from "next/navigation";
import { logout } from "@/app/admin/lib/adminApi";

// inside the component:
const router = useRouter();

async function handleLogout() {
  try {
    await logout();          // POST /api/admin/auth/logout
  } finally {
    router.push("/admin/login");
  }
}

// Desktop sidebar (replace the <a> at line 218-237):
<button
  aria-label="Log out"
  onClick={handleLogout}
  style={{ /* same styles as before; change border:"none" already present */ }}
>
  <Icon name="logout" size={14} aria-hidden={true} />
</button>

// Mobile tab (replace the <a> at line 294-320):
<button
  key="logout"
  onClick={handleLogout}
  style={{ /* same styles */ }}
>
  <Icon name="logout" size={18} aria-hidden={true} />
  <span style={{ fontSize: 9, fontFamily: "var(--font-mono)", fontWeight: 600,
    letterSpacing: "0.06em", textTransform: "uppercase" }}>OUT</span>
</button>
```

### CR-02: Public `SiteFooter` renders on all `/admin/*` pages — `FooterBoundary` only suppresses `/map`

**File:** `frontend/app/components/FooterBoundary.tsx:8`

**Issue:** `FooterBoundary` only suppresses the footer for the exact path `/map`. Because `FooterBoundary` is placed in the root layout (`layout.tsx:64`), it also renders inside every `/admin/*` page. The admin portal wraps content in a `div.admin-portal` with `minHeight:100vh` and `display:flex`, but the public `SiteFooter` ("Namma Daari · v0.1.0") is appended after that div inside the `<body>`, visible below the admin content on every admin page. The mobile bottom tab bar (fixed, `zIndex:1000`) obscures it on mobile, but on desktop the footer is visible and incongruous.

**Fix:**
```tsx
// frontend/app/components/FooterBoundary.tsx
export function FooterBoundary() {
  const pathname = usePathname();
  if (pathname === "/map") return null;
  if (pathname.startsWith("/admin")) return null;   // add this line
  return <SiteFooter />;
}
```

## Warnings

### WR-01: Mobile tab-bar hardcodes `repeat(5, 1fr)` grid but conditionally hides one item — visual gap for reviewers

**File:** `frontend/app/admin/components/AdminSidebar.tsx:276`

**Issue:** `gridTemplateColumns: "repeat(5, 1fr)"` is unconditional. The `MOBILE_TABS` array has 5 entries, but the `users` tab is `roleGated: true` and is `return null`-ed when `!isAdminOrSuper`. A reviewer-role user sees 4 tabs in a 5-column grid, leaving an empty fifth column between "MAP" and "OUT". This creates a visible layout gap.

**Fix:** Drive the column count from the number of actually-rendered tabs, or compute it before render:
```tsx
const visibleMobileTabs = MOBILE_TABS.filter(
  tab => !(tab.roleGated && !isAdminOrSuper)
);

// In the nav style:
gridTemplateColumns: `repeat(${visibleMobileTabs.length}, 1fr)`,

// Then render visibleMobileTabs.map(...) instead of MOBILE_TABS.map(...)
```

### WR-02: `super_admin` role string in `isAdminOrSuper` check is dead code — backend never sends it

**File:** `frontend/app/admin/components/AdminSidebar.tsx:70`

**Issue:**
```tsx
const isAdminOrSuper = role === "admin" || role === "super_admin";
```
The backend's `/api/admin/auth/me` endpoint returns `role: "admin" | "reviewer"` as a DB enum. The `is_super_admin` flag is a separate boolean field. `admin/layout.tsx` reads `user.role ?? "reviewer"` — it never synthesizes a `"super_admin"` string. The `role === "super_admin"` branch can never be true, which means the intent (giving super-admins access to gated items) only works incidentally because super-admins also have `role = "admin"`. If this logic is ever copied to a context that uses `is_super_admin` to override role, the mismatch will cause a real access control bug.

**Fix:** Either derive the `role` prop from `is_super_admin` in the layout, or change the check to match reality:
```tsx
// Option A: update admin/layout.tsx to synthesize the role string
const role = user.is_super_admin ? "super_admin" : (user.role ?? "reviewer");

// Option B: update AdminSidebar to accept a boolean prop instead
interface AdminSidebarProps {
  role: string;
  isSuperAdmin: boolean;
}
const isAdminOrSuper = role === "admin" || isSuperAdmin;
```

### WR-03: Duplicate `<link rel="manifest">` in rendered HTML

**File:** `frontend/app/layout.tsx:33` and `frontend/app/layout.tsx:52`

**Issue:** The `manifest` field in the Next.js `metadata` export (line 33) causes Next.js to automatically inject a `<link rel="manifest" href="/manifest.json">` tag. Line 52 explicitly adds an identical `<link rel="manifest" href="/manifest.json">` inside `<head>`. The rendered HTML will contain two identical manifest link tags. While browsers tolerate duplicates, it signals a misunderstanding of the metadata API, wastes a resource hint slot, and may confuse PWA tooling.

**Fix:** Remove the explicit `<link>` on line 52; the `metadata.manifest` entry handles it:
```tsx
// Remove this line from the <head> block:
<link rel="manifest" href="/manifest.json" />
// The metadata export at line 33 already covers it.
```

## Info

### IN-01: Both nav landmarks share the same `aria-label` while both remain in the accessibility tree

**File:** `frontend/app/admin/components/AdminSidebar.tsx:75` and `:272`

**Issue:** The desktop sidebar (`line 75`) and the mobile tab bar (`line 272`) both carry `aria-label="Admin navigation"` and `role="navigation"`. CSS `display:none` does NOT remove elements from the accessibility tree. Screen readers encounter two navigation landmarks with identical labels simultaneously, violating WCAG 2.4.1 best practices for distinct landmark labels. The hidden nav's contents are also traversable via screen reader virtual cursor.

**Fix:** Add `aria-hidden="true"` to whichever nav is currently hidden, toggled with `isDesktop`:
```tsx
// Desktop nav:
aria-hidden={!isDesktop}

// Mobile nav:
aria-hidden={isDesktop}
```

### IN-02: Wildcard `remotePatterns` in `next/image` config allows proxying images from any host

**File:** `frontend/next.config.mjs:23-26`

**Issue:**
```js
images: {
  remotePatterns: [
    { protocol: "http", hostname: "**" },
    { protocol: "https", hostname: "**" },
  ],
},
```
This permits Next.js's `<Image>` component to optimise and proxy images from any URL on the internet. If any page renders user-supplied URLs via `<Image>`, the Next.js image endpoint becomes an open proxy (SSRF vector) that can be used to fetch and serve arbitrary resources through the application's origin. Restrict to the actual domains used (backend uploads and any known CDN).

**Fix:**
```js
images: {
  remotePatterns: [
    // Local/Docker backend
    { protocol: "http",  hostname: "localhost" },
    { protocol: "http",  hostname: "backend"   },
    // Production backend
    { protocol: "https", hostname: "walkability-api.up.railway.app" },
    // Staging
    { protocol: "https", hostname: "staging.nammadaari.com" },
  ],
},
```
