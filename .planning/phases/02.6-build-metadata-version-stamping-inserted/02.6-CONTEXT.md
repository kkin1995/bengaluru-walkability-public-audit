# Phase 02.6: Build Metadata & Version Stamping - Context

**Gathered:** 2026-05-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Inject the `package.json` version into two UI surfaces at build time via `NEXT_PUBLIC_APP_VERSION`:
1. **Citizen-facing site** — a new `SiteFooter` component shown on non-map pages (/, /report, /success)
2. **Admin sidebar** — replace the hardcoded `v2.4.1` string in `AdminSidebar.tsx` with the env var

`NEXT_PUBLIC_APP_VERSION` is populated from `package.json` version in `next.config.mjs` so bumping `package.json` auto-updates both surfaces on the next deploy with no other file changes.

</domain>

<decisions>
## Implementation Decisions

### Citizen Footer Scope
- **D-01:** The version footer appears on **non-map pages only**: `/`, `/report`, `/success`. The `/map` page is full-screen Leaflet with fixed-position floating controls (back button, filter strip, Report CTA) — a footer at page bottom would collide with the Report CTA.
- **D-02:** Implementation: conditional in root layout (`app/layout.tsx`) using a pathname check (`pathname !== '/map'`). If the check cost is a concern, a layout group (`(citizen)`) wrapping non-map pages is an acceptable alternative — planner decides which is cleaner.

### Footer Visual Design
- **D-03:** Thin full-width footer bar: full-width border-top, `--font-mono` typeface, `--muted` color, small font size (11–12px). Mirrors the admin sidebar brand mark aesthetic. Padding must include `safe-area-inset-bottom` for iOS notch.
- **D-04:** The component is named `SiteFooter` and lives in `frontend/app/components/`. It reads from `frontend/app/lib/config.ts` (not `process.env.NEXT_PUBLIC_APP_VERSION` directly — per CLAUDE.md config rule).
- **D-05:** Styling uses CSS custom properties via inline `style` objects only — no Tailwind (established pattern from Phase 02.3.1).

### Version String Format
- **D-06:** Citizen footer displays: **`Namma Daari · v{version}`** (e.g. `Namma Daari · v0.1.0`). Brand name + semver.
- **D-07:** Admin sidebar displays: **`BENGALURU · v{version}`** — the existing text `BENGALURU · v2.4.1` is replaced; only the version part changes, the brand prefix stays.
- **D-08:** `config.ts` exports `export const APP_VERSION = process.env.NEXT_PUBLIC_APP_VERSION ?? "0.0.0"`. The `0.0.0` fallback is for local dev without the env var set.
- **D-09:** `next.config.mjs` injects the env var: `env: { NEXT_PUBLIC_APP_VERSION: require('./package.json').version }` (or `JSON.parse(fs.readFileSync('./package.json')).version` for ESM compatibility).

### Version Bump Process
- **D-10** [informational]**:** No CI automation for version bumping in this phase. Bumping is manual: `npm version patch|minor|major` in `frontend/` (or direct edit of `package.json`). The ROADMAP already states "bumping `package.json` version automatically updates both UI surfaces on the next deploy" — this is the full contract.

### Claude's Discretion
- Exact CSS values for footer height, padding, and font-size — follow the design system tokens (`--font-mono`, `--muted`, etc.) and match the visual weight of the admin sidebar brand string
- Whether to use a layout route group `(citizen)` or a pathname conditional for the non-map exclusion — planner picks the cleaner approach
- Whether `SiteFooter` is a Server Component or Client Component — it needs no interactivity, so Server Component is the natural choice

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `frontend/app/lib/config.ts` — Pattern established: export env vars as named constants; `APP_VERSION` follows the same pattern as `API_BASE_URL`
- `frontend/app/admin/components/AdminSidebar.tsx` — Brand mark block already has the right structure: `WLK.CONSOLE` + `BENGALURU · v2.4.1`; only the version string literal needs replacing

### Established Patterns
- **Inline styles, no Tailwind** — every rewritten/new component since 02.3.1 uses `style={{ ... }}` with CSS custom properties; `SiteFooter` must follow this
- **Config rule** — CLAUDE.md explicitly forbids `process.env.*` in component files; must go through `config.ts`
- **`safe-area-inset-bottom`** — needed for iOS notch; already used in mobile bottom tab bar of AdminSidebar as precedent

### Integration Points
- `next.config.mjs` → `NEXT_PUBLIC_APP_VERSION` env var → `config.ts` `APP_VERSION` export → consumed by `SiteFooter.tsx` and `AdminSidebar.tsx`
- Root layout (`app/layout.tsx`) needs to conditionally render `SiteFooter` — requires pathname access (use `usePathname` in a client boundary, or check via layout route groups)

</code_context>

## Specific Ideas

- Admin sidebar brand: `BENGALURU · v{APP_VERSION}` — only the version number changes, prefix stays exactly as-is
- Citizen footer: `Namma Daari · v{APP_VERSION}` — full-width bar, mono font, muted color, border-top separator

</specifics>

<deferred>
## Deferred Ideas

- **Git SHA in version string** (`v0.1.0 (abc1234)`) — useful for debugging deployed commits but adds build complexity; deferred to a future observability phase if needed
- **Environment tag** (`v0.1.0 (staging)`) — would help GBA distinguish staging vs. prod during pilot; deferred since Railway staging is decommissioned (self-hosted now) and the need is low
- **Automated version bump in CI** — could auto-increment `package.json` on release; deferred to post-GBA-handoff when a formal release process is established
- **Footer content beyond version** — copyright notice, privacy policy link, open-source attribution; deferred as out of scope for this phase

</deferred>
