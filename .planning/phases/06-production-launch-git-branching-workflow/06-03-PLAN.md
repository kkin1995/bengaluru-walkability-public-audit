    alongside docker-compose.yml (the base) when deploying the staging stack. It must NOT
    redefine named volumes from docker-compose.yml (postgres_data, uploads) — it only adds
    its own staging volumes.

    SERVICE nginx (the critical difference from production):
    - Override ports to publish staging nginx on HOST port 3011 mapped to container port 80:
      ports: ["3011:80"]
      This replaces the production nginx ports: ["80:80"] from docker-compose.yml.
      The Cloudflare Tunnel second ingress rule points to http://localhost:3011, which reaches
      this nginx container. Production nginx continues to own port 80.
    - Override depends_on to match the server pattern (frontend required: false):
      depends_on:
        backend:
          condition: service_healthy
        frontend:
          condition: service_started
          required: false
    - Override volumes to mount the staging nginx config:
      volumes: [./nginx/nginx.staging-server.conf:/etc/nginx/conf.d/default.conf:ro]

    SERVICE backend (override environment only):
    - Add to environment block (do NOT copy all environment vars from docker-compose.yml —
      only override what differs from the base):
      PORT: "3011"
      PUBLIC_URL: https://staging-api.nammadaari.com
      CORS_ORIGIN is already set via GitHub Environment secret — do not hardcode it here.
    - Note: The DATABASE_URL in the base file uses port 5432 and the db service name. For
      staging, the db service runs on the same Docker internal network, so port 5432 is still
      correct for container-to-container communication (the 5433 port is only the HOST binding
      for external access — but external DB access is not needed). Leave DATABASE_URL as-is.
    - Add expose: ["3011"] to document the staging backend port.
    - Override healthcheck to hit port 3011:
      healthcheck:
        test: ["CMD-SHELL", "curl -f http://localhost:3011/health || exit 1"]
        interval: 10s
        timeout: 5s
        start_period: 30s
        retries: 3

    SERVICE db (optional — only if PostgreSQL host port exposure is needed for debugging):
    - If external DB access for staging debugging is desired, add:
      ports: ["5433:5432"]
      But this is optional — omit if not needed, as the backend connects via Docker network.
      Given solo developer workflow (D-06), include it for operational convenience.

    SERVICE frontend:
    - Park behind profile to prevent auto-start:
      profiles: [frontend-only]

    VOLUMES section:
    - Declare only the staging-specific volumes (NOT the production volumes):
      volumes:
        postgres_staging_data:
        uploads_staging:
    - The base docker-compose.yml already declares postgres_data and uploads; do not repeat them.
    - However, the base file's backend service uses volume uploads:/app/uploads. The staging
      override must change this to uploads_staging. Add to backend service:
      volumes: [uploads_staging:/app/uploads]
    - The base file's db service uses volume postgres_data:/var/lib/postgresql/data. The staging
      override must change this to postgres_staging_data. Add to db service:
      volumes: [postgres_staging_data:/var/lib/postgresql/data]

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Staging nginx (port 3011) → staging backend (port 3011) | Internal Docker network; no host exposure of backend |
| Host port 3011 → staging nginx | Cloudflare Tunnel second ingress routes staging-api.nammadaari.com to localhost:3011 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-03-01 | Spoofing | staging nginx accidentally using production volumes | mitigate | D-14: distinct volume names (postgres_staging_data, uploads_staging) prevent collision; volumes are daemon-global and sharing would merge data |
| T-06-03-02 | Spoofing | production nginx port conflict with staging nginx | mitigate | Staging nginx publishes 3011:80 (not 80:80) — Pitfall 1 from RESEARCH.md explicitly avoids this |
| T-06-03-03 | Information Disclosure | PUBLIC_URL defaulting to http://localhost on staging | mitigate | Pitfall 3 from RESEARCH.md: PUBLIC_URL explicitly set to https://staging-api.nammadaari.com in staging Compose override |
| T-06-03-04 | Tampering | staging nginx config sharing includes with production | mitigate | D-15: files are independent copies, no shared includes |
| T-06-03-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in this plan |
</threat_model>
