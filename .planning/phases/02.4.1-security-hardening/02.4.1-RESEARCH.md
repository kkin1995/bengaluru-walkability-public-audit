Phase 02.4.1 is a pre-launch security and operational hardening pass across three domains: application security fixes in the Rust/Axum backend and nginx, backup automation using systemd timers and Docker volume inspection, and documentation (secret rotation + restore procedures) appended to `DEPLOYMENT.md`. There are no new external package dependencies — all changes modify existing code, config, or add shell/systemd unit files.

The application security work is highly targeted. Three surgical changes: a JPEG magic bytes check in the `create_report` handler (two bytes, one `if`), a cookie attribute fix in `admin_logout` (three lines mirrored from the login handler), and two nginx `add_header` directives. The tech debt cleanup is mechanical — removing `TODO: implement` docstring prefixes from functions that are already implemented, and lifting four bounding box constants to module level.

The operational security work (backup automation) is the most structurally novel. It introduces a `backup/` directory with a shell script and two systemd unit files. The shell script uses `docker run --rm` to invoke `pg_dump` and `tar` inside temporary containers, which avoids any host-level PostgreSQL tooling dependency. The systemd timer pattern is already used in this project for `cloudflared`, so the pattern is known and consistent.

**Primary recommendation:** Three plans — (1) application security fixes + nginx, (2) backup automation + systemd units, (3) tech debt cleanup + docs. This grouping separates code changes from operational infrastructure from documentation, enabling clean granular commits per the project's `granular-commits` skill.

## Pattern 1: JPEG Magic Bytes Check

**What:** Check the first two bytes of the uploaded image for the JPEG SOI (Start of Image) marker `0xFF 0xD8` before any other processing. Return HTTP 400 on mismatch.

**When to use:** At the handler level, in the same guard sequence as existing honeypot and bbox checks. Must come AFTER multipart field extraction (needs bytes) and BEFORE `strip_exif`.

**Placement in `create_report`:** After the existing required-field checks (image_bytes empty check), before the SHA256 hash block. The CONTEXT.md says "before any processing" but practically it must come after the multipart loop collects `image_bytes`.

```rust
// Source: project codebase — mirrors existing AppError::BadRequest pattern
// in backend/src/handlers/reports.rs after image_bytes empty check
if req.image_bytes.len() < 2
    || req.image_bytes[0] != 0xFF
    || req.image_bytes[1] != 0xD8
{
    return Err(AppError::BadRequest(
        "Only JPEG images are accepted".into(),
    ));
}
```

[VERIFIED: codebase inspection — `AppError::BadRequest` maps to HTTP 400 in `errors.rs`]

**Why BEFORE strip_exif:** `strip_exif` calls `img_parts::jpeg::Jpeg::from_bytes()` which silently falls back to returning original bytes on parse error — a non-JPEG file would be written to disk verbatim as a `.jpg`. The magic bytes check must be an explicit rejection, not a silent fallback path. [VERIFIED: codebase inspection — `strip_exif` in `reports.rs:316-326`]

**Test pattern:** Pure unit test (no I/O). Add to `mod tests` in `reports.rs`:

```rust
// Source: mirrors existing honeypot/bbox unit test pattern in reports.rs
fn is_jpeg(bytes: &[u8]) -> bool {
    bytes.len() >= 2 && bytes[0] == 0xFF && bytes[1] == 0xD8
}

#[test]
fn jpeg_magic_bytes_accepted() {
    assert!(is_jpeg(&[0xFF, 0xD8, 0xFF, 0xE0, 0x00]));
}

#[test]
fn svg_rejected_not_jpeg() {
    assert!(!is_jpeg(b"<?xml version=\"1.0\""));
}

#[test]
fn png_rejected_not_jpeg() {
    assert!(!is_jpeg(&[0x89, 0x50, 0x4E, 0x47]));
}

#[test]
fn empty_bytes_rejected() {
    assert!(!is_jpeg(&[]));
}

#[test]
fn single_byte_rejected() {
    assert!(!is_jpeg(&[0xFF]));
}
```

## Pattern 2: Logout Cookie Fix

**What:** The `admin_logout` handler builds a removal cookie that lacks `SameSite=None` and `Secure`. Browsers use cookie attribute matching when deciding which cookie to clear on cross-domain requests. The login cookie has `SameSite=None` + `Secure`; the removal cookie must match.

**Current logout handler (broken):**
```rust
// backend/src/handlers/admin.rs:342-352
pub async fn admin_logout(jar: CookieJar) -> impl axum::response::IntoResponse {
    let removal = axum_extra::extract::cookie::Cookie::build(("admin_token", ""))
        .path("/")
        .http_only(true)
        .build();
    tracing::info!("Admin logout");
    (StatusCode::OK, jar.remove(removal))
}
```

**Fixed pattern (mirrors login handler):**
```rust
// Source: mirrors admin_login cookie construction at admin.rs:311-325
pub async fn admin_logout(jar: CookieJar) -> impl axum::response::IntoResponse {
    let cookie_secure = std::env::var("COOKIE_SECURE")
        .map(|v| v == "true" || v == "1")
        .unwrap_or(false);

    let mut removal = axum_extra::extract::cookie::Cookie::build(("admin_token", ""))
        .path("/")
        .http_only(true)
        .same_site(axum_extra::extract::cookie::SameSite::None)
        .build();
    if cookie_secure {
        removal.set_secure(true);
    }

    tracing::info!("Admin logout");
    (StatusCode::OK, jar.remove(removal))
}
```

[VERIFIED: codebase inspection — `cookie` crate 0.18.1 in Cargo.lock; `axum-extra` 0.9.6; `CookieBuilder.same_site()` is available in cookie 0.18]
[VERIFIED: codebase — login handler at `admin.rs:311-325` uses identical `std::env::var("COOKIE_SECURE")` pattern]

**Key implementation detail:** `Cookie::build()` in cookie 0.18 returns a `CookieBuilder`. The builder has `.same_site()` as a builder method. However, `.secure()` as a builder method sets it unconditionally. To mirror the conditional `if cookie_secure { cookie.set_secure(true); }` pattern from login, build first with `.build()`, then call `.set_secure(true)` conditionally as a setter. Alternatively, use `if cookie_secure { builder = builder.secure(true); }` before `.build()`. Either approach compiles.

## Pattern 3: nginx Content-Type Override

**What:** Add `add_header Content-Type 'image/jpeg' always;` to the `/uploads/` location block in both nginx config files.

**Where:** `nginx/nginx.conf` (local dev / full-stack) and `nginx/nginx.server.conf` (production self-hosted). The `/uploads/` block already has `expires 30d` and `add_header Cache-Control` — the Content-Type line appends to the same block.

**Current block (both files):**
```nginx
location /uploads/ {
    proxy_pass http://backend;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_cache_bypass $http_upgrade;
    expires 30d;
    add_header Cache-Control "public, no-transform";
}
```

**Fixed (add one line):**
```nginx
location /uploads/ {
    proxy_pass http://backend;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_cache_bypass $http_upgrade;
    expires 30d;
    add_header Cache-Control "public, no-transform";
    add_header Content-Type 'image/jpeg' always;
}
```

[VERIFIED: codebase inspection — `nginx/nginx.conf:129-137` and `nginx/nginx.server.conf:117-125`]

**The `always` flag:** Without `always`, nginx only adds the header on 2xx responses. `always` adds it on all responses including 3xx/4xx which is correct for a security override. [ASSUMED — nginx `add_header always` behavior is training knowledge; confirmed as standard practice]

## Pattern 4: Backup Script + Systemd Timer

**What:** A shell script invoked by a systemd service, scheduled by a weekly systemd timer.

**PostgreSQL backup via docker:**
```bash
# Source: Docker documentation pattern for pg_dump without host pg_dump
# Volume name 'postgres_data' confirmed from docker-compose.yml:128
# POSTGRES_USER and POSTGRES_PASSWORD loaded from .env on the host
docker run --rm \
    -v postgres_data:/var/lib/postgresql/data \
    -v /data/backups/db:/backup \
    --env-file /path/to/.env \
    postgres:alpine \
    pg_dump \
        -U "${POSTGRES_USER:-walkability}" \
        -d "${POSTGRES_DB:-walkability}" \
        -h localhost \
        -f /backup/${DATE}.sql.gz \
        --compress=9
```

**Important:** `pg_dump` connects via a TCP socket. The Dockerized approach that works reliably is to run `pg_dump` INSIDE a container that connects to the running `db` container over the Docker network — NOT via a volume-only approach. The correct pattern for this project:

```bash
# Source: [ASSUMED — standard Docker pg_dump pattern]
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="/data/backups/db/walkability_${DATE}.sql.gz"

docker run --rm \
    --network walkability-public-audit_default \
    -v /data/backups/db:/backup \
    postgres:alpine \
    sh -c "pg_dump -U walkability -h db walkability | gzip > /backup/walkability_${DATE}.sql.gz"
```

**Docker network name:** The project's docker-compose.yml does not define a named network — Docker Compose auto-generates the network name from the directory name + `_default`. The actual network name on the production server depends on the directory it was cloned into. The backup script must detect or parameterize this. [ASSUMED — Docker Compose default network naming; planner should verify actual network name on the server]

**Alternative approach (simpler, no network config needed):**
```bash
# Run pg_dump directly inside the running db container
docker exec walkability-public-audit_db_1 \
    pg_dump -U walkability walkability | gzip > "$BACKUP_FILE"
```
This avoids the network naming problem entirely. Container name follows Docker Compose convention: `<project>_<service>_<replica>`. [ASSUMED — container naming convention]

**Recommended approach:** `docker exec` on the running `db` container is simpler and avoids network configuration issues. The backup script should use `docker exec $(docker compose -f /path/to/docker-compose.yml ps -q db) pg_dump ...` to get the container ID dynamically rather than hardcoding a container name.

**Uploads volume backup:**
```bash
# Source: [ASSUMED — standard Docker volume backup pattern]
UPLOADS_FILE="/data/backups/uploads/uploads_${DATE}.tar.gz"

docker run --rm \
    -v uploads:/data:ro \
    -v /data/backups/uploads:/backup \

```

## Common Pitfalls

### Pitfall 1: Magic Bytes Check After strip_exif

**What goes wrong:** Placing the JPEG check AFTER `strip_exif` means a non-JPEG file has already been processed (or passed through silently). Also, `strip_exif` silently returns the original bytes on parse failure — so a non-JPEG would be written to disk as a `.jpg` extension file regardless.

**Why it happens:** The natural place in the handler to add a check is "near the processing code" which is the `strip_exif` call at line 249. But the bytes must be validated BEFORE any processing.

**How to avoid:** Place magic bytes check immediately after the `image_bytes.is_empty()` check (line 180), before the SHA256 block (line 193).

**Warning signs:** If tests pass a non-JPEG file through strip_exif without hitting the 400 error, check the ordering.

---

### Pitfall 2: Logout Cookie Attribute Mismatch

**What goes wrong:** Browser silently fails to clear the cross-domain `admin_token` cookie if the removal cookie's `SameSite` attribute differs from the session cookie. Admin users click "Logout" but are still authenticated on next page load.

**Why it happens:** `CookieJar::remove()` sets `Max-Age=0` and an expired date but does NOT automatically copy attributes from any existing cookie. The removal cookie must have the same `SameSite`, `Secure`, `Path`, and `Domain` as the original.

**How to avoid:** Mirror the login handler's cookie construction exactly. Read `COOKIE_SECURE` env var in logout handler, set `SameSite::None`, set `Secure` conditionally.

**Warning signs:** After the fix, test logout in a cross-domain browser session (Vercel frontend → Cloudflare tunnel backend). A successful logout should clear the `admin_token` from browser dev tools → Application → Cookies.

---

### Pitfall 3: Docker Network Name for Backup pg_dump

**What goes wrong:** `docker run --rm --network <name> postgres:alpine pg_dump -h db ...` fails because the Docker Compose network name is auto-generated from the project directory name (e.g., `bengaluru-walkability-public-audit_default`), and the backup script hardcodes a wrong name.

**Why it happens:** Docker Compose auto-generates network names. The project directory on the production server may differ from the repo name.

**How to avoid:** Use `docker exec` on the running `db` container instead of running a separate container on the network. `docker exec $(docker compose -f /path/to/docker-compose.yml ps -q db) pg_dump ...` is more robust.

**Warning signs:** `docker run` exits immediately with a network connection error; `pg_dump` output file is 0 bytes or missing.

---

### Pitfall 4: nginx `add_header` Inheritance

**What goes wrong:** nginx `add_header` directives are NOT inherited from parent blocks into child blocks that define their own `add_header`. The `/uploads/` location block already has `add_header Cache-Control "public, no-transform"`. Adding `add_header Content-Type 'image/jpeg' always;` in the same location block works correctly because both directives are in the SAME block.

**Why it happens:** If someone tries to add the Content-Type header in a parent context (e.g., the `server` block), it won't apply to the `/uploads/` block because the block has its own `add_header`.

**How to avoid:** Add the `add_header Content-Type` directive INSIDE the `/uploads/` location block, not in a parent context.

**Warning signs:** Response headers don't include `Content-Type: image/jpeg` when testing with `curl -I <tunnel-url>/uploads/test.jpg`.

---

### Pitfall 5: Systemd Timer `Persistent=true`

**What goes wrong:** Without `Persistent=true`, if the server is off during the scheduled weekly run, the backup simply skips that week. This can leave gaps in backup history after reboots/maintenance.

**Why it happens:** Default systemd timer behavior does not catch up missed runs.

**How to avoid:** Include `Persistent=true` in the `.timer` unit. With this flag, systemd runs the timer immediately on next startup if the last scheduled run was missed.

**Warning signs:** `systemctl list-timers walkability-backup.timer` shows `LAST` as N/A after a reboot cycle.

---

### Pitfall 6: bounding box constant visibility after deduplication

**What goes wrong:** After moving constants to module level, the test module can't access them unless it uses `super::CONSTANT_NAME` or has `use super::*;`.

**Why it happens:** The test module (`mod tests`) is a child module. Module-level items in the parent are accessible via `super::`.

**How to avoid:** In the test module, reference as `super::LAT_MIN` etc., or add `use super::*;` at the top of `mod tests`. The test assertion messages use `LAT_MIN, LNG_MIN` in format strings — if the test module has `use super::*;`, the names resolve directly.

**Warning signs:** `cargo test` fails with "use of undeclared..." after the refactor.

/// Returns true when the bytes have a valid JPEG SOI marker (0xFF 0xD8).
/// Legitimate JPEG files always start with these two bytes.
fn is_jpeg(bytes: &[u8]) -> bool {
    bytes.len() >= 2 && bytes[0] == 0xFF && bytes[1] == 0xD8
}

## Open Questions

1. **Docker network name for backup pg_dump**
   - What we know: Docker Compose auto-names networks from directory name; `docker exec` approach avoids this entirely
   - What's unclear: The production directory name on the server
   - Recommendation: Use `docker exec` approach in the backup script; document both options

2. **nginx proxy_hide_header for Content-Type override**
   - What we know: `add_header Content-Type 'image/jpeg' always;` adds the header. It may not REPLACE the existing Content-Type set by the backend's ServeDir.
   - What's unclear: Whether nginx's `add_header` overrides a proxied upstream's Content-Type or appends alongside it
   - Recommendation: Plan should include a verification step: `curl -I <url>/uploads/<filename>` and confirm only one Content-Type header appears. If both appear, add `proxy_hide_header Content-Type;` before the `add_header` line.

3. **Uptime monitoring service selection**
   - What we know: `/health` returns `{"status":"ok"}` on HTTP 200; both UptimeRobot and Cloudflare Health Checks support HTTP keyword monitoring
   - What's unclear: Which is easier for this specific Cloudflare tunnel setup
   - Recommendation: UptimeRobot free tier is simpler to configure (no Cloudflare Pro required); Cloudflare health checks may require a paid plan for custom alerting
