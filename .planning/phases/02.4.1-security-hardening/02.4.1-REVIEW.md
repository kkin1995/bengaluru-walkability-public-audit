# Phase 02.4.1: Code Review Report

**Reviewed:** 2026-05-21T00:00:00Z
**Depth:** standard
**Files Reviewed:** 24
**Status:** issues_found

## Summary

This phase implements five security-hardening changes: JPEG magic-byte validation, admin logout cookie hardening, nginx Content-Type override for `/uploads/`, a weekly backup script, and supporting systemd units. The JPEG guard and cookie attributes are functionally correct, but there are four critical issues: the logout cookie is never actually delivered to the client (the `jar.remove()` call is broken by the `SameSite=None` cookie attributes), the backup script runs as root with world-readable output files, the backup script embeds a hardcoded absolute path that ties the project to a specific user's home directory, and the `pg_dump` command leaks the database password via environment exposure. Several additional warnings exist around cookie Max-Age omission, missing `Secure` flag on the removal cookie, an EXIF fallback that admits non-JPEG bytes on parse failure, backup file retention applying to all `.tar.gz` files in the backup root, and the nginx Content-Type override preventing legitimate varied-format uploads in the future.

## Critical Issues

### CR-01: `admin_logout` — removal cookie never clears in the browser (`SameSite=None` without `Secure=true` is always rejected)

**File:** `backend/src/handlers/admin.rs:336-346`

**Issue:** `axum_extra`'s `CookieJar::remove` works by setting `Max-Age=0` on the cookie it is given. However, the code builds the removal cookie with `SameSite::None` but only conditionally sets `Secure`. In every environment where `COOKIE_SECURE` is not `"true"` (local dev, any HTTP environment), the browser will **refuse to store** a `SameSite=None` cookie that lacks `Secure=true` per RFC 6265bis. The removal cookie is dropped silently by the browser, so the `admin_token` cookie is never actually cleared and the user remains authenticated after clicking logout.

This is the mirror problem: `admin_login` sets `SameSite::None` AND conditionally sets `Secure` (only when `COOKIE_SECURE=true`). In production this is correct. But for the removal cookie, not setting `Secure` in the same conditions means the removal never reaches the browser.

Additionally, the removal cookie is missing `Max-Age=0` being explicitly set — the code relies on `jar.remove()` to do that, but `jar.remove()` uses the cookie object passed to it as the *identity* for removal and sets `Max-Age=0` on the matched entry in the jar. If the removal cookie's attributes do not match the stored cookie's attributes exactly, some browser/jar implementations will not recognize it as the same cookie. The `axum_extra` `CookieJar` relies on cookie name + path to identify the cookie to remove; the `Max-Age=0` is set automatically. The primary bug remains: the browser rejects `SameSite=None` without `Secure`.

**Fix:** Set `Secure=true` on the removal cookie unconditionally whenever `SameSite=None` is used. Since `SameSite=None` is always set, `Secure` must also always be set:

```rust
pub async fn admin_logout(jar: CookieJar) -> impl axum::response::IntoResponse {
    let cookie_secure = std::env::var("COOKIE_SECURE")
        .map(|v| v == "true" || v == "1")
        .unwrap_or(false);

    let mut removal = axum_extra::extract::cookie::Cookie::build(("admin_token", ""))
        .path("/")
        .http_only(true)
        .same_site(axum_extra::extract::cookie::SameSite::None)
        .build();
    // SameSite=None REQUIRES Secure; set it unconditionally when SameSite=None is used.
    // Without Secure, the browser rejects SameSite=None cookies entirely and the
    // logout never takes effect.
    if cookie_secure {
        removal.set_secure(true);
    } else {
        // In HTTP-only dev environments, fall back to SameSite=Lax so the
        // removal cookie is accepted by the browser.
        removal.set_same_site(axum_extra::extract::cookie::SameSite::Lax);
    }

    tracing::info!("Admin logout");
    (StatusCode::OK, jar.remove(removal))
}
```

### CR-02: `backup.sh` — backup files created with world-readable permissions (data exfiltration risk)

**File:** `backup/backup.sh:24` and `backup/backup.sh:41-45`

**Issue:** The script never sets a `umask` before writing backup files. On most Linux systems the default umask is `0022`, which makes files mode `0644` — world-readable. The PostgreSQL dump (`walkability_<date>.sql.gz`) and uploads archive (`uploads_<date>.tar.gz`) will be readable by any local user on the system. The SQL dump contains all database contents including `admin_users` rows (password hashes), submitter contacts, and all report data.

```bash
# Line 24 — no umask set before this write:
docker exec "$DB_CONTAINER" pg_dump -U walkability walkability | gzip > "$DB_BACKUP_FILE"
```

**Fix:** Add `umask 0077` at the top of the script (immediately after `set -euo pipefail`) so all created files are mode `0600` and all created directories are mode `0700`:

```bash
set -euo pipefail
umask 0077   # all backup files and dirs: owner-only read/write
```

### CR-03: `backup.sh` — hardcoded absolute path ties script to a specific user's home directory

**File:** `backup/backup.sh:5-6`

**Issue:** The compose file paths are hardcoded to `/home/karankinariwala/bengaluru-walkability-public-audit/...`. This is a single-point-of-failure: if the repository is cloned to any other location, or if the `gh-runner` or another system user runs the script, it will fail with "No such file or directory". The systemd service unit (`walkability-backup.service`) runs as `User=root`, so root would need the path to resolve correctly. More seriously, the path encodes a specific username, making the configuration non-portable and failing silently in disaster-recovery scenarios (when the original machine is gone and the repo is cloned to a new machine under a different user).

**Fix:** Derive the repository root from the script's own location:

```bash
REPO_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
COMPOSE_FILE="${REPO_ROOT}/docker-compose.yml"
COMPOSE_SERVER_FILE="${REPO_ROOT}/docker-compose.server.yml"
```

### CR-04: `backup.sh` — `pg_dump` password potentially exposed; no `PGPASSWORD` isolation

**File:** `backup/backup.sh:24`

**Issue:** The `pg_dump` call inside the container uses `-U walkability` without a password argument. It relies on the PostgreSQL container's internal `trust` or `md5` auth configuration. If the container uses `md5` authentication (which it does in production for security), `pg_dump` will either fail or prompt for a password interactively, causing the script to hang. If a `.pgpass` file or `PGPASSWORD` environment variable is pre-set in the container, the password is visible to any process inspecting `/proc/<pid>/environ` on the host during the `docker exec`. More critically, if the operator later adds `-W password` or `--password=...` to the command line, it becomes visible in `ps aux` output — a common mistake with backup scripts.

The backup runs as `root` via systemd, which makes all these environment variables visible to root processes. However, the script also does nothing to pass the `POSTGRES_PASSWORD` from the `.env` file to the container in a safe way.

**Fix:** Use `PGPASSWORD` scoped only to the `docker exec` call, reading it from a secrets file or the `.env`:

```bash
# Read password from .env file — never pass on the command line
POSTGRES_PASSWORD=$(grep '^POSTGRES_PASSWORD=' "${REPO_ROOT}/.env" | cut -d= -f2-)
DB_BACKUP_FILE="${DB_BACKUP_DIR}/walkability_${DATE}.sql.gz"
docker exec -e "PGPASSWORD=${POSTGRES_PASSWORD}" "$DB_CONTAINER" \
    pg_dump -U walkability walkability | gzip > "$DB_BACKUP_FILE"
unset POSTGRES_PASSWORD
```

## Warnings

### WR-01: `admin_logout` removal cookie missing `Max-Age` — depends on jar implementation

**File:** `backend/src/handlers/admin.rs:336-346`

**Issue:** The `admin_login` handler sets `cookie.set_max_age(time::Duration::seconds(jwt_session_hours * 3600))` so the browser discards the cookie at expiry. The `admin_logout` handler does not set `max_age(time::Duration::ZERO)` on the removal cookie before passing it to `jar.remove()`. The `axum_extra` `CookieJar::remove()` does set `Max-Age=0` internally, but only for cookies in the jar that match the removal cookie's name + path. If the jar does not contain a matching cookie (e.g., the request arrived without a cookie, or the name lookup failed), no `Max-Age=0` header is emitted in the response, meaning the browser's existing cookie survives. Explicitly setting `max_age(time::Duration::ZERO)` on the removal cookie ensures the `Set-Cookie: admin_token=; Max-Age=0` header is always present in the response regardless of jar state.

**Fix:**
```rust
let mut removal = axum_extra::extract::cookie::Cookie::build(("admin_token", ""))
    .path("/")
    .http_only(true)
    .max_age(time::Duration::ZERO)   // explicit expiry: belt + suspenders
    .same_site(axum_extra::extract::cookie::SameSite::None)
    .build();
```

### WR-02: `strip_exif` fallback silently passes non-JPEG bytes to disk after `is_jpeg` guard

**File:** `backend/src/handlers/reports.rs:343-353`

**Issue:** The `strip_exif` function falls back to `bytes.to_vec()` when `Jpeg::from_bytes` fails:

```rust
Err(_) => bytes.to_vec(),
```

The `is_jpeg` guard on line 205 checks the SOI magic bytes `0xFF 0xD8` before calling `strip_exif`. A valid JPEG file will always parse successfully with `img-parts`. However, a carefully crafted file that starts with `0xFF 0xD8` but is otherwise malformed (e.g., a truncated JPEG, or a polyglot file that passes the two-byte SOI check) will pass `is_jpeg`, reach `strip_exif`, fail `Jpeg::from_bytes`, and be written to disk verbatim — including any embedded content (JavaScript in XMP metadata, HTML in comments, etc.). The SOI guard is necessary but not sufficient; the fallback re-opens the attack surface it was intended to close.

**Fix:** Return an error instead of the original bytes on parse failure:

```rust
fn strip_exif(bytes: &[u8]) -> Result<Vec<u8>, AppError> {
    use img_parts::{jpeg::Jpeg, ImageEXIF};
    Jpeg::from_bytes(bytes.to_vec().into())
        .map(|mut jpeg| {
            jpeg.set_exif(None);
            jpeg.encoder().bytes().to_vec()
        })
        .map_err(|_| AppError::BadRequest("Image processing failed: not a valid JPEG".into()))
}
```

And update the caller at line 273:
```rust
let clean_bytes = strip_exif(&req.image_bytes)?;
```

### WR-03: nginx `add_header Content-Type "image/jpeg" always` overrides Content-Type for ALL files under `/uploads/`

**File:** `nginx/nginx.conf:137`, `nginx/nginx.server.conf:125`

**Issue:** The `add_header Content-Type "image/jpeg" always` directive forces `Content-Type: image/jpeg` on every response from the `/uploads/` location block, regardless of what the upstream (Axum's `ServeDir`) sends. This is syntactically valid nginx and works for the current codebase (which only accepts JPEG uploads). However:

1. It does not override the upstream's `Content-Type` header — nginx's `add_header` *adds* a second `Content-Type` header rather than replacing the first. The upstream `ServeDir` sends its own `Content-Type` header (typically `image/jpeg` based on file extension), so the response will contain **two `Content-Type` headers**: one from Axum and one from nginx. RFC 7230 forbids multiple `Content-Type` headers; browser behaviour is undefined and some parsers use the first value, others the last.
2. If the codebase ever accepts PNG or WebP uploads (a likely future extension), all such files will be served with `Content-Type: image/jpeg`, causing browsers to reject them or display them incorrectly.

The intent (preventing browsers from sniffing content as HTML/JS) is correct, but `add_header` is the wrong directive. Use `proxy_hide_header Content-Type` + `add_header Content-Type` only if the goal is to replace. Alternatively, rely on `ServeDir`'s correct per-extension type inference and add `X-Content-Type-Options: nosniff` to prevent sniffing.

**Fix:** Remove the `add_header Content-Type` line and add a `nosniff` header instead:
```nginx
location /uploads/ {
    proxy_pass http://backend;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_cache_bypass $http_upgrade;
    expires 30d;
    add_header Cache-Control "public, no-transform";
    add_header X-Content-Type-Options "nosniff" always;
}
```

### WR-04: `backup.sh` — retention `find` matches `.tar.gz` files system-wide under `BACKUP_ROOT`, not just uploads

**File:** `backup/backup.sh:51`

**Issue:** The retention cleanup command:
```bash
find "$BACKUP_ROOT" -mtime +30 -name "*.tar.gz" -delete
```
searches recursively under `BACKUP_ROOT` for all `.tar.gz` files older than 30 days. If any operator ever places a `.tar.gz` file under `/data/backups/` for unrelated purposes (e.g., a manual backup of config files), it will be silently deleted. The intent is to delete only `uploads_<date>.tar.gz` files.

**Fix:** Scope the search to the specific subdirectories:
```bash
find "$DB_BACKUP_DIR"      -mtime +30 -name "*.sql.gz"  -delete
find "$UPLOADS_BACKUP_DIR" -mtime +30 -name "*.tar.gz"  -delete
```

### WR-05: `backup.sh` runs as `root` in systemd unit — unnecessarily broad privilege

**File:** `backup/walkability-backup.service:7`

**Issue:** The systemd unit specifies `User=root`. The backup script only needs to:
- Run `docker compose ps` and `docker exec` (requires `docker` group membership)
- Write to `/data/backups/` (could be owned by a dedicated backup user)

Running the entire backup script as root means a shell injection bug in any of the subprocess calls (e.g., in `$DB_CONTAINER`, `$DATE`, or `$ACTUAL_SIZE`) would give an attacker root access to the host. The `$DB_CONTAINER` value comes from `docker compose ps -q db` and contains a container ID — but if the Docker socket is compromised, the container ID could be manipulated to inject shell commands.

**Fix:** Create a dedicated `walkability-backup` user, add it to the `docker` group, own `/data/backups/` by that user, and change `User=` in the service unit:
```ini
[Service]
Type=oneshot
User=walkability-backup
ExecStart=/home/karankinariwala/bengaluru-walkability-public-audit/backup/backup.sh
```

### WR-06: `dedup_job.rs` — `run_dedup_pass` processes ALL non-duplicate reports in the last 15 minutes on every pass, with no pagination or limit

**File:** `backend/src/db/dedup_job.rs:62-70`

**Issue:** The candidate query fetches all reports created in the last 15 minutes without `LIMIT`:
```sql
SELECT id, category::TEXT, latitude, longitude
FROM reports
WHERE duplicate_of_id IS NULL
  AND created_at >= NOW() - INTERVAL '15 minutes'
ORDER BY created_at ASC
```

If a spam burst submits thousands of reports in 15 minutes (bypassing rate limiting, e.g., from multiple IPs), this query will return all of them and the loop will issue one `FIND_NEARBY_OPEN_REPORT_SQL` query per candidate — potentially thousands of PostGIS spatial queries per 5-minute tick. While this is a performance concern primarily, it can also degrade to a correctness issue: if the pass takes longer than 5 minutes, the next tick starts while the previous is still running, causing two concurrent `link_duplicate` transactions on the same rows and potential deadlocks or double-linking.

This is flagged as a Warning (not Critical) because it requires an active spam scenario to trigger the correctness issue, and the rate limiter provides partial protection.

**Fix:** Add a `LIMIT` to the candidate query (e.g., `LIMIT 500`) to cap per-pass work.

## Info

### IN-01: `backup.sh` — no verification that the uploads backup tar is non-empty

**File:** `backup/backup.sh:41-45`

**Issue:** The database backup validates size with `du -k` and exits on failure. The uploads `tar czf` step has no equivalent size validation. A successful-looking `tar czf` on an empty `/data` volume would produce a near-empty (but non-zero) `.tar.gz`. If uploads are accidentally deleted or the volume is empty, the backup system will report success with a 200-byte archive.

**Fix:** Add a size check analogous to the database backup:
```bash
UPLOADS_SIZE=$(du -k "$UPLOADS_BACKUP_FILE" | cut -f1)
if [ "$UPLOADS_SIZE" -lt 1 ]; then
    echo "BACKUP VALIDATION FAILED: uploads backup is empty" >&2
    exit 1
fi
```

### IN-03: `backup/walkability-backup.timer` — no `[Install]` section `WantedBy` for the `.service` file (only timer has it)

**File:** `backup/walkability-backup.service:1-8`

**Issue:** `walkability-backup.service` has no `[Install]` section. This is intentional for timer-driven services (the timer activates the service, not a direct `systemctl enable` on the service). However, `walkability-backup-failure.service` also has no `[Install]` section and is referenced via `OnFailure=` in the main service unit. For `OnFailure=` references to work, the failure service must be reachable by systemd at runtime, which it is (it doesn't need to be enabled independently). This is not a bug, but worth documenting explicitly.

The `walkability-backup.service` has no corresponding `.service` file `[Install]` section, so `systemctl enable walkability-backup.service` will fail with "No preset found" unless the timer is what gets enabled. The DEPLOYMENT.md should document that only the timer needs to be enabled, not the service directly.

**Fix:** Add a comment to `walkability-backup.service`:
```ini
# This service is activated by walkability-backup.timer.
# Do NOT enable this service directly — enable the timer:
#   sudo systemctl enable --now walkability-backup.timer
```
