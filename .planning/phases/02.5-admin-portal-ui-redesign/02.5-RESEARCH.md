## Summary

Phase 02.5 replaces all Tailwind-based admin portal UI with a CSS custom property token system (Direction B "Walkability Console" palette) and 15 new primitive components, while rewriting the 6 existing admin components in-place. The design source is fully specified in `design-ref/admin-portal/` — tokens.css contains the verbatim token definitions, primitives.jsx contains the exact prop API contracts for all new components, and the screens-b-*.jsx files show every screen layout.

The existing admin codebase is straightforward Tailwind + lucide-react with no dark mode, no custom token layer, and no offline states. All styling is via Tailwind class strings — the rewrite replaces these entirely with inline `style={{ ... }}` objects consuming CSS variables. This approach is already established in Phase 02.3.1 and is the project standard for all new/redesigned code.

The key implementation challenges are: (1) the FOTWT prevention script must run synchronously before React hydrates, requiring a `dangerouslySetInnerHTML` script tag in the admin layout head; (2) JetBrains Mono is currently loaded at weights 400/500 only — weight 600 is required by the design and must be added to `frontend/app/layout.tsx`; (3) existing tests assert on Tailwind class names and will need updating when components are rewritten; (4) the `suppressHydrationWarning` attribute must be added to `<html>` in the root layout to silence the expected class mismatch from the dark-mode script.

**Primary recommendation:** Execute as 4 sequential plans — (1) token foundation + layout setup + JetBrains Mono weight fix + 15 new primitives, (2) AdminSidebar rewrite + mobile bottom tab bar + dark mode toggle, (3) all page screen rewrites (Dashboard, Reports, Report Detail, Map, Login), (4) Users, Profile, Organizations, Empty/Error/Offline states, and accessibility pass.

### Pattern 1: CSS Custom Property Token Scope

**What:** Admin-specific token overrides scoped to `.admin-portal` class, nested inside a flat CSS file. This avoids leaking Direction B tokens into citizen-facing pages.

**When to use:** All admin components — components do not need to know which direction they are in; they consume `var(--bg)`, `var(--accent)` etc. which resolve to Direction B values inside `.admin-portal`.

```css

.admin-portal {
  --bg: #f3f3f1;
  --surface: #ffffff;
  --surface-2: #eaeae6;
  --surface-3: #d8d8d4;
  --border: #d4d4d1;
  --border-strong: #a8a8a3;
  --ink: #0a0a0a;
  --ink-2: #3a3a37;
  --muted: #6b6b66;
  --muted-2: #9a9a94;
  --accent: oklch(0.56 0.13 200);
  --accent-ink: oklch(0.38 0.13 200);
  --accent-bg: oklch(0.95 0.03 200);
  --accent-border: oklch(0.86 0.06 200);
  --on-accent: #ffffff;
  /* ... full .dir-b block ... */
  --r-xs: 4px; --r-sm: 6px; --r-md: 8px; --r-lg: 10px; --r-xl: 14px; --r-full: 999px;
```

### Pattern 2: FOTWT Prevention Script

**What:** A blocking synchronous script in the admin layout `<head>` that reads localStorage before React hydrates and sets the `.dark` class on `<html>`.

**When to use:** Admin layout only — must run before first paint to prevent flash.

```tsx
// Source: CONTEXT.md D-10; standard Next.js FOTWT pattern
// File: frontend/app/admin/layout.tsx

// In the returned JSX <head>:
<script
  dangerouslySetInnerHTML={{
    __html: `(function(){var d=localStorage.getItem('admin-theme');if(d==='dark')document.documentElement.classList.add('dark');})();`,
  }}
/>

// Root layout html element needs suppressHydrationWarning:
// frontend/app/layout.tsx line 49:
<html lang="en" className={fontVars} suppressHydrationWarning>
```

**Note:** `suppressHydrationWarning` is added to `<html>` in `frontend/app/layout.tsx` (root layout), not in the admin layout, because the `.dark` class is set on `document.documentElement` which is the `<html>` element rendered by the root layout. ### Pattern 3: CSS Variable Inline Style Component

**What:** Components use inline `style` objects with `var(--token)` references. `data-*` attributes carry variant identity for testability (jsdom strips CSS var() from inline styles, so Tailwind class assertions are replaced by `data-variant` attribute assertions).

**When to use:** All new admin primitive components. Established in Phase 02.3.1.

```tsx
// Source: codebase convention (Phase 02.3.1 precedent; CONVENTIONS.md)
// File: frontend/app/admin/components/Btn.tsx

"use client";

export type BtnVariant = "primary" | "accent" | "secondary" | "ghost" | "soft" | "danger" | "danger-soft";
export type BtnSize = "xs" | "sm" | "md" | "lg";

export function Btn({ variant = "primary", size = "md", children, style, ...rest }: BtnProps) {
  const sizeStyle = SIZES[size];
  const variantStyle = VARIANTS[variant];
  return (
    <button
      data-variant={variant}
      data-size={size}
      data-component="btn"
      style={{ display: "inline-flex", alignItems: "center", justifyContent: "center", ...sizeStyle, ...variantStyle, ...style }}
      {...rest}
    >
      {children}
    </button>
  );
}
```

**Test assertion pattern (data-* attributes):**
```tsx
// Instead of: expect(el).toHaveClass('bg-amber-100')
// Use:        expect(el.dataset.variant).toBe('accent')
// Or:         expect(el.getAttribute('data-tone')).toBe('warn')
```

### Pattern 4: SeverityIndicator Bars (WCAG 1.4.1)

**What:** Three stacked bars of heights [4px, 8px, 12px] — lit bars use `sev-{level}` color, unlit bars use `--border-strong`. Always accompanied by text label. Triple encoding: color + pattern + text.

**When to use:** All admin severity displays. Never use color-only. [CITED: 02.5-UI-SPEC.md Component Inventory]

```tsx
// Source: design-ref/admin-portal/primitives.jsx SeverityIndicator
// Always use style="bars" in admin portal (not pill)
const bars = [4, 8, 12];
const level = { low: 1, medium: 2, high: 3 }[severity];
return (
  <span style={{ display: "inline-flex", alignItems: "center", gap: 6 }}>
    <span style={{ display: "inline-flex", alignItems: "flex-end", gap: 2, height: 12 }}>
      {bars.map((h, i) => (
        <span key={i} style={{
          width: 3, height: h,
          background: i < level ? `var(--sev-${severity})` : "var(--border-strong)",
          borderRadius: 1
        }}/>
      ))}
    </span>
    <span style={{ fontSize: 11, fontFamily: "var(--font-mono)", textTransform: "uppercase",
                   letterSpacing: "0.04em", color: "var(--ink-2)" }}>
      {label}  {/* "Low" / "Medium" / "High" */}
    </span>
  </span>
);
```

### Pattern 5: useOnlineStatus Hook

**What:** Client hook reads `navigator.onLine` on mount and subscribes to window `'offline'`/`'online'` events. [CITED: CONTEXT.md D-15]

```tsx
// File: frontend/app/admin/lib/useOnlineStatus.ts
"use client";
import { useState, useEffect } from "react";

export function useOnlineStatus(): boolean {
  const [isOnline, setIsOnline] = useState(true);
  useEffect(() => {
    setIsOnline(navigator.onLine);
    const goOnline = () => setIsOnline(true);
    const goOffline = () => setIsOnline(false);
    window.addEventListener("online", goOnline);
    window.addEventListener("offline", goOffline);
    return () => {
      window.removeEventListener("online", goOnline);
      window.removeEventListener("offline", goOffline);
    };
  }, []);
  return isOnline;
}
```

### Anti-Patterns to Avoid

- **Tailwind classes in rewritten components:** The rewrite mandate (D-09) is absolute. No `className="bg-gray-50"` in new/rewritten admin components. Use `style={{ background: 'var(--surface-2)' }}`.
- **Hardcoded hex colors in component style objects:** Always use token references (`var(--accent)`, not `oklch(0.56 0.13 200)`). Hardcoded values break dark mode.
- **Modifying `:root` in admin.css:** The `:root` block in globals.css belongs to the citizen-facing direction. Only `.admin-portal { }` and `.dark .admin-portal { }` blocks go in admin.css.
- **Setting `.dark` class on `<body>` instead of `<html>`:** The FOTWT script targets `document.documentElement` (the `<html>` element). The CSS selector `.dark .admin-portal` requires `.dark` to be on an ancestor of `.admin-portal`. Since `.admin-portal` is on a `<div>` inside `<body>`, `.dark` on `<html>` is the correct ancestor. `.dark` on `<body>` would also work but is non-standard; use `<html>` per D-10.
- **Color-only severity signals:** SeverityIndicator must always render bars pattern + text label + color. Never a color dot alone.
- **`lucide-react` imports in new components:** D-07 locks the Icon component replacement. Do not import from lucide-react in any rewritten file.
- **Icon without `aria-hidden="true"`:** All decorative Icon usages must carry `aria-hidden="true"` per UI-SPEC. Icon-only interactive buttons must carry an explicit `aria-label`.

## Common Pitfalls

### Pitfall 1: JetBrains Mono Weight 600 Not Loaded

**What goes wrong:** Section labels, nav labels, timestamps, and hero counts render at the wrong weight (browser falls back to weight 500 or synthesizes bold). Design requires weight 600 throughout admin chrome.

**Why it happens:** `frontend/app/layout.tsx` loads JetBrains Mono at `weight: ["400", "500"]` only. Weight 600 is not declared.

**How to avoid:** In Plan 1 Wave 0, add `"600"` to the JetBrains Mono weight array in `frontend/app/layout.tsx` before implementing any admin component that uses `fontWeight: 600` with `var(--font-mono)`.

**Warning signs:** Chrome DevTools shows "Synthesized Bold" in the font panel for JetBrains Mono 600 elements.

### Pitfall 2: `suppressHydrationWarning` on Wrong Element

**What goes wrong:** React hydration error: "Warning: Prop `className` did not match. Server: '' Client: 'dark'". The FOTWT script adds `.dark` to `<html>` client-side, but the server-rendered HTML has no `.dark` class.

**Why it happens:** `suppressHydrationWarning` must be on the `<html>` element in `frontend/app/layout.tsx` (root layout). The admin layout cannot render a second `<html>` element — it is a nested layout.

**How to avoid:** Add `suppressHydrationWarning` to `<html>` in `frontend/app/layout.tsx`. The admin layout's FOTWT script goes in `<head>` (injected via `<Script>` or a `<script dangerouslySetInnerHTML>` tag rendered in the admin layout's return value before `{children}`). [CITED: CONTEXT.md D-10, design-ref specifics section]

**Warning signs:** Console error in development: "Hydration failed because the server rendered HTML didn't match the client."

### Pitfall 3: Existing Tests Assert on Tailwind Class Names

**What goes wrong:** After rewriting StatusBadge from Tailwind to CSS custom properties, existing tests in `StatusBadge.test.tsx` that check for `bg-gray-100`, `bg-amber-100`, `bg-green-100` class names fail — the new component has no Tailwind classes.

**Why it happens:** The current test suite uses `classesContaining(el, "amber")` to verify status color mapping. This pattern only works with Tailwind. CSS custom properties via inline styles are not visible to jsdom's className API.

**How to avoid:** When rewriting each component, simultaneously update its test file to assert on `data-*` attributes instead. The established pattern (from Phase 02.3.1 / STATE.md): `data-tone`, `data-variant`, `data-size`, `data-component` on primitives. Example: `expect(badge.dataset.tone).toBe('warn')` replaces `expect(classesContaining(el, 'amber').length).toBeGreaterThan(0)`.

**Warning signs:** Test failures immediately after component rewrite with messages like "Expected 1 element with class containing 'amber' but found 0".

### Pitfall 4: Admin Layout is a Server Component — Cannot Import Client Hooks

**What goes wrong:** Trying to implement dark mode toggle logic or `useOnlineStatus()` directly in `app/admin/layout.tsx` causes a "useState/useEffect can only be used in a client component" error.

**Why it happens:** `app/admin/layout.tsx` is a Server Component (no `"use client"` directive). It handles auth guard by reading cookies server-side. The FOTWT script runs as raw HTML, not as React state.

**How to avoid:** The FOTWT script is a raw `<script>` tag injected via `dangerouslySetInnerHTML` — not a hook. Dark mode toggle state lives in `AdminSidebar.tsx` (already a client component). All client-side interactivity stays in client components. [CITED: CONTEXT.md code_context section, codebase analysis of layout.tsx]

**Warning signs:** Build error referencing "hooks can only be used in Client Components."

### Pitfall 5: `.admin-portal` Class Not on Outermost Wrapper

**What goes wrong:** Direction B tokens don't apply because the `.admin-portal` class is missing or placed on an inner element that doesn't wrap all admin UI.

**Why it happens:** The current layout.tsx wrapper is `<div className="min-h-screen bg-gray-50">` — the new layout must add `.admin-portal` to this exact element and remove the Tailwind class.

**How to avoid:** In the layout.tsx rewrite, the outermost `<div>` must have `className="admin-portal"` (not `style={...}`). This ensures CSS cascade works correctly for all child components.

**Warning signs:** Page background remains `#fafaf9` (citizen color) instead of `#f3f3f1` (Direction B color).

### Pitfall 6: `oklch()` Color Support

**What goes wrong:** Direction B uses `oklch()` color notation for accent, status, severity, and semantic tokens. Older browsers (Chrome < 111, Safari < 15.4) do not support `oklch()`. If the project has a browser support policy requiring older browsers, all `oklch()` values need `@supports` fallbacks.

**Why it happens:** The design spec uses `oklch()` throughout and `globals.css` already uses it for citizen-facing tokens. The project has already accepted this tradeoff.

**How to avoid:** No action needed — the project already uses `oklch()` in globals.css (established in Phase 02.3.1). Admin tokens follow the same pattern. Target browsers (government office workers in India) are on modern Chromium-based browsers.

**Warning signs:** Not a concern for this project's target users.

### Pitfall 7: Icon Component Uses `window.CATEGORIES` in Design Ref

**What goes wrong:** The `CategoryGlyph` component in `primitives.jsx` references `window.CATEGORIES` — this is a design canvas artifact and will throw in Next.js.

**Why it happens:** The design canvas uses `data.js` which populates `window.CATEGORIES`. In Next.js there is no such global.

**How to avoid:** Do not implement `CategoryGlyph` as-is. Use `Icon` directly with the appropriate category icon name, sourcing the mapping from `frontend/app/lib/constants.ts` or `translations.ts`. [CITED: CONTEXT.md — getCategoryLabel() from translations.ts is the single source of truth]

**Warning signs:** `ReferenceError: window is not defined` during SSR, or `TypeError: Cannot read properties of undefined` on client.

```tsx
const STATUS_MAP = {
  submitted:    { tone: "info",   dot: "var(--status-submitted)", label: "Submitted" },

  return (

      data-tone={m.tone}
      data-status={status}

      style={{
        display: "inline-flex", alignItems: "center",
        padding: "4px 10px", borderRadius: "var(--r-full)",
        fontSize: monoLabel ? 11 : 12, fontWeight: 500,
        fontFamily: monoLabel ? "var(--font-mono)" : "inherit",
        letterSpacing: monoLabel ? "0.02em" : undefined,

        background: `var(--${m.tone}-bg, var(--accent-bg))`,
        color: `var(--${m.tone}-ink, var(--accent-ink))`,
        border: `1px solid var(--${m.tone}-border, var(--accent-border))`,
        gap: 6,
      }}
    >
      <span style={{ width: 6, height: 6, borderRadius: 999, background: m.dot, flexShrink: 0 }} aria-hidden="true" />
      {m.label}
    </span>
  );
}
```

## Open Questions

1. **Admin Layout FOTWT Script Placement in Next.js 14**
   - What we know: `app/admin/layout.tsx` is a Server Component that renders inside the root `app/layout.tsx`. The root layout renders `<html>` and `<head>`. Nested layouts cannot render a second `<html>` element.
   - What's unclear: Can a `<script dangerouslySetInnerHTML>` tag placed directly in the nested admin layout's return value (before `{children}`) reliably execute before first paint, given that it will be rendered inside `<body>`?
   - Recommendation: Place the script at the very top of the admin layout's returned JSX (before the `.admin-portal` div). In production, Next.js will inline it near the top of the rendered HTML for that route segment. Alternatively, the script can be injected via a `<Script strategy="beforeInteractive">` tag — but `next/script` with `beforeInteractive` requires a `src` attribute, so `dangerouslySetInnerHTML` in a plain `<script>` tag is the correct approach. The script should be the first element in the returned fragment to execute as early as possible.

2. **lucide-react Removal Timing**
   - What we know: `lucide-react` is used in `AdminSidebar.tsx` (Menu, X icons). After AdminSidebar is rewritten with the Icon component, there are no remaining admin usages.
   - What's unclear: Are there any citizen-facing pages that also use lucide-react? (Searching the codebase: `grep -r "lucide-react" frontend/app` would confirm.)
   - Recommendation: Planner should add a task in the final plan to grep for all `lucide-react` imports across the entire frontend and only run `npm uninstall lucide-react` if zero non-admin usages remain.
