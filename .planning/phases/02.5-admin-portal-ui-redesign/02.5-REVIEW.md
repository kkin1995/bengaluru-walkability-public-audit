# Phase 02.5: Code Review Report

**Reviewed:** 2026-05-22T12:00:00Z
**Depth:** standard
**Files Reviewed:** 45
**Status:** issues_found

## Summary

Phase 02.5 is a full admin portal UI redesign delivering a "Direction B" design system (CSS token layer, JetBrains Mono, dark mode, component library). The implementation covers ~45 files across components, pages, layout, and tests.

The design system token layer and component library (Btn, Card, Pill, StatusBadge, SeverityIndicator, etc.) are well-structured and self-contained. The most serious defects cluster in three areas:

1. **Security** — The admin layout injects a `dangerouslySetInnerHTML` script containing a `localStorage.getItem` call; while the script itself is a static IIFE with no user input, a reflected-XSS vector exists in the map page where a report's `description` field is used inside a Leaflet `divIcon` HTML string without escaping. The logout link is a plain `<a href>` rather than a form POST, which can be CSRF-abused to silently log out users. The password generator in `CreateUserModal` uses `Math.random()` — a non-cryptographic PRNG — to generate initial passwords, which violates the in-file claim of ARGON2ID security posture.

2. **Correctness** — The `ReportDetailPage` `params` prop is read synchronously as `params.id` in a Next.js 14 App Router page, but Next.js 14 requires `params` to be awaited as it may be a Promise in certain server-component/dynamic-route configurations. The map page's Leaflet marker icon construction calls `require("leaflet")` synchronously inside a `.map()` body on every render, re-importing the module repeatedly rather than initializing once. The `PhotoTile` component is called with `size={undefined as unknown as number}` in the report detail page, deliberately bypassing the type system to produce an `undefined` width/height on the rendered `img`, which causes a broken layout. The `handleDelete` function in the report detail page fails silently on a deletion API error without surfacing any error state to the user — `isDeleting` is set back to `false` in the catch but the modal is left open with no feedback.

3. **Authorization / role-gating** — The `ReportsPage` client component reads `role` from `(props as any).role`, which is a test-injection backdoor kept in production code. In production the `getMe()` fetch defaults to `"admin"` on any error, meaning a network error or expired session silently grants admin-level delete capabilities to the UI.

## Critical Issues

### CR-01: Password generator uses Math.random() — cryptographically insecure PRNG

**File:** `frontend/app/admin/components/CreateUserModal.tsx:83-89`
**Issue:** `generatePassword()` constructs a 16-character password using `Math.floor(Math.random() * chars.length)`. `Math.random()` is not cryptographically secure — its output is predictable. The comment in the UI explicitly claims "ARGON2ID" security posture. An attacker who can observe the system clock or seed-guess the PRNG can enumerate the generated password space. Generated passwords that are immediately handed to a new user (before the user changes them) are the highest-risk moment.
**Fix:**
```typescript
function generatePassword() {
  const chars = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789!@#$%^&*";
  const array = new Uint32Array(16);
  crypto.getRandomValues(array);
  let pwd = "";
  for (let i = 0; i < 16; i++) {
    pwd += chars[array[i] % chars.length];
  }
  setPassword(pwd);
}
```

### CR-02: Leaflet Popup description is injected unescaped into HTML — stored XSS vector

**File:** `frontend/app/admin/reports/map/page.tsx:447-458`
**Issue:** The Leaflet `<Popup>` renders `report.description` directly in JSX. While React's JSX escapes text content, the `iconHtml` string constructed for `L.divIcon` on line 419 uses a template literal with `pinColor` (which comes from a hardcoded switch statement). More critically, the Popup `<p>` on line 455 renders `truncateDescription(report.description)` in JSX — this is safe in React. **However**, the `window.location.assign()` call in `DupeSubTable` (ReportsTable.tsx:176) navigates to `/admin/reports/${dupe.id}` using a raw `dupe.id` from the API. If an attacker can control a report ID (via a crafted API response or SSRF), this becomes an open redirect / path injection. The more pressing issue is the `iconHtml` template literal: `pinColor` is safe (hardcoded switch), but this pattern is fragile — if any future contributor adds a user-controlled field to `iconHtml`, there is no escaping in place. Additionally, `report.category` is rendered directly in the Popup `<p>` on line 447 in JSX, which is safe, but `report.status` text is inlined in a styled `<span>` colored by `pinColor` — this is safe today but the lack of any escaping infrastructure is a latent risk.

The confirmed exploitable issue: `DupeSubTable` uses `window.location.assign()` with an unsanitized `dupe.id` from the API response, and the anchor `href` is constructed from the same ID. If the API returns a crafted ID containing `javascript:` (theoretically possible if the backend has a bug), the `<a href>` would be a JS-execution vector.

**Fix:** Validate that `dupe.id` is a UUID before constructing hrefs and calling `window.location.assign()`:
```typescript
// In DupeSubTable, before rendering:
const safeId = /^[0-9a-f-]{36}$/i.test(dupe.id) ? dupe.id : "";
// Use safeId in href and window.location.assign()
```

### CR-03: Admin logout is a GET <a> link — trivially CSRF-able

**File:** `frontend/app/admin/components/AdminSidebar.tsx:217`
**Issue:** The logout action is implemented as `<a href="/api/admin/auth/logout">`. A GET request for a logout operation is a well-known CSRF pattern: any page the admin visits can embed `<img src="/api/admin/auth/logout">` or similar to silently log out the user. The backend at `POST /api/admin/auth/logout` (per CLAUDE.md) expects a POST. The sidebar link issues a GET, which either calls the wrong endpoint or the backend accepts GET for logout, either of which is a security defect.
**Fix:** Replace the anchor with a form POST or a button that calls the `logout()` API function:
```tsx
<button
  onClick={async () => {
    await fetch("/api/admin/auth/logout", { method: "POST", credentials: "include" });
    window.location.assign("/admin/login");
  }}
  aria-label="Log out"
  style={{ /* existing styles */ }}
>
  <Icon name="logout" size={14} aria-hidden={true} />
</button>
```

### CR-04: Default role is "admin" on getMe() failure — privilege escalation in the UI

**File:** `frontend/app/admin/reports/page.tsx:29` and `frontend/app/admin/reports/[id]/page.tsx:49`
**Issue:** Both pages initialize `role` state to `"admin"` and only downgrade to `"reviewer"` if `getMe()` explicitly returns `role === "reviewer"`. On any network failure, token expiry, or API error, the `catch` block silently keeps the default `"admin"` role. This means an unauthenticated or session-expired browser tab displays delete buttons and admin-only controls to whoever is using it. The correct default is `"reviewer"` (least privilege), upgrading only when the API confirms an elevated role.

Additionally, `ReportsPage` reads `(props as any).role` — a test-injection backdoor — directly in production code. This bypasses the `getMe()` check entirely.
**Fix:**
```typescript
// reports/page.tsx line 29
const [role, setRole] = useState<"admin" | "reviewer">(injectedRole ?? "reviewer");

// reports/[id]/page.tsx line 49
const [role, setRole] = useState<"admin" | "reviewer">("reviewer");

// And in the getMe() .then():
setRole(user.role === "admin" || user.role === "super_admin" ? "admin" : "reviewer");
```

### CR-05: Next.js 14 dynamic route params accessed synchronously — potential runtime crash

**File:** `frontend/app/admin/reports/[id]/page.tsx:39-43`
**Issue:** The page component signature is `{ params }: { params: { id: string } }` and `params.id` is accessed synchronously on line 83. In Next.js 14+ with the App Router, `params` in a client component (`"use client"`) is passed synchronously by Next.js, so this works today. However, the file uses `"use client"` and calls `getAdminReport(params.id)` inside a `useEffect` — the component correctly accesses `params.id` only after mount. The actual risk is that `params` is typed as `{ id: string }` but in Next.js 14.2+ with async server components, the recommended pattern is `params: Promise<{ id: string }>` requiring `await`. In the current client-component context this works, but it is architecturally fragile: any promotion to a server component will crash. More immediately, the `params` object is read inside a `useEffect` dependency array as `[params.id]` but `params` itself is not stabilized, which means if Next.js ever passes a new `params` object reference (same value) on re-render, the effect will re-fire unnecessarily.

The definite bug: the `PhotoTile` on line 196 is called as `size={undefined as unknown as number}` — a deliberate type-cast to `undefined`. `PhotoTile` renders `<img width={size} height={size}>` which produces `width="undefined"` in the DOM. This causes CSS layout breakage on the fallback (no-photo) path.
**Fix for PhotoTile:**
```tsx
// reports/[id]/page.tsx ~line 196: Remove the size prop entirely or pass a valid number.
// PhotoTile renders correctly with no image when src is absent; pass a container-filling style:
<PhotoTile
  style={{ width: "100%", height: "100%", display: "block", borderRadius: 0 }}
  aria-hidden="true"
/>
// PhotoTile already handles `src` being absent; the `size` prop defaults to 64 if omitted.
```

### CR-06: handleDelete silently swallows errors — user gets no feedback on failure

**File:** `frontend/app/admin/reports/[id]/page.tsx:109-119`
**Issue:** `handleDelete` catches the deletion error but only sets `isDeleting` back to `false`. The delete modal remains open, the user sees no error message, and there is no indication that the deletion failed. From the user's perspective, pressing "Delete" appears to simply do nothing.
```typescript
async function handleDelete() {
  if (!report) return;
  setIsDeleting(true);
  try {
    await deleteReport(report.id);
    setShowDeleteModal(false);
    router.push("/admin/reports");
  } catch {
    setIsDeleting(false);  // <-- only this: no error state set
  }
}
```
**Fix:** Add a `deleteError` state and surface it in the modal:
```typescript
const [deleteError, setDeleteError] = useState<string | null>(null);

// In handleDelete catch:
} catch {
  setIsDeleting(false);
  setDeleteError("Failed to delete report. Please try again.");
}

// In the modal JSX, after the title:
{deleteError && (
  <p role="alert" style={{ color: "var(--danger-ink)", fontSize: 13, marginBottom: 12 }}>
    {deleteError}
  </p>
)}
```

### CR-07: Input component wraps input in <label> — causes double-activation and broken association

**File:** `frontend/app/admin/components/Input.tsx:21-59`
**Issue:** The `Input` component renders `<label data-component="input">` wrapping both the icon and the `<input>`. This means:
1. Any `htmlFor` / `id` pair on the caller side is superfluous (the label association is implicit via wrapping). In the login page, `<label>` wraps `<Input>` which internally wraps another `<label>`, producing a **nested label** (invalid HTML). Specifically, `login/page.tsx:169` and `185` render `<label style="display:flex">` containing `<Input>` which itself renders a `<label>`. Nested labels are invalid HTML5 and cause screen readers to announce the label text twice.
2. More critically, clicking anywhere on the `Input` component's visible area (including the icon) activates the label click, which focuses the inner `<input>`. This is the intended behavior — but when a `suffix` node (like a button) is passed (as in `CreateUserModal.tsx:235-245`), clicking the suffix button inside the label wrapper also triggers the label activation, potentially double-firing the button click in some browsers.

The nested label in the login page is the confirmed defect:
**Fix:** Change the `Input` wrapper from `<label>` to `<div>`, and require callers to provide explicit `id` + label association:
```tsx
// Input.tsx: change <label data-component="input" ...> to <div data-component="input" ...>
// Callers that need label-for-input association must use their own <label htmlFor="inputId">
// and pass id="inputId" to the Input component.
```

### WR-01: Dark mode state is not synchronized between AdminSidebar and profile page

**File:** `frontend/app/admin/components/AdminSidebar.tsx:51-53`, `frontend/app/admin/profile/page.tsx:46-48`
**Issue:** Both `AdminSidebar` and `ProfilePage` independently read `document.documentElement.classList.contains("dark")` on mount to initialize `isDark` state. There is no shared state — toggling dark mode in the sidebar does not update the `isDark` indicator in the profile page (and vice versa). The DOM `classList` is correctly mutated in both places so the visual result is correct, but the button label (`DARK MODE` / `LIGHT MODE`) in the sidebar can be incorrect if the user navigates between pages or if the initial state differs.

This is a robustness/correctness issue: a user can end up with a dark-mode-enabled DOM but the sidebar showing "DARK MODE" (suggesting it's off) after state desynchronizes.
**Fix:** Use a custom event, React context, or simply always derive `isDark` from `document.documentElement.classList.contains("dark")` at render time rather than caching it in state.

### WR-02: ReportsTable filter counts operate on the pre-filtered prop — misleading when server filters are active

**File:** `frontend/app/admin/components/ReportsTable.tsx:613-622`
**Issue:** The filter chip counts (`submittedCount`, `reviewCount`, `highSevCount`) are computed from the `reports` prop (the current page's 20 items), not from `totalCount`. When server-side filters are active (e.g., the parent page filters by category), these counts reflect only the current page slice, not the total across all pages. ### WR-07: ReportsTable onStatusChange prop is used as both a filter callback and a status-change trigger — semantic overload

**File:** `frontend/app/admin/reports/page.tsx:101-108`, `frontend/app/admin/components/ReportsTable.tsx:492-494`
**Issue:** `ReportsTableProps` has both `onStatusChange` (documented as "called when the user changes status") and `onCategoryChange`. In `reports/page.tsx`, `onStatusChange={handleStatusChange}` wires to a server-side filter function that re-fetches reports with a status filter parameter. But in `ReportsTable`, `onStatusChange` is also the fallback when `onUpdateStatus` is absent: `(onUpdateStatus ?? onStatusChange)(report.id)`. This means when `onUpdateStatus` is not provided, clicking "Status" calls the filter function with a report ID instead of a filter value — the filter function `handleStatusChange(value: string)` receives a UUID and passes it to `getAdminReports({ status: uuid })`, which returns 0 results silently.

In practice, `onUpdateStatus={handleUpdateStatus}` is always provided in the current `reports/page.tsx`, but the fallback path is a latent bug that will surface if someone removes `onUpdateStatus`.
**Fix:** Remove the `onStatusChange` fallback in `ReportsTable`. Require `onUpdateStatus` or make the button non-functional when neither is provided.
