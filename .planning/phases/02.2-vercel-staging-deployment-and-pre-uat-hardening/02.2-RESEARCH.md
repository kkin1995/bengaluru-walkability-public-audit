## Summary

This phase deploys the existing Rust/Axum backend to Railway (Docker service + Railway PostGIS template) and the Next.js frontend to Vercel (monorepo root directory = `frontend/`), with a custom domain `staging-walkability.kinariwala.com` pointing to Vercel. The two most critical implementation challenges are: (1) a **SameSite=None + Secure** cookie change required in the backend login handler — the current `SameSite::Strict` setting will silently break admin login when the frontend and backend are on different domains; and (2) a **frontend middleware workaround** to handle the fact that Vercel's Next.js middleware cannot read cookies set by a Railway domain.

Railway's managed Postgres does not ship PostGIS in the default template — you must deploy the dedicated **PostGIS template** (`railway.com/deploy/postgis`), which provides Postgres 16 + PostGIS 3.4 + pgcrypto (standard contrib). The existing backend `Dockerfile` (debian:bookworm-slim, non-Alpine) works as-is with Railway's Docker builder. Railway injects the `PORT` env var at runtime; the backend already reads it via `config.rs`. The admin seed logic is fully idempotent and runs every boot safely.

**Primary recommendation:** Complete the three-step deployment sequence: (1) Railway PostGIS DB → (2) Railway backend service → (3) Vercel frontend with `NEXT_PUBLIC_API_URL` set to the Railway URL. Fix `SameSite::Strict` → `SameSite::None` (with `Secure`) in the backend login handler before UAT.

### Pattern 1: Railway Monorepo — Dockerfile in Subdirectory

**What:** Railway deploys the `backend/` subdirectory as a Docker service. When the Dockerfile is not at the repo root, a `railway.toml` file must be committed to `backend/` (or the root) to tell Railway where the Dockerfile lives.

**Config-as-code NOTE:** Railway's config file does NOT follow the Root Directory path setting. Specify the absolute path from repo root.

**`backend/railway.toml` to create:**

```toml
[build]
builder = "DOCKERFILE"
dockerfilePath = "backend/Dockerfile"

[deploy]
healthcheckPath = "/health"
healthcheckTimeout = 300
restartPolicyType = "ON_FAILURE"
restartPolicyMaxRetries = 5

[[deploy.watchPatterns]]
pattern = "backend/**"
```

**Railway service settings (UI):**
- Root Directory: `backend` (so build context is the `backend/` folder; Docker `COPY` commands work against `backend/`)
- OR leave Root Directory empty and rely on `railway.toml` `dockerfilePath` pointing to `backend/Dockerfile`

**Critical:** Railway's Docker build context must be `backend/` for the existing Dockerfile to work (`COPY Cargo.toml ./`, `COPY src ./src`, etc. all expect to run from within `backend/`). Set "Root Directory" to `backend` in Railway service settings. The `dockerfilePath` in `railway.toml` is then relative to that root, so just `Dockerfile`.

**Corrected `backend/railway.toml`:**

```toml
[build]
builder = "DOCKERFILE"

[deploy]
healthcheckPath = "/health"
healthcheckTimeout = 300
restartPolicyType = "ON_FAILURE"
restartPolicyMaxRetries = 5

[[deploy.watchPatterns]]
```

(Railway service Root Directory setting = `backend`)

### Pattern 2: Railway PORT Injection

**What:** Railway injects `PORT` as a runtime environment variable. The backend's `config.rs` reads `PORT` with `env::var("PORT").unwrap_or_else(|_| "3001".to_string())`.

**Confirmed behavior (HIGH confidence):** Railway injects `PORT` at runtime for Docker services — it is available as an environment variable when the container starts. The backend code reads it correctly. No code changes needed.

**One constraint:** The Dockerfile uses exec-form CMD `CMD ["./server"]`. Railway's injected `PORT` is available as an env var at runtime (not build-time), so the Rust binary reading `std::env::var("PORT")` at startup works correctly. No shell-form CMD needed (the PORT substitution is done in Rust code, not the shell).

**Set `PORT=3001` explicitly** in Railway service variables anyway (as D-13 requires) so Railway knows which port to expose publicly. Railway uses this value to configure its HTTP router.

### Pattern 3: Railway Variable Reference for DATABASE_URL

**What:** Within a Railway project, services can reference other services' variables using `${{ServiceName.VAR}}` syntax.

**For the backend service's `DATABASE_URL` variable on Railway, set the value to:**

```
${{Postgres.DATABASE_PRIVATE_URL}}
```

This uses Railway's internal private network (faster, no egress cost). The `DATABASE_PRIVATE_URL` provides a `postgres://user:pass@postgres.railway.internal:5432/railway` format connection string.

**NOTE on private networking:** The backend Dockerfile uses `debian:bookworm-slim` (not Alpine). The Alpine-specific `ENABLE_ALPINE_PRIVATE_NETWORKING=true` workaround is NOT needed. Private networking works for debian-based images without special configuration.

**Alternative:** Use `${{Postgres.DATABASE_URL}}` (public URL) if private networking causes issues during initial setup. Switch to private URL once confirmed working.

### Pattern 4: Vercel Monorepo Root Directory

**What:** Vercel needs to know the `frontend/` subdirectory is the Next.js project.

**Setup steps:**
1. In Vercel Dashboard → New Project → Import Git Repository → select this repo
2. Before deploying, click "Edit" next to Root Directory → set to `frontend`
3. Vercel will detect Next.js automatically once the root directory is set
4. Build Command: `next build` (Vercel default, correct for Next.js)
5. Output Directory: `.next` (Vercel default, correct for standalone)

**Note on `output: "standalone"`:** The `next.config.mjs` has `output: "standalone"`. Vercel's build system handles standalone output correctly — it does NOT need to be `output: "standalone"` for Vercel (that's for Docker/custom server deploys). For Vercel, the standard Next.js output mode works. However, `output: "standalone"` does not break Vercel deploys; Vercel ignores it and uses its own deployment mechanism. No change needed.

### Pattern 5: NEXT_PUBLIC_API_URL — Build-Time Baking

**What:** `NEXT_PUBLIC_*` variables are inlined at `next build` time. They are NOT available at runtime without a rebuild.

**Critical implication:** The Railway backend URL (`https://walkability-api.up.railway.app` or similar) must be known BEFORE Vercel builds the frontend. This means:

1. Deploy Railway backend first → get the public URL
2. Set `NEXT_PUBLIC_API_URL=https://walkability-api.up.railway.app` in Vercel project settings (Environment: Production + Preview)
3. Trigger a new Vercel deploy (or it deploys automatically on next push)

**The Vercel environment variable settings panel has three scopes: Production, Preview, Development.** Set `NEXT_PUBLIC_API_URL` and `INTERNAL_API_URL` in both Production and Preview scopes so preview deployments also work.

`INTERNAL_API_URL` is a server-side variable (no `NEXT_PUBLIC_` prefix) — it IS available at runtime without baking. It can be updated without rebuilding.

### Pattern 6: Custom Domain DNS

**What:** Adding `staging-walkability.kinariwala.com` as a custom domain to the Vercel project.

**Steps:**
1. Vercel Dashboard → Project → Settings → Domains → Add → `staging-walkability.kinariwala.com`
2. Vercel will display the required DNS record
3. At DNS registrar (for `kinariwala.com`): Add CNAME record `staging-walkability` → `cname.vercel-dns.com.` (include the trailing period if registrar requires it)
4. DNS propagation: typically 5-30 minutes for CNAME changes
5. Vercel auto-provisions TLS (Let's Encrypt) once DNS resolves

**Note:** The CNAME target may differ from `cname.vercel-dns.com` — Vercel sometimes provides project-specific CNAME values (e.g., `d1d4fc829fe7bc7c.vercel-dns-017.com`). Always use the exact value Vercel shows in the dashboard.

### Pattern 7: GitHub Actions Smoke Test with Retry

**What:** `deploy.yml` smoke test runs after Railway and Vercel auto-deploy. Need to account for Railway cold-start delay on first deployment.

**Recommended pattern:**

```yaml
name: Deploy

on:
  push:
    branches:
      - main
  workflow_dispatch:

jobs:
  ci:
    name: "Run CI checks"
    uses: ./.github/workflows/ci.yml

  smoke-test:
    name: "Smoke test staging"
    needs: ci
    runs-on: ubuntu-latest
    env:
      RAILWAY_BACKEND_URL: ${{ secrets.RAILWAY_BACKEND_URL }}
      VERCEL_STAGING_URL: https://staging-walkability.kinariwala.com
    steps:
      - name: Wait for Railway deploy to complete
        run: sleep 30

      - name: Health check — Railway backend
        run: |
          for i in 1 2 3 4 5; do
            if curl -sf "$RAILWAY_BACKEND_URL/health"; then
              echo "Backend healthy"
              exit 0
            fi
            echo "Attempt $i failed, retrying in 15s..."
            sleep 15
          done
          echo "Backend health check failed after 5 attempts"
          exit 1

      - name: API check — Railway reports endpoint
        run: curl -sf "$RAILWAY_BACKEND_URL/api/reports" | head -c 200

      - name: Frontend check — Vercel staging
        run: curl -sf "$VERCEL_STAGING_URL" -o /dev/null -w "HTTP %{http_code}\n"
```

**Required GitHub secret:** `RAILWAY_BACKEND_URL` — set this to the Railway backend's public URL after first Railway deploy. This is a one-time manual setup step.

**Why `sleep 30`:** Railway redeploys asynchronously. A push to main triggers Railway's GitHub integration, which Railway processes independently. The `sleep 30` gives Railway time to start the redeploy before the smoke test polls begin. The retry loop handles remaining cold-start time.

### Anti-Patterns to Avoid

- **Setting `NEXT_PUBLIC_API_URL=""` on Vercel:** This is the docker-compose pattern (relative URLs through nginx). On Vercel + Railway (different domains), relative URLs resolve against the Vercel domain and miss the Railway backend entirely. Every API call returns 404.
- **Using Railway's standard Postgres template and running `CREATE EXTENSION postgis`:** The extension library files are not present in Railway's standard Postgres image. The command will fail with "could not open extension control file". Must use the PostGIS template.
- **Leaving `SameSite::Strict` on the admin login cookie:** Will silently break admin login. Browser will not send the cookie back to the Railway domain on subsequent requests from the Vercel domain. See critical finding below.
- **Setting `CORS_ORIGIN` to the `*.vercel.app` preview URL:** The Axum CORS layer uses an exact string match. Set to the custom domain `https://staging-walkability.kinariwala.com`.

## CRITICAL FINDING: SameSite Cookie Architecture Issue

### The Problem

The backend admin login handler sets `SameSite::Strict` on the `admin_token` cookie (line 318 of `backend/src/handlers/admin.rs`):

```rust
cookie.set_same_site(axum_extra::extract::cookie::SameSite::Strict);
```

When frontend and backend are on the **same domain** (docker-compose with nginx), this works. When they are on **different domains** (Vercel = `staging-walkability.kinariwala.com`, Railway = `walkability-api.up.railway.app`):

1. `kinariwala.com` and `railway.app` are different eTLD+1 domains. They are "cross-site" per the browser's definition.
2. `SameSite=Strict`: Cookie is NEVER sent to a different site. Admin login POST to Railway succeeds, Railway sets the cookie, but the browser never sends it back — every subsequent admin API call appears unauthenticated.
3. `SameSite=Lax`: Cookie is sent only on top-level GET navigations. Also breaks authenticated PATCH/DELETE API calls.
4. **`SameSite=None; Secure`**: Cookie IS sent on all cross-site requests. This is the correct setting for a split frontend/backend architecture. Requires `Secure=true` (enforced by HTTPS, which Railway provides).

### The Compounding Problem: Next.js Middleware

The `frontend/middleware.ts` reads `request.cookies.get('admin_token')` to guard `/admin/*` routes. The cookie set by the Railway backend (`Set-Cookie: admin_token=...; Domain=walkability-api.up.railway.app; ...`) is domain-scoped to Railway's domain — it is **not visible** to Vercel's middleware, which runs under `staging-walkability.kinariwala.com`.

**Result:** Even if `SameSite=None` is set, the middleware on Vercel will always redirect to login because the cookie is stored under Railway's domain, not Vercel's.

### Resolution

Two options:

**Option A (Recommended): API Proxy via Next.js rewrites** — Add a `rewrites` entry in `next.config.mjs` to proxy `/api/**` requests through Vercel to Railway. The browser calls `https://staging-walkability.kinariwala.com/api/...` (same-origin), Railway sets the cookie with `Domain=staging-walkability.kinariwala.com` (or no domain = defaults to the request host = Vercel), and the cookie IS visible to the Next.js middleware.

```js
// next.config.mjs addition
async rewrites() {
  return [
    {
      source: '/api/:path*',
      destination: `${process.env.INTERNAL_API_URL}/api/:path*`,
    },
    {
      source: '/uploads/:path*',
      destination: `${process.env.INTERNAL_API_URL}/uploads/:path*`,
    },
    {
      source: '/health',
      destination: `${process.env.INTERNAL_API_URL}/health`,
    },
  ]
}
```

With this approach: `NEXT_PUBLIC_API_URL=""` (empty string, same as docker-compose pattern), all API calls go through Vercel's edge, cookie is set on Vercel's domain, middleware works. `CORS_ORIGIN` on Railway must be set to `https://staging-walkability.kinariwala.com` (the Vercel URL, since that's now the origin making the server-side proxy request).

**CAUTION:** Vercel rewrites run server-side. File uploads (multipart/form-data) have a 4.5 MB body size limit on Vercel's serverless functions. The app allows 20 MB uploads. Rewrites for `POST /api/reports` (photo upload) will hit this limit.

**Option B: Change SameSite to None + fix middleware** — Change `SameSite::Strict` → `SameSite::None` in `admin_login` handler, set `Secure=true` unconditionally (already gated by `COOKIE_SECURE=true`), and modify the Next.js middleware to call `GET /api/admin/auth/me` on the backend to validate the session (instead of reading the local cookie). More complex but avoids Vercel's upload size limit.

**Hybrid (Best for this project):** Use Vercel rewrites for ALL routes EXCEPT `POST /api/reports` (the photo upload endpoint). Proxy everything else. For the upload endpoint, the frontend calls Railway directly via `NEXT_PUBLIC_API_URL`. This avoids the 4.5 MB Vercel limit while keeping admin auth working through the proxy.

**Simplest option for UAT only:** Add Next.js rewrites for `/api/admin/*` only (no upload path rewrites). Admin auth cookie is set on Vercel's domain through the proxy. Public report submission continues to call Railway directly. Both `NEXT_PUBLIC_API_URL` (for direct calls) and the rewrite rule (for admin) can coexist.

## Common Pitfalls

### Pitfall 1: Railway Deploy Context Mismatch

**What goes wrong:** Railway detects the Dockerfile at repo root and tries to build with the repo root as context. The `backend/Dockerfile` uses `COPY Cargo.toml ./` and `COPY src ./src` which reference paths relative to `backend/`. If build context is `/` (repo root), `COPY Cargo.toml ./` copies nothing (there is no Cargo.toml at repo root) and the build fails silently or produces an empty binary.

**Why it happens:** Railway's auto-detection scans for a Dockerfile anywhere in the repo. Without explicit configuration, it may pick the wrong context root.

**How to avoid:** In Railway service settings, set "Root Directory" to `backend`. This makes Railway use `backend/` as the Docker build context. The `Dockerfile` path then resolves relative to that root.

**Warning signs:** Build log shows `COPY Cargo.toml ./` but subsequent steps reference a `src/` that doesn't exist; `cargo build` fails immediately.

### Pitfall 2: NEXT_PUBLIC_API_URL Baking Order

**What goes wrong:** Developer deploys Railway first, then immediately deploys Vercel without setting `NEXT_PUBLIC_API_URL`. Vercel builds with the variable empty or missing. All client-side API calls use relative URLs (`/api/...`) which resolve to the Vercel domain and 404.

**Why it happens:** `NEXT_PUBLIC_*` variables are inlined at build time. A Vercel deploy triggered by the same git push that triggered Railway will run before the Railway backend URL is known.

**How to avoid:** Set `NEXT_PUBLIC_API_URL` in Vercel project settings BEFORE the first deploy. If using a stable Railway service name (e.g., project named `walkability-api`), the URL pattern `https://walkability-api.up.railway.app` can be predicted before Railway deploys.

**Warning signs:** Browser network tab shows `fetch("https://staging-walkability.kinariwala.com/api/reports")` returning 404.

### Pitfall 3: SameSite=Strict Breaking Admin Login (CRITICAL)

**What goes wrong:** Admin navigates to `https://staging-walkability.kinariwala.com/admin/login`, submits credentials. POST to `https://walkability-api.up.railway.app/api/admin/auth/login` succeeds (HTTP 200), but browser discards the `Set-Cookie` header (SameSite=Strict cross-site). Subsequent GET `/api/admin/auth/me` returns 401. The admin dashboard redirects to login on every page load.

**Why it happens:** `SameSite::Strict` in `backend/src/handlers/admin.rs` line 318. Browser spec: Strict cookies are not sent to cross-site origins.

**How to avoid:** Implement one of the three resolution options above before admin login testing. Verify cookie attributes in browser DevTools → Application → Cookies after login.

**Warning signs:** Login POST returns 200 but admin dashboard immediately redirects to `/admin/login`. Browser DevTools shows no `admin_token` cookie stored for the Vercel domain.

### Pitfall 4: PostGIS Template vs Standard Postgres

**What goes wrong:** Developer provisions Railway's standard "PostgreSQL" service (not the PostGIS template). Rust backend runs migrations. Migration `001_init.sql` runs `CREATE EXTENSION postgis` and fails: `ERROR: could not open extension control file ".../postgis.control": No such file or directory`. Backend crashes on startup.

**Why it happens:** Railway's standard Postgres image (`postgres:16-alpine` or similar) does not include PostGIS shared libraries or control files.

**How to avoid:** Deploy using the Railway PostGIS template (`https://railway.com/deploy/postgis`). This deploys Postgres 16 with PostGIS 3.4.0 pre-installed. pgcrypto is a standard PostgreSQL contrib extension and will be available.

**Warning signs:** Backend startup logs show `Failed to run database migrations` and mention `postgis.control`.

### Pitfall 5: Railway Cold-Start and Smoke Test Timing

**What goes wrong:** `deploy.yml` smoke test job runs immediately after the workflow is triggered. Railway's GitHub integration auto-deploy starts independently and may take 3-8 minutes for a Rust Docker build. Smoke test checks `/health` before Railway finishes deploying and marks the workflow as failed even though the deployment eventually succeeds.

**Why it happens:** Railway deploys asynchronously, not synchronously with GitHub Actions.

**How to avoid:** Add `sleep 30` before the retry loop to let Railway start the build. Use a retry loop (5 attempts × 15s = 75s additional wait) to accommodate build and cold-start time. Total wait: ~105s. Rust Docker builds with cache should complete within this window after initial setup.

**Warning signs:** Smoke test fails with "Connection refused" or "404" but checking the Railway dashboard shows a deploy in progress.

### Pitfall 6: CORS_ORIGIN Set to Wrong URL

**What goes wrong:** `CORS_ORIGIN` is set to `https://walkability-frontend.vercel.app` (the Vercel auto-assigned URL) instead of `https://staging-walkability.kinariwala.com` (the custom domain). Admin API calls from the custom domain return `CORS policy: No 'Access-Control-Allow-Origin' header`. The Axum CORS layer uses exact string matching.

**Why it happens:** The Vercel project has both a `*.vercel.app` URL and the custom domain. The custom domain is what the browser shows; CORS checks the `Origin` header which matches the browser's address bar URL.

**How to avoid:** Set `CORS_ORIGIN=https://staging-walkability.kinariwala.com` on Railway. If using the API proxy pattern (Option A above), the `Origin` header seen by Railway is the Vercel URL (the proxy's origin), so this may need to be the Vercel server IP or wildcard. Consult the proxy pattern's CORS behavior before finalizing.

## Code Examples

### Admin Seed Logic (no changes needed — idempotent)

```rust
// Source: backend/src/db/admin_seed.rs
// Runs on every startup. Skips if admin_users table already has rows.
pub async fn seed_admin_user(pool: &PgPool) {
    let email = std::env::var("ADMIN_SEED_EMAIL").unwrap_or_default();
    let password = std::env::var("ADMIN_SEED_PASSWORD").unwrap_or_default();

    if !should_seed(&email, &password) {
        return; // silently skips if env vars absent
    }

    let count: i64 = sqlx::query_scalar("SELECT COUNT(*) FROM admin_users")
        .fetch_one(pool).await?;

    if count > 0 {
        return; // idempotent: skips if admin already exists
    }
    // ... insert new super-admin
}
```

Key facts:
- Runs every boot — safe because it checks `COUNT(*) FROM admin_users` first
- Skips if `ADMIN_SEED_EMAIL` or `ADMIN_SEED_PASSWORD` is empty/whitespace
- Only sets `is_super_admin = TRUE` via this seed path
- Re-deploys on Railway are safe — seed is a no-op after first boot

### Cookie Fix — SameSite Change Required

```rust
// Current (breaks cross-domain): backend/src/handlers/admin.rs line 318
cookie.set_same_site(axum_extra::extract::cookie::SameSite::Strict);

// Required for Vercel + Railway split-domain:
cookie.set_same_site(axum_extra::extract::cookie::SameSite::None);
// NOTE: SameSite=None requires Secure=true (enforced by COOKIE_SECURE=true env var)
```

## Open Questions

1. **Vercel upload proxy size limit**
   - What we know: Vercel serverless functions have a 4.5 MB request body limit. The Axum backend allows 20 MB (set via `DefaultBodyLimit::max`).
   - What's unclear: Does Vercel's rewrite-based proxy enforce the same 4.5 MB limit, or is there a streaming proxy mode that avoids it?
   - Recommendation: Do NOT proxy `POST /api/reports` through Vercel. Let the browser POST directly to the Railway URL via `NEXT_PUBLIC_API_URL`. Only proxy `/api/admin/*` routes.

2. **Railway service public URL prediction**
   - What we know: Railway generates a URL based on the project/service name (e.g., `walkability-api.up.railway.app`).
   - What's unclear: The exact URL is assigned by Railway on first deploy and may not match the service name exactly.
   - Recommendation: Deploy Railway first, copy the assigned public URL, then set it as `NEXT_PUBLIC_API_URL` in Vercel and `RAILWAY_BACKEND_URL` in GitHub secrets.

3. **Cookie domain for admin_token with proxy**
   - What we know: With the admin API proxy (Option A), Railway's `Set-Cookie` response is forwarded to the browser by Vercel. The `Domain` attribute on the cookie may be set to Railway's domain, which would still be inaccessible from Vercel.
   - What's unclear: Does Next.js rewrites strip/rewrite the `Set-Cookie` Domain attribute, or does it forward Railway's domain?
   - Recommendation: Test in staging. If the cookie Domain is Railway's, the middleware check will fail. May need Vercel to strip the `Domain` attribute before forwarding, or use a custom response header handler in `next.config.mjs`. As a fallback, modify the middleware to call `GET /api/admin/auth/me` (through the proxy) instead of reading the local cookie directly.
