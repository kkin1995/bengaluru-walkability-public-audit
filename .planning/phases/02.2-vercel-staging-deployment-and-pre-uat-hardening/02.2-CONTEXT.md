# Phase 02.2: Vercel Staging Deployment and Pre-UAT Hardening - Context

**Gathered:** 2026-04-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Get the full stack onto a publicly accessible staging URL (`staging-walkability.kinariwala.com`) so GBA/Walkaluru stakeholders can do UAT before Phase 3 ships. The staging architecture differs from the production docker-compose.yml: Vercel hosts the Next.js frontend, Railway hosts the Rust/Axum backend + PostGIS database, and nginx is dropped (Railway handles HTTPS termination natively).

New product features (government triage workflow, export, analytics, public map enhancements) are NOT part of this phase.

</domain>

<decisions>
## Implementation Decisions

### Staging Architecture
- **D-01:** Frontend on **Vercel** (Next.js — natural fit; auto-deploy from GitHub). Backend (Rust/Axum binary) on **Railway** as a Docker service. PostGIS on **Railway Postgres** with PostGIS extension enabled.
- **D-02:** **nginx is dropped for staging.** Railway provides HTTPS termination natively; Vercel serves the frontend. The nginx service stays in `docker-compose.yml` unchanged for future production self-hosting.
- **D-03:** Target cost: within Railway Hobby plan's $5/mo credit at zero staging traffic. No persistent volume provisioning required for UAT — ephemeral uploads acceptable for a partner demo.

### Staging URL
- **D-04:** Staging URL: `https://staging-walkability.kinariwala.com` — a subdomain of the user's existing `kinariwala.com` domain. One-time setup: add a `CNAME staging-walkability → cname.vercel-dns.com` record at the DNS registrar, then add the custom domain in Vercel project settings.

### Critical Environment Variable Chain
- **D-05:** `NEXT_PUBLIC_API_URL` on Vercel **must be set to the Railway backend public URL** (e.g. `https://walkability-api.up.railway.app`). The docker-compose pattern of `NEXT_PUBLIC_API_URL=""` (relative URLs, nginx-proxied) does NOT work when frontend and backend are on different domains. This is the single most likely misconfiguration to break staging.
- **D-06:** `INTERNAL_API_URL` on Vercel must also point to the Railway backend URL (for server-side Next.js fetches in `admin/layout.tsx` etc.).
- **D-07:** `CORS_ORIGIN` on Railway must be set to exactly `https://staging-walkability.kinariwala.com`. The Axum backend uses `allow_credentials(true)` — no wildcard origin is permitted.
- **D-08:** `COOKIE_SECURE=true` on Railway (already the docker-compose default from Phase 02.1 — carry forward, do not override).

### Deployment Automation
- **D-09:** Railway wired to **GitHub integration auto-deploy from main branch** (Railway detects the Dockerfile automatically). Vercel also auto-deploys on git push. Both platforms redeploy on push to main independently.
- **D-10:** `deploy.yml` trigger: **CI-gated push to main + `workflow_dispatch`** as a second trigger. The `needs: ci` prerequisite already exists. The deploy job becomes a **post-deploy smoke test orchestrator** (Railway + Vercel auto-deploy handle the actual deployment; deploy.yml confirms staging is healthy after both redeploy).
- **D-11:** `workflow_dispatch` provides a deliberate "promote to staging" button for the day before a high-stakes GBA demo — same CI gate, explicit human trigger.

### Pre-UAT Hardening
- **D-12:** **Staging smoke tests in CI** — the `deploy` job in `deploy.yml` must hit `GET /health` and `GET /api/reports` on the Railway backend URL after deploy. Fails the workflow if staging is not serving. Implement as `curl -f` steps or equivalent.
- **D-13:** **Env var / secrets checklist** — create a documented checklist (in phase deliverables or STAGING-SETUP.md) of every required Railway and Vercel environment variable. Must be verified before the UAT link is shared with partners. Required vars:
  - Railway: `DATABASE_URL`, `JWT_SECRET`, `COOKIE_SECURE=true`, `CORS_ORIGIN`, `UPLOADS_DIR`, `PORT=3001`, `RUST_LOG=info`, `ADMIN_SEED_EMAIL`, `ADMIN_SEED_PASSWORD`
  - Vercel: `NEXT_PUBLIC_API_URL`, `INTERNAL_API_URL`
- **D-14:** **HTTPS-only enforcement** — verify Railway and Vercel both serve over HTTPS (both platforms enforce this by default on custom domains). Confirm `COOKIE_SECURE=true` is set on the Railway backend before admin login is tested.
- **D-15:** **Admin account verification** — confirm `ADMIN_SEED` runs on first Railway boot and the staging admin login returns a valid session. This is the gate before sharing the UAT link.

### UAT Data Setup
- **D-16:** **Minimal seeding** — only the initial admin account via `ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` env vars (already handled by existing seed logic on first boot). No pre-seeded reports. Partners will submit test reports themselves during UAT.

### Claude's Discretion
- Whether the env var checklist is a standalone `STAGING-SETUP.md` or embedded in the plan deliverables
- Exact Railway `railway.toml` configuration (if needed) vs. relying on pure GitHub integration auto-detection
- Whether `workflow_dispatch` trigger replaces or supplements the push-to-main trigger (supplement is the correct answer per discussion)
- Smoke test implementation details (curl steps vs. a shell script)
- Whether Railway volume provisioning for `/app/uploads` is needed for UAT (ephemeral is acceptable per D-03; planner to decide)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `.github/workflows/deploy.yml` — the placeholder stub is already structured correctly (`needs: ci` chain, deploy job shell); only the deploy step body needs to be replaced with smoke tests
- `frontend/app/lib/config.ts` — `NEXT_PUBLIC_API_URL` already sourced from env here; Vercel env var will be picked up automatically at build time
- `docker-compose.yml` env var block — complete reference for required Railway env vars (names are identical)

### Established Patterns
- `NEXT_PUBLIC_API_URL=""` in docker-compose — this is the Docker/nginx pattern (relative URLs). On Vercel + Railway, this MUST be set to the absolute Railway URL. This is the most common staging misconfiguration to guard against.
- `COOKIE_SECURE=${COOKIE_SECURE:-true}` default in docker-compose — carry forward to Railway env vars unchanged
- Admin seed: existing seeding logic fires on first boot using `ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` — no code changes needed, only env vars on Railway

### Integration Points
- Vercel project: add custom domain `staging-walkability.kinariwala.com`; set `NEXT_PUBLIC_API_URL` build arg + runtime env; set `INTERNAL_API_URL` runtime env
- Railway project: add Postgres service → enable PostGIS extension; add backend service from Dockerfile; set all required env vars; wire `DATABASE_URL` to Railway's internal Postgres URL
- DNS registrar (kinariwala.com): add `CNAME staging-walkability → cname.vercel-dns.com`
- `deploy.yml`: add `workflow_dispatch:` to `on:` block; replace deploy step body with post-deploy smoke test (`curl -f $RAILWAY_BACKEND_URL/health`, `curl -f $RAILWAY_BACKEND_URL/api/reports`)

### Known Risk
- **Image uploads on Railway**: the Rust backend writes uploaded photos to `UPLOADS_DIR`. Without a Railway persistent volume, uploads are lost on redeploy. Ephemeral uploads are acceptable for UAT (D-03), but the planner should document this limitation in the staging checklist and flag it for production planning.

</code_context>

<specifics>
## Specific Ideas

- `NEXT_PUBLIC_API_URL` must be the Railway backend URL — not empty string, not localhost. This is the single highest-risk misconfiguration for a Vercel+Railway split architecture.
- The smoke test in deploy.yml should run AFTER both Railway and Vercel have deployed. Use a short sleep or a retry loop before hitting `/health` to account for Railway cold-start on first deploy.
- Admin account verification is a manual pre-UAT checklist item, not an automated test — the planner should produce a one-page "before you send the link" checklist.
- CORS_ORIGIN must be the Vercel custom domain URL, not the `*.vercel.app` preview URL — set this on Railway before first UAT session.

</specifics>

<deferred>
## Deferred Ideas

- **nginx on Railway** — adds complexity with no benefit for staging; Railway handles HTTPS. Revisit only if staging needs to replicate rate-limiting behavior exactly (rate limiting is already in the Axum layer via `governor` crate).
- **Pre-seeded sample reports** — user chose minimal seeding for now. If partners need to see a populated map before submitting their own reports, a seed SQL script + synthetic photos could be added as a follow-on. Note for future UAT prep.
- **Custom civic domain (e.g. `walkability.in`)** — appropriate for public launch; `kinariwala.com` subdomain is correct for internal partner UAT staging. Domain registration for production launch belongs in a future phase or milestone.
- **Railway persistent volume for uploads** — needed for production-grade staging; acceptable as ephemeral for UAT. Should be addressed before production Railway deployment or when migrating to a VPS.

</deferred>
