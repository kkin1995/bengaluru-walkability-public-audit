# Phase 02.4 Cutover Checklist — Railway → Self-Hosted Desktop

Updates to external dashboards required to complete the cutover. Run AFTER Plans 01–03 are merged and the desktop runbook (DEPLOYMENT.md) has been completed.

**Last updated:** 2026-05-20

---

> **Do each section in order.** This checklist is the only manual / non-code step in Phase 02.4.
> Every item lives in a third-party dashboard rather than in the code repository.
> Skipping ahead (e.g. updating Vercel before GitHub Secrets are set) will leave the system
> in a broken intermediate state — the deploy workflow will fail or the frontend will still
> call the defunct Railway URL.

---

## 1. GitHub Repository Secrets

Path: **GitHub repo → Settings → Secrets and variables → Actions → Secrets tab**

### 1a. Remove

- [ ] Remove secret: **`RAILWAY_BACKEND_URL`** (this secret has no consumers after Plan 02 merges — the new `deploy.yml` uses `vars.BACKEND_URL` instead)

### 1b. Add

Add each secret by clicking **"New repository secret"**. Save every generated value to a password manager **before** pasting it — GitHub Secrets are write-only; the dashboard never re-displays the value after saving.

- [ ] **`POSTGRES_PASSWORD`** — postgres container password for the Arch Linux desktop deploy. Generate with:
  ```bash
  openssl rand -base64 32
  ```

- [ ] **`JWT_SECRET`** — backend session-token signing key (32+ chars required). Generate with:
  ```bash
  openssl rand -hex 32
  ```

- [ ] **`ADMIN_SEED_EMAIL`** — initial super-admin email address created on first boot. Use the operator's real email, or `admin@kinariwala.com` if the seed account will be discarded after first login.

- [ ] **`ADMIN_SEED_PASSWORD`** — initial super-admin password (12+ chars). Generate with:
  ```bash
  openssl rand -base64 24
  ```
  Store securely; change via Admin UI (`/admin/profile`) after first login.

> **Reminder:** GitHub Secrets are write-only from the UI. Once saved, the value is never
> shown again. Save every generated value to a password manager BEFORE pasting.

## 2. GitHub Repository Variables

Path: **GitHub repo → Settings → Secrets and variables → Actions → Variables tab**

GitHub "Variables" are non-secret configuration values exposed via `${{ vars.* }}` in workflow files. Unlike Secrets, their values are visible in workflow run logs — URLs belong here, not in Secrets.

- [ ] **`BACKEND_URL`** — public Cloudflare tunnel URL for the Arch Linux desktop backend. This is the value set in DEPLOYMENT.md Section 4e. Example:
  ```
  https://api-walkability.kinariwala.com
  ```

- [ ] **`FRONTEND_URL`** — Vercel frontend URL. Must NOT include a trailing slash. Example:
  ```
  https://staging-walkability.kinariwala.com
  ```

- [ ] **`CORS_ORIGIN`** — must equal `FRONTEND_URL` exactly (same value, no trailing slash). The Axum backend enables `allow_credentials(true)`, which means the CORS spec rejects wildcard origins — only the single exact origin you specify is accepted. Example:
  ```
  https://staging-walkability.kinariwala.com
  ```

> **CORS gotcha:** If `FRONTEND_URL` and `CORS_ORIGIN` drift apart — even by a trailing slash,
> a protocol mismatch, or a capitalisation difference — the browser will see CORS errors and
> admin login will silently fail (login appears to succeed but the cookie is never set).
> Double-check both values after entry.

## 3. GitHub Actions Environment

Path: **GitHub repo → Settings → Environments**

- [ ] Create environment named **`production`** (lowercase, exact match to the `environment: production` line in `.github/workflows/deploy.yml`)

  Sub-steps after creating the environment:
  - The deploy job requires this environment. If it does not exist, the deploy job will hang indefinitely in "Waiting" status in the Actions tab — it will never fail, just never proceed.
  - **Optional — required reviewers:** Add yourself as a required reviewer. This means any push to `main` pauses the deploy job and waits for a one-click approval in the Actions UI. Recommended as a defence-in-depth control against accidental deploys.
  - **Optional — wait timer:** Add a 1-minute wait timer. This gives a window to force-push a revert before the deploy actually runs on the desktop.

## 4. Vercel Environment Variables

Path: **Vercel project → Settings → Environment Variables**

> ⚠️ **`NEXT_PUBLIC_API_URL` is baked into the JavaScript bundle at Vercel build time.**
> Changing it WITHOUT triggering a Vercel redeploy will leave every user's browser pointing at
> the old (now-defunct) Railway URL. The entire app — report submission, map, admin login — will
> fail silently until a redeploy rebuilds the bundle with the new URL.

- [ ] Update **`NEXT_PUBLIC_API_URL`** in **Production AND Preview** scopes: change the value from the Railway URL to the Cloudflare tunnel URL (must equal `vars.BACKEND_URL` set in Section 2 exactly).

- [ ] Update **`INTERNAL_API_URL`** in **Production AND Preview** scopes: change the value from the Railway URL to the Cloudflare tunnel URL (same value as `NEXT_PUBLIC_API_URL` above). This variable is used by Next.js server components for server-side API calls — it is not baked at build time but must match the new backend URL.

- [ ] Trigger a **manual Vercel redeploy** to pick up the new `NEXT_PUBLIC_API_URL`:
  1. Go to **Vercel project → Deployments**
  2. Click the three-dot menu (⋯) on the latest Production deployment
  3. Select **"Redeploy"**
  4. When prompted, ensure **"Use existing Build Cache"** is set to **OFF** (to guarantee the new env vars are picked up rather than a cached bundle)
  5. Wait for the deployment to complete (green checkmark)

> Previous Vercel deployments continue to reference the old Railway URL until the redeploy
> completes. There is no automatic propagation — the redeploy step above is mandatory.

## 5. End-to-End Verification

Run through this list AFTER Sections 1–4 are complete AND the desktop deployment from DEPLOYMENT.md is up and running. Do not declare Phase 02.4 done until every item is checked.

Replace `<tunnel-url>` with the value of `BACKEND_URL` and `<frontend-url>` with the value of `FRONTEND_URL` throughout.

- [ ] `curl https://<tunnel-url>/health` returns `{"status":"ok"}` from the public internet via the Cloudflare Tunnel.

- [ ] `curl https://<tunnel-url>/api/reports` returns a valid JSON response (an array, possibly empty `[]` on a fresh deploy).

- [ ] The Vercel frontend loads at `<frontend-url>` without a blank page or browser console errors (open DevTools → Console before loading).

- [ ] Navigating to `<frontend-url>/admin/login`, entering `ADMIN_SEED_EMAIL` + `ADMIN_SEED_PASSWORD`, and clicking submit successfully redirects to `/admin/reports`.

- [ ] In browser DevTools (**Application → Cookies** after admin login), the `admin_token` cookie is present under the `<frontend-url>` domain with both `Secure` and `HttpOnly` attributes set.

- [ ] In a fresh incognito window, navigating directly to `<frontend-url>/admin/reports` redirects to `/admin/login` rather than rendering the page (auth guard is working).

- [ ] Submitting a test report at `<frontend-url>/report` (with a photo and GPS) returns a success message, and the new report pin appears on the public map at `<frontend-url>/map`.

- [ ] On the next `git push origin main`: the GitHub Actions **Deploy** workflow runs; the `deploy` job runs on the `walkability-prod` self-hosted runner (visible in the job header); the "Wait for local health" step passes; the `smoke-test` job passes against `vars.BACKEND_URL` and `vars.FRONTEND_URL`; the workflow completes green.

- [ ] SSH'd into the desktop (or running locally), `docker compose -f docker-compose.yml -f docker-compose.server.yml ps` shows `db`, `backend`, and `nginx` all with `healthy` status.

## Rollback

If the cutover fails (e.g. the Cloudflare Tunnel never connects after DEPLOYMENT.md is followed, or the desktop cannot be kept online), the rollback path is:

1. **Restore Vercel env vars:** Revert `NEXT_PUBLIC_API_URL` and `INTERNAL_API_URL` to the old Railway URL in Vercel project settings, then trigger a manual Vercel redeploy with Build Cache OFF (same process as Section 4 above).
2. **Restore GitHub Secrets:** Update `RAILWAY_BACKEND_URL` (or re-add it) with the Railway backend URL.
3. **Restore Railway:** If the Railway service was only paused, resume it. If it was deleted, rollback is no longer available.

> ⚠️ **Once the Railway project is deleted, rollback is permanently unavailable.** Railway projects
> cannot be restored after deletion. The desktop deploy MUST be verified end-to-end before the
> Railway project is deleted. Do not delete Railway until the Section 5 verification checklist
> is complete and a successful GitHub Actions deploy has run on the self-hosted runner.
