# Phase 04.1: Code Review Report

**Reviewed:** 2026-06-01T10:30:00Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

This phase implements: (1) migration 014 to bulk-link all 369 ward rows to their
corporation organisations via ILIKE; (2) two new analytics SQL constants
(`CORP_ANALYTICS_SQL`, `WARD_LINK_MIGRATION_SQL`) and query functions in
`admin_queries.rs`; (3) corresponding SQL-string tests in `analytics_tests.rs`;
and (4) frontend wiring for the corporation CORP column and compact-rows view in
`ReportsTable.tsx` and `adminApi.ts`.

The migration SQL itself is correct and idempotent. The frontend type definitions
are accurate for the new `assignUserOrg` / `listOrganizations` functions. The main
blocker is a type-system mismatch between the Postgres `NUMERIC` type returned by
`ROUND()` and the `f64` Rust type — this causes `resolution_rate_pct` to silently
return `null` for every corporation with at least one report, making ANALYTICS-03
non-functional. There are also three warnings around test accuracy, pagination
assumptions, and a misleading TypeScript type for duplicate report items.

## Critical Issues

### CR-01: `ROUND()` returns `NUMERIC` — `try_get::<f64>` silently returns `None` for every corporation (ANALYTICS-03 broken)

**File:** `backend/src/db/admin_queries.rs:1418-1465`

**Issue:** `CORP_ANALYTICS_SQL` uses `ROUND(100.0 * COUNT(...) / NULLIF(COUNT(...), 0), 1)`.
PostgreSQL's `ROUND(numeric, int)` returns type `NUMERIC` (OID 1700), not `float8`
(OID 701). The `Cargo.toml` declares `sqlx = { version = "0.7", features = ["postgres",
"runtime-tokio-rustls", "uuid", "chrono"] }` — the `bigdecimal` and `decimal` features
are absent. In sqlx 0.7, without those features there is no `Decode<f64>` implementation
for the NUMERIC OID. Therefore `r.try_get::<f64, _>("resolution_rate_pct").ok()` at
line 1460 always returns `Err` (type OID mismatch), which `.ok()` silently converts to
`None`. The corporation analytics endpoint will return `resolution_rate_pct: null` for
**all** corporations that have at least one report, making ANALYTICS-03 non-functional.
The `NULL` path (when `NULLIF` fires for zero-report corporations) is the only case where
`None` is correct, but the bug makes every non-zero case look identical.

**Fix:** Add an explicit cast in the SQL to `float8` to bypass the NUMERIC type:

```sql
-- In CORP_ANALYTICS_SQL, change:
ROUND(100.0 * COUNT(r.id) FILTER (WHERE r.status IN ('resolved', 'closed')) \
    / NULLIF(COUNT(r.id), 0), 1) AS resolution_rate_pct \

-- To:
ROUND(100.0 * COUNT(r.id) FILTER (WHERE r.status IN ('resolved', 'closed')) \
    / NULLIF(COUNT(r.id), 0), 1)::float8 AS resolution_rate_pct \
```

The `::float8` cast makes Postgres emit OID 701 which sqlx decodes as `f64` natively.
No Cargo.toml change is needed.

## Warnings

### WR-01: Unit test `list_admin_reports_with_org_id_includes_recursive_cte` simulates the wrong SQL structure — validates a different (PG < 12 incompatible) form

**File:** `backend/src/db/admin_queries.rs:1998-2031`

**Issue:** The test constructs the org CTE **inline inside** the `IN(...)` subquery:
`AND reports.ward_id IN (WITH RECURSIVE org_subtree AS (...) SELECT w.id ...)`. The
actual runtime code (lines 337-354) correctly places the CTE at the **top level** of the
query string as a `WITH RECURSIVE` prefix before `SELECT`. PostgreSQL 11 rejects inline
CTEs inside subquery expressions; the comment on lines 334-335 explicitly calls out this
compatibility concern. The test asserts only `full_where.contains("org_subtree")` and
`full_where.contains("w.org_id = s.id")` — both strings appear in both forms, so the
test passes regardless of placement. As a result, a regression that moved the CTE inline
would pass all tests while silently breaking the query on PG 11.

**Fix:** Rewrite the test to build the SQL exactly as the runtime does — CTE as a
prefix string — and assert it **starts with** `WITH RECURSIVE`:

```rust
fn list_admin_reports_with_org_id_includes_recursive_cte() {
    let org_id = Some(Uuid::nil());
    let (where_clause, mut param_idx) =
        build_report_where_clause(None, None, None, None, None, 1);
    let (cte_prefix, org_clause) = if org_id.is_some() {
        let cte = format!(
            "WITH RECURSIVE org_subtree AS (\
                SELECT id FROM organizations WHERE id = ${}\
                UNION ALL\
                SELECT o.id FROM organizations o\
                  JOIN org_subtree s ON o.parent_id = s.id\
            ) ",
            param_idx
        );
        param_idx += 1;
        let clause = " AND reports.ward_id IN (\
                SELECT w.id FROM wards w\
                  JOIN org_subtree s ON w.org_id = s.id\
            )".to_string();
        (cte, clause)
    } else {
        (String::new(), String::new())
    };
    assert!(
        cte_prefix.trim_start().starts_with("WITH RECURSIVE"),
        "CTE must be at top level, not inline in subquery (PG < 12 compat)"
    );
    assert!(org_clause.contains("w.org_id = s.id"), ...);
}
```

### WR-02: Test `auto_assign_history_sql_uses_open_status_and_null_changed_by` is self-referential — it validates a string it defines inline, not any production constant

**File:** `backend/src/db/admin_queries.rs:2228-2234`

**Issue:** The test defines its own `sql` string as a literal at line 2229 and then
asserts that the same literal contains `'open'::report_status` and `NULL`. This is
a circular assertion — it **always passes** regardless of what the production code
does, because the string being asserted is not derived from any constant or function
in the codebase. It also asserts `'open'::report_status`, which contradicts the
actual `assign_report_org` function (lines 758-760) that uses `'assigned'::report_status`.
There is no runtime or compile-time guard connecting this test to any auto-assignment
status history path.

**Fix:** Either (a) expose the auto-assignment note as a const and assert against it,
or (b) delete the test since it provides no behavioral coverage. At minimum, the doc
comment (which says "auto-assign status_history insert must use 'open' status") is
incorrect — the actual `assign_report_org` advances status to `'assigned'`, not `'open'`.

### WR-03: Pagination range display in `ReportsTable` hardcodes page-size `20` regardless of actual limit

**File:** `frontend/app/admin/components/ReportsTable.tsx:805`

**Issue:** The pagination range label is computed as:
```tsx
{((page - 1) * 20) + 1}–{Math.min(page * 20, totalCount ?? 0)} / {totalCount ?? 0}
```
The magic number `20` is the backend default limit, but `ReportsTableProps` does not
expose a `limit` prop. If the parent ever calls the reports API with a non-default
limit (e.g. `limit=50`), the displayed range will be wrong (showing "1–20" when the
actual window is "1–50"). This currently matches the backend default, but will silently
break if the call site changes.

**Fix:** Accept a `pageSize` (or `limit`) prop with a default of `20`:
```tsx
interface ReportsTableProps {
  // ...existing props
  pageSize?: number;  // defaults to 20 — must match the API call at the call site
}

// In pagination JSX:
const ps = pageSize ?? 20;
`${((page - 1) * ps) + 1}–${Math.min(page * ps, totalCount ?? 0)}`
```

## Info

### IN-01: `AdminReport` interface in `adminApi.ts` declares `updated_at: string` and `image_url: string` as non-optional, but duplicate items returned by `getDuplicatesForReport` lack both fields

**File:** `frontend/app/admin/lib/adminApi.ts:67-69`

**Issue:** `getDuplicatesForReport` calls `apiFetch<AdminReportListResponse>` and
returns `data.data as AdminReport[]`. The backend `get_duplicate_reports_for_original`
function (admin_queries.rs lines 479-497) does not include `updated_at`, `image_url`,
`location_source`, `assigned_org_id`, `assigned_org_name`, or `resolution_*` fields
in its JSON output. TypeScript does not catch this mismatch because `apiFetch` casts
with `as Promise<T>`. Runtime rendering in `DupeSubTable` only accesses `id`,
`created_at`, `ward_name`, `category`, `status`, and `severity` — all of which are
present — so the UI does not break. However, any future code that accesses
`dupe.image_url` or `dupe.updated_at` will get `undefined` at runtime with no
TypeScript error.

**Fix:** Define a narrower type for duplicate sub-table items:
```ts
export interface DuplicateReportSummary {
  id: string;
  created_at: string;
  image_path: string;
  latitude: number;
  longitude: number;
  category: string;
  severity: string;
  description: string | null;
  submitter_name: string | null;
  status: string;
  ward_name: string | null;
  duplicate_of_id: null;
  duplicate_count: 0;
  duplicate_confidence: null;
}
```
And update `getDuplicatesForReport` to return `Promise<DuplicateReportSummary[]>`.

### IN-02: `WARD_LINK_MIGRATION_SQL` mirror constant can silently drift from the actual migration file

**File:** `backend/src/db/admin_queries.rs:1481-1486`

**Issue:** The constant at line 1481 is documented as a "mirror" of migration
`014_link_wards_to_organisations.sql` to enable SQL-string tests. It is currently
accurate. However, there is no automated check that keeps them in sync: if the
migration file is updated (e.g. to add a `RETURNING` clause or change the `WHERE`
predicate), the constant will silently drift, and the test `ward_org_id_ilike_pattern_consistency`
will assert against the old string while the live migration runs different SQL.

**Fix:** Add a comment in migration `014_link_wards_to_organisations.sql` referencing
the mirror constant, and note in both locations that they must be changed together.
A stronger option is to load and compare the migration file content in a `#[test]`
using `include_str!` to make drift compile-time detectable:
```rust
const MIGRATION_014: &str = include_str!(
    "../../migrations/014_link_wards_to_organisations.sql"
);
// Then assert MIGRATION_014 contains the same ILIKE clause as WARD_LINK_MIGRATION_SQL.
```
