**Reviewed:** 2026-06-01T12:45:00Z
**Depth:** standard

## Summary

This phase implements: (1) migration 014 bulk-linking all 369 ward rows to their
corporation organisations via ILIKE; (2) `CORP_ANALYTICS_SQL` (with the `::float8`
cast applied — this is already fixed in the submitted code), `WARD_ANALYTICS_SQL`,
`TREND_SQL`, and `WARD_BOUNDARIES_SQL` constants and query functions in
`admin_queries.rs`; (3) SQL-string unit tests in `analytics_tests.rs`; and (4) frontend
wiring for the new `corporation` field in `adminApi.ts` and `ReportsTable.tsx`.

The migration SQL is correct, idempotent, and safe (all source values are
trusted seed data, not user input). The `::float8` cast in `CORP_ANALYTICS_SQL` is
correctly applied. The `AdminReport.corporation: string | null` TypeScript addition is
well-typed.

Two blockers were found. First, `list_admin_reports` derives the `corporation` field
from `reports.assigned_org_id` (the manually-assigned org), not from `wards.org_id`
(the ward's natural corporation populated by migration 014). This means the CORP column
in the table list shows `null` for every unassigned report — the entire population of
new/open reports — defeating the purpose of migration 014 for the list view. Second,
the unit test for the recursive CTE builds a structurally different (inline, PG < 12
incompatible) SQL form than the runtime code, giving it no real regression value.

## Critical Issues

### CR-01: `list_admin_reports` derives `corporation` from `assigned_org_id`, not `wards.org_id` — CORP column shows `null` for all unassigned reports

**File:** `backend/src/db/admin_queries.rs:386-390` (SQL), `443` (comment), `2192-2224` (test NF-03-B)

**Issue:** The list query SELECT at line 386 reads:
```sql
o.name AS corporation,
...
LEFT JOIN organizations o ON o.id = reports.assigned_org_id
```
It joins `organizations` on `reports.assigned_org_id` — the org to which the report was
manually assigned. This field is `NULL` until a reviewer explicitly assigns the report.
For every unassigned report (all `open`, `acknowledged`, and freshly-created reports), the
`corporation` column is `NULL`, so the CORP column in the table renders `—`.

Migration 014 populates `wards.org_id` specifically so that each ward's corporation can
be derived from geography, without requiring manual assignment. The detail view
(`get_admin_report_by_id`, line 543) correctly uses `LEFT JOIN organizations o ON o.id =
w.org_id`. The list view does not.

The comment at line 443 states "corporation is auto-derived at query time via LEFT JOIN
wards" which is factually wrong — no join to wards feeds the `corporation` alias in the
list query. The test `list_admin_reports_corp_join_uses_assigned_org_id` at line 2192
locks in this wrong behavior as an explicit contract, preventing future correction.

The `ward_hierarchy?.corporation` fallback in `ReportsTable.tsx:1051` also never fires
for list-view reports because `ward_hierarchy` is only returned by the detail endpoint,
not by `list_admin_reports`.

**Fix:** Change the list query to join on `wards.org_id` (consistent with the detail
view and with migration 014's intent), and update the test assertion accordingly:

```sql
-- Replace (line 390):
LEFT JOIN organizations o ON o.id = reports.assigned_org_id

-- With:
LEFT JOIN organizations o ON o.id = wards.org_id
```

The existing `LEFT JOIN wards ON wards.id = reports.ward_id` at line 389 is already
present — only the `organizations` join target needs changing. Also update the comment
at line 443 and relax or invert the assertion in test `list_admin_reports_corp_join_uses_assigned_org_id`.

### CR-02: Unit test `list_admin_reports_with_org_id_includes_recursive_cte` builds the CTE inline inside `IN(...)` — does not match the runtime top-level CTE structure

**File:** `backend/src/db/admin_queries.rs:1998-2031`

**Issue:** The runtime code (lines 337-354) places the `WITH RECURSIVE org_subtree AS (...)`
clause as a top-level CTE **before** the `SELECT` keyword — a valid form on all PostgreSQL
versions. The test (line 2006) constructs a different SQL structure: it places the CTE
inline inside a subquery expression:

```sql
AND reports.ward_id IN (
    WITH RECURSIVE org_subtree AS (...) SELECT w.id FROM wards w ...
)
```

This inline-CTE-in-subquery form is non-standard and rejected by PostgreSQL 11 and
earlier. The runtime code comment at line 334–335 explicitly calls out this PG < 12
incompatibility as the reason the CTE is top-level. The test asserts only
`full_where.contains("org_subtree")` and `full_where.contains("w.org_id = s.id")` —
both substrings appear in both forms, so the test passes regardless of CTE placement. A
regression that moved the CTE inline would pass all tests while breaking the query on
PG 11.

**Fix:** Rewrite the test to mirror the actual runtime code path — build `cte_prefix`
as a top-level prefix and assert it starts with `WITH RECURSIVE`:

```rust
fn list_admin_reports_with_org_id_includes_recursive_cte() {
    let (where_clause, mut param_idx) =
        build_report_where_clause(None, None, None, None, None, 1);
    let (cte_prefix, org_clause) = {
        let cte = format!(
            "WITH RECURSIVE org_subtree AS (\
                SELECT id FROM organizations WHERE id = ${}\
                UNION ALL\
                SELECT o.id FROM organizations o\
                  JOIN org_subtree s ON o.parent_id = s.id\
            ) ",
            param_idx
        );
        param_idx += 1;
        let clause = " AND reports.ward_id IN (\
                SELECT w.id FROM wards w\
                  JOIN org_subtree s ON w.org_id = s.id\
            )".to_string();
        (cte, clause)
    };
    assert!(
        cte_prefix.trim_start().starts_with("WITH RECURSIVE"),
        "CTE must be top-level prefix before SELECT, not inline in subquery (PG 11 compat)"
    );
    assert!(org_clause.contains("w.org_id = s.id"), "...");
}
```

## Warnings

### WR-01: Test `auto_assign_history_sql_uses_open_status_and_null_changed_by` is a self-referential assertion — validates an inline string literal, not any production constant

**File:** `backend/src/db/admin_queries.rs:2228-2234`

**Issue:** The test defines its own `sql` literal at line 2229 and then asserts that the
same literal contains `'open'::report_status` and `NULL`. The string being asserted is
never derived from any production constant or function — it is constructed inside the
test itself. This is a circular assertion: it always passes regardless of what production
code does.

The actual auto-assignment SQL lives in `backend/src/handlers/reports.rs:309` and is
not exported as a constant. If that handler SQL changes (e.g., status changed from
`'open'` to `'submitted'`), this test still passes. There is no enforced link between
the test literal and the live handler SQL.

Additionally, the assertion `'open'::report_status` contradicts the manual
`assign_report_org` function (lines 758-760) which uses `'assigned'::report_status`.
The doc comment conflates the geographic auto-assign (at report submission time, which
uses `'open'`) with manual org assignment.

**Fix:** Either expose the handler's auto-assign SQL as a constant in `admin_queries.rs`
(or `queries.rs`) and reference it in the test, or delete the test and add it to the
handler's own test suite. If kept, the doc comment must clarify it tests the geographic
auto-assign path at submission time, not `assign_report_org`.

### WR-02: Pagination range display in `ReportsTable` hardcodes page-size `20` — will silently show wrong range if limit changes

**File:** `frontend/app/admin/components/ReportsTable.tsx:805`

**Issue:** The pagination range label is:
```tsx
{((page - 1) * 20) + 1}–{Math.min(page * 20, totalCount ?? 0)} / {totalCount ?? 0}
```
The magic number `20` is the current backend default limit, but `ReportsTableProps`
(lines 40-54) has no `limit` or `pageSize` prop. If any call site passes a different
limit (the map page at `admin/reports/map/page.tsx` already uses `limit: 200`), the
displayed range will be wrong. The component is also used in tests with
`pagination: { page: 1, limit: 20, ... }` confirming the expected interface expects
limit to be available.

**Fix:** Accept an optional `pageSize` prop defaulting to `20`:
```tsx
interface ReportsTableProps {
  // ...
  pageSize?: number; // must match the limit passed to getAdminReports at the call site
}
// In pagination JSX:
const ps = pageSize ?? 20;
{((page - 1) * ps) + 1}–{Math.min(page * ps, totalCount ?? 0)}
```

### IN-01: `WARD_LINK_MIGRATION_SQL` mirror constant can silently drift from the actual migration file with no compile-time detection

**File:** `backend/src/db/admin_queries.rs:1481-1486`

**Issue:** The constant at line 1481 is documented as a mirror of
`014_link_wards_to_organisations.sql` to enable SQL-string tests. The two are currently
consistent. However, no automated check enforces synchronisation: if the migration file
is later updated (e.g., to add `RETURNING`, change the `WHERE` predicate, or add a
schema-qualified table name), the constant silently drifts and the test
`ward_org_id_ilike_pattern_consistency` will assert against stale SQL while the live
migration runs different logic.

**Fix:** Use `include_str!` to make synchronisation compile-time enforced:
```rust
// Instead of a hand-maintained mirror, embed the file directly:
const MIGRATION_014_SQL: &str = include_str!(
    "../../migrations/014_link_wards_to_organisations.sql"
);
// Then assert MIGRATION_014_SQL contains the expected ILIKE clause.
```
This makes a drift between the file and the test a compile error.

### IN-02: `onCategoryChange` and `onStatusFilter` are declared in `ReportsTableProps` but never destructured or used

**File:** `frontend/app/admin/components/ReportsTable.tsx:46-47`

**Issue:** Both `onCategoryChange?: (value: string) => void` and
`onStatusFilter?: (value: string) => void` are declared in the interface but are not
included in the component's destructuring pattern (line 558-570) and are never called
anywhere in the component body. TypeScript does not warn about this because they are
optional. Internal filter state is managed via `activeFilters` (client-side), so the
server-side filter callbacks these props imply are never invoked.

**Fix:** Remove the two props from `ReportsTableProps` or, if server-side filtering was
planned, add the implementation. Callers passing these props silently receive no-ops.

### IN-03: `getDuplicatesForReport` in `adminApi.ts` returns `AdminReport[]` but the backend returns a narrower shape lacking several required fields

**File:** `frontend/app/admin/lib/adminApi.ts:239-246`

**Issue:** `getDuplicatesForReport` casts the API response to `AdminReportListResponse`
and returns `data.data as AdminReport[]`. The backend `get_duplicate_reports_for_original`
(admin_queries.rs lines 463-499) omits `updated_at`, `image_url`, `location_source`,
`submitter_contact`, `assigned_org_id`, `assigned_org_name`, and `resolution_*` fields.
`AdminReport` declares `updated_at: string` and `image_url: string` as non-optional
required fields — so the cast is unsound. TypeScript does not catch this because
`apiFetch` uses `as Promise<T>`.

The rendering code in `DupeSubTable` only accesses `id`, `created_at`, `ward_name`,
`category`, `status`, `severity` — all present — so there is no visible runtime error
today. Future code accessing `dupe.updated_at` or `dupe.image_url` will receive
`undefined` silently.

**Fix:** Define a narrower type for duplicate summary items and use it:
```ts
export interface DuplicateReportSummary {
  id: string;
  created_at: string;
  image_path: string;
  latitude: number;
  longitude: number;
  category: string;
  severity: string;
  description: string | null;
  submitter_name: string | null;
  status: string;
  ward_name: string | null;
}

export async function getDuplicatesForReport(
  originalId: string
): Promise<DuplicateReportSummary[]> { ... }
```
