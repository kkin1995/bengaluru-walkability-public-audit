**Summary:** Admin portal footer shows `BUILD_HASH: 0000000` instead of the actual git commit SHA.

### Finding UAT-01-06
**Severity:** 🔴 Critical  
**Section:** B — Citizen Portal  
**Test Case:** B7.3, B7.4  
**Summary:** Photos do not render on the public report detail page. Photos DO load correctly in the admin portal (queue cards and report detail view), so this is not a global storage or nginx failure.  
**Steps to reproduce:** Open map → tap any marker → tap "Read More →" → observe photo area.  
**Expected:** Submitted photo renders in the image area.  
**Actual:** Grey/white gradient with "?" broken image icon and raw partial report UUID visible (e.g. `31C990D8`). Affects all reports. IMG_4831.PNG, IMG_4833.PNG.  
**Confirmed scope:** Admin portal serves photos correctly (IMG_4841). Public detail page does not. The issue is specific to the photo URL or auth logic used by the public-facing Next.js component.  
**Likely cause:** The public detail page `<img src>` is using a different path or origin than the admin portal uses. Two candidate causes: (1) the public component builds a photo URL pointing to the wrong host or path prefix, (2) the nginx `uploads` location block requires authentication, making photos auth-gated and inaccessible to unauthenticated public users.  
**Immediate check:** Inspect the `src` attribute of the broken image in Safari dev tools on the public detail page and compare to the working `src` used in the admin queue card.  
**Must fix before sign-off.**

### Finding UAT-01-07
**Severity:** 🟡 Medium  
**Section:** C — Admin Portal  
**Test Case:** C2.4  
**Summary:** Report photo renders rotated 90° in the admin detail view.  
**Steps to reproduce:** Log in → QUEUE → tap any report submitted from an iPhone → observe photo at top of detail page.  
**Expected:** Photo renders in correct upright orientation.  
**Actual:** Photo appears rotated 90° clockwise. IMG_4841.PNG.  
**Cause:** EXIF metadata stripped on upload for privacy. iOS cameras embed orientation in EXIF — when stripped, browsers render raw sensor orientation. **Fix:** Before stripping EXIF, read the orientation tag and bake the correct rotation into the pixel data using `sharp` (Node) or `image-rs` (Rust). Do not use CSS workaround — fix at ingest.

### Finding UAT-01-08
**Severity:** 🔵 Low  
**Section:** C — Admin Portal  
**Test Case:** C2.3  
**Summary:** `LOCATION_SRC: MANUAL_PIN` label is misleading — the location came from the browser Geolocation API, not a user-dragged pin.  
**Explanation:** When the iOS camera is opened from a web browser, iOS does not write GPS EXIF to the captured photo. The app therefore uses the browser Geolocation API to capture location separately. `MANUAL_PIN` is the internal label for this path (as opposed to a future `EXIF_GPS` source). The behavior is correct.  
**Issue:** The label implies user-manual action. A citizen who used the "Adjust" pin tool and one who didn't will both show `MANUAL_PIN`, making the field uninformative for admin triage.  
**Suggested label:** `GPS_API` for Geolocation API captures, `MANUAL_ADJUST` for cases where the user explicitly dragged the pin, `EXIF_GPS` for future EXIF-derived sources.  
**Screenshot:** IMG_4841.PNG  
**Notes:** Cosmetic only — no functional or data integrity issue.

### Finding UAT-01-11
**Severity:** 🟡 Medium  
**Section:** C — Admin Portal  
**Test Case:** C1.4, C1.6  
**Summary:** Admin dashboard "+N today" counter shows incorrect values and decrements when reports are moved out of Submitted status, despite no new reports being submitted.  
**Steps to reproduce:** Note "+3 today" → move one report to In Progress (no new submissions) → return to dashboard → counter reads "+2 today".  
**Expected:** "+N today" is an immutable count of new reports received today, unaffected by status changes.  
**Actual:** Counter dropped from +3 to +2 with zero new submissions in the interval. Confirmed by tester: no reports were submitted in this window. The counter is filtering on current status rather than counting immutable creation events. IMG_4876.PNG, IMG_4877.PNG.  
**Fix:** Change the query for "+N today" to `COUNT(*) WHERE created_at::date = CURRENT_DATE` with no status filter. The SUBMITTED / UNDER REVIEW / RESOLVED stat cards already serve the status-breakdown purpose.
